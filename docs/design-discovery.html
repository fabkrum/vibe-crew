Design Discovery

How VibeCrew Creates a Design System Tailored to Your Product

Design Discovery replaces the generic “pick a color” approach with a 3-phase contextual interview that understands what you're building, who it's for, and how it should feel. The result is a design system that encodes real product understanding — not just aesthetic preferences.

Design Discovery runs during /new-project as Tier 1 Step 2, between VISION.md (goals) and the TDR (technology decisions). It produces two artifacts:

CSS

design-system.css

CSS custom properties for colors, typography, spacing, radii, shadows, transitions, and layout context. Every component references these tokens.

MD

design-brief.md

The “why” document. Captures product context, visual direction rationale, component preferences, and design principles for agents to reference.

Phase 1

Product & Audience Context

Five questions establish who you're building for and how the product should feel. Every question offers predefined options and a free-text alternative — you're never locked into the provided choices.

#QuestionOptions
Q1 What are we building? SaaS dashboard · Marketplace / e-commerce · Content platform · Mobile-first tool · Social / community · Creative tool · or describe it
Q2 Who uses it? Technical professionals · Non-technical consumers · Enterprise teams · Creative freelancers · Students / learners · or describe them
Q3 How do they use it? Quick daily checks · Deep focused sessions · On-the-go mobile · Collaborative team use · Passive consumption · or describe the usage
Q4 How should it feel? Trustworthy & professional · Playful & energetic · Minimal & calm · Bold & premium · Warm & approachable · or describe the feeling
Q5 What is the primary thing users do? Analyze data · Create content · Manage workflows · Browse & discover · Communicate · Transact · or describe the action

Free-Text Interpretation

When you type your own answer instead of picking an option, VibeCrew interprets it, maps it to design parameters, and confirms before proceeding.

Example

You type: “busy nurses checking patient vitals between rounds”
VibeCrew interprets: quick daily checks + trustworthy & professional + analyze data, and confirms this mapping with you before moving on.

After all 5 answers, a summary is presented:

“We're building a SaaS dashboard for enterprise teams, designed for deep focused sessions. It should feel trustworthy & professional, focused on analyzing data.”

Profile Adaptations

  • Minimal verbosity: Options only, no explanations of why each question matters
  • Educational verbosity: Explains the UX principle behind each question before asking
  • Supervised autonomy: Confirms the summary before proceeding to Phase 2
  • Full-auto autonomy: Skips the interview entirely. Uses VISION.md to infer answers, picks Direction A, and generates both files immediately
Phase 2

Visual Direction

Based on your Phase 1 answers, VibeCrew generates 3 tailored visual directions. These aren't generic — a “SaaS dashboard that should feel trustworthy” gets very different options than a “mobile tool that should feel playful.”

What Each Direction Includes

For each of the 3 directions, VibeCrew generates:

  • Name — 2-3 words (e.g., “Linear Finance”)
  • Reference — 1-2 known products for inspiration
  • Color palette — Primary HSL, neutral temperature, accent approach
  • Typography — Heading + body font pairing
  • Spacing/density — Compact, comfortable, or spacious
  • Border radius — Sharp, subtle, rounded, or pill
  • Shadow strategy — Flat, subtle, layered, or dramatic
  • One-line vibe — A sentence capturing the feel

The three directions are presented as a compact comparison, and you choose: A, B, C, or describe your own direction in free text. If you describe a custom direction, VibeCrew generates the full specification and confirms before proceeding.

Example Directions

For “SaaS dashboard + trustworthy & professional”, you might see:
A: Bloomberg Modern — Dense, data-first, monospace headings, cool neutrals
B: Linear Finance — Clean geometry, Inter + JetBrains Mono, subtle shadows
C: Stripe Dashboard — Premium purple accents, generous spacing, layered depth

Phase 3

Component Preferences

The final phase asks 2-3 questions about component patterns, filtered by your Phase 1 answers. A dashboard gets different navigation options than a content platform.

Q6: Navigation Style (always asked)

Options vary by product category:

  • Dashboards: Sidebar / top bar / combined
  • Content & marketplace: Top nav / hamburger / tab bar
  • Mobile-first: Bottom tab bar / hamburger slide-out / gesture-based

Q7: Data Display (conditional)

Only asked if your primary action involves data, workflows, or transactions:

  • Dense tables / card grid / list view / mixed layout

Q8: Interaction Density (always asked)

  • Minimal — Lots of whitespace, one action per view
  • Moderate — Balanced density, grouped actions
  • Dense — Information-rich, multiple actions visible

These preferences directly inform the Builder agent during Tier 2 feature development. When creating components, the Builder reads the design brief to know whether to use sidebar navigation, card grids vs tables, and how dense to make the interface.

Output

Output Artifacts

design-system.css

A complete set of CSS custom properties on :root. Token categories:

  • Colors — HSL-based primary, secondary, neutral, and semantic colors with dark mode overrides
  • Typography — Modular scale (1.25 ratio), font families, weights, line heights
  • Spacing — 4px base unit, --spacing-1 through --spacing-24
  • Border radius — Scale from --radius-sm to --radius-full
  • Shadows — Layered from --shadow-xs to --shadow-xl
  • Transitions — Fast (150ms), normal (250ms), slow (350ms)
  • Layout context — --density-factor, --content-width-max, --nav-width (from Design Discovery)
CSS/* Usage in components */
.dashboard-sidebar {
  width: var(--nav-width);
  background: var(--color-surface);
  border-right: 1px solid var(--color-border);
  padding: var(--spacing-4);
}

.data-table td {
  padding: calc(var(--spacing-3) * var(--density-factor));
  font-size: var(--font-size-sm);
  color: var(--color-foreground);
}

design-brief.md

The “why” document that captures every decision and its rationale. Sections include:

  • Product Context — Category, audience, usage pattern, emotional direction, key action
  • Visual Direction — Chosen direction name, reference products, rationale
  • Design Tokens Summary — Key tokens with reasoning for each choice
  • Component Preferences — Navigation, data display, interaction density with rationale
  • Design Principles — 3 principles derived from context
  • Accessibility Baseline — WCAG AA, focus indicators, touch targets, reduced motion
Customization

Customization & Iteration

The Approve / Edit / Skip Flow

After both files are generated, VibeCrew presents a summary and asks: “Does this design direction feel right?”

  • Approve — Lock in the design system and proceed to TDR
  • Edit — Specify what to change (colors, fonts, density, etc.) and VibeCrew revises
  • Skip — Mark as skipped and move on (you can always come back)

Extending During Tier 2

The design system is not static. During feature development, the Builder agent can add new tokens (e.g., a feature-specific accent color) but cannot modify existing tokens without developer approval. This preserves consistency across the application while allowing organic growth.

Design Brief as Agent Context

The design-brief.md file gives the Builder agent product awareness beyond raw design tokens. When creating a new component, the Builder reads the design brief to understand:

• Navigation style — Should this page use a sidebar or top nav?
• Data display — Should data render as tables, cards, or lists?
• Interaction density — How much whitespace between elements?
• Audience context — Are users technical or non-technical? Quick glances or deep sessions?

This transforms the Builder from “apply these tokens” to “design for this audience with these tokens.”

Advanced Workflows

VibeCrew v1.4.0 introduced four advanced workflows that extend the development lifecycle: reusable session templates, automated code simplification, self-healing CI, and adversarial review of technology decisions.

Workflow Templates (/replay)

Capture what worked and reuse it. /replay extracts reusable workflow templates from successful sessions (Vibe Score ≥ 70) so you can apply proven patterns to future features.

Three modes

☰

List templates

Run /replay with no arguments to list all saved workflow templates with their names, descriptions, and quality thresholds.

+

Create a template

Run /replay --create <name> to extract a template from the most recent high-scoring session. Captures phase order, branch conventions, test strategy, and quality thresholds.

▶

Apply a template

Run /replay <name> to load a template and have it guide your current feature development with the proven workflow.

When to create templates

After a session scores 90+, create a template. Common examples: "api-feature" for CRUD endpoints, "ui-component" for design-system-aligned components, "data-migration" for schema changes. Templates are stored in .vibecrew/workflows/.

Code Simplification (/simplify)

After building a feature, run /simplify to get an Opus-powered analysis of your code for unnecessary complexity. The agent operates in a read-only worktree — it analyzes but never modifies your code directly.

The simplification cycle

/simplify collects files changed on the feature branch ↓ Launches the Code Simplifier agent (Opus, worktree, read-only) ↓ Agent analyzes four categories: Dead code · Abstraction flattening · API simplification · Dependency reduction ↓ Presents suggestions one at a time for your approval ↓ Each accepted change is applied and tests re-run If tests fail → automatic revert

Suggestions are categorized by impact (high, medium, low) and include before/after snippets, estimated line reduction, and confidence ratings. You approve or reject each individually. Reports are saved to .vibecrew/simplifications/.

Safe by design

The analysis agent cannot write files. Only the /simplify skill applies approved changes in the main session, and every change is verified by running your test suite. Failed tests trigger an automatic revert.

Auto-Healing CI (/heal)

When CI fails, run /heal instead of manually debugging logs. The CI Healer fetches the failure logs from GitHub Actions, diagnoses the root cause, and applies targeted fixes — up to 3 attempts.

How it works

  1. Fetch and diagnose

    /heal runs gh run view --log-failed to retrieve the CI output, then pattern-matches errors to categorize the failure: build, test, lint, dependency, or environment.

  2. Checkpoint

    Before any fix, a git checkpoint is created so all changes can be reverted cleanly if the fix doesn't work.

  3. Fix loop (max 3 attempts)

    The CI Healer agent applies the minimum viable fix for the diagnosed failure, then pushes and waits for CI. If CI fails again, it re-diagnoses with the new context and tries a different approach.

  4. Report

    A heal report is saved to .vibecrew/ci-heals/ documenting each attempt, diagnosis, fix, and outcome. If all 3 attempts fail, the healer escalates to you with a summary of what it tried.

Failure CategoryCommon PatternsFix Strategy
BuildTypeScript errors, missing imports, syntax errorsFix the type error or import at its source
TestAssertion failures, snapshot mismatches, timeoutsUpdate assertion/snapshot or fix the logic bug
LintESLint/Prettier violationsAuto-fix with the project's lint command
DependencyMissing packages, version conflictsInstall missing dep or resolve version conflict
EnvironmentMissing env vars, wrong Node version, permission errorsUpdate CI config (YAML/TOML) to match requirements

Opponent Processor (TDR Debate)

Every technology decision deserves a devil's advocate. During Tier 1, after the Stack Scout produces the TDR, VibeCrew automatically invokes the Opponent Processor — a read-only agent that challenges every decision.

What it produces

✗

Counter-arguments

For each technology decision, the opponent generates 2–3 reasons why the choice might be wrong, citing real-world failure modes and edge cases.

⚖

Debate matrix

A structured comparison table scoring each option across 6 criteria: performance, DX, ecosystem, scalability, learning curve, and lock-in risk.

⚠

Risk assessment

Identifies the highest-risk decisions and recommends which ones deserve extra scrutiny or prototyping before committing.

After reviewing both the TDR and the counter-analysis, you choose: keep the original decisions, reconsider specific choices, or skip the review. The opponent's analysis is saved alongside the TDR for future reference.

Why adversarial review matters

The Stack Scout is optimized to find the best answer quickly. The Opponent Processor is optimized to find where that answer might break. Together, they produce more robust technology decisions than either could alone. This is especially valuable for decisions that are expensive to reverse (database choice, state management, auth provider).

VibeCrew provides real-time cost visibility and multi-layered safety enforcement. Cost tracking runs at zero token cost via hook scripts, and safety hooks block destructive operations before they execute.

Cost Guardrails

The cost-guardrails.sh hook runs on every Stop event, calculating per-turn costs with model-aware pricing and accumulating totals in .vibecrew/session-cost.json.

Daily totals are calculated by summing estimated_cost_usd from all session files matching today’s date, plus the live session cost. All thresholds are configurable in .vibecrew/config.json.

Safety Hooks

Three layers of protection run as PreToolUse hooks, blocking operations before they execute:

■

protect-data.sh

Blocks destructive bash commands: rm -rf, git push --force, DROP TABLE, sudo, kill -9, chmod 777, and more. 18 denied tool patterns in settings.json.

■

phase-gate.sh

Blocks source code writes (src/, app/, lib/, components/) until all Tier 1 foundation artifacts exist. Allows config and docs writes always.

■

restrict-paths.sh

Validates that write targets are within the project directory and match allowed path patterns. Prevents accidental writes to system files or other projects.

Permission rules

settings.json defines 71+ permission rules: 53 allowed tool patterns (npm, git, gh, jq, standard dev tools) and 18 denied patterns (sudo, force push, hard reset, kill -9, mkfs, dd). These are enforced at the Claude Code level before any hook runs.

Checkpoint safety net

Both /heal and /new-feature create a git checkpoint (vibecrew-checkpoint-<timestamp>) before making changes. If anything goes wrong, /undo can roll back to any checkpoint. Checkpoints are lightweight git tags that don’t add repository overhead.

How language detection works

detect-conventions.sh scans project root for manifests ↓ Identifies language from: package.json, pyproject.toml, Gemfile, go.mod, Cargo.toml, composer.json, pom.xml ↓ extract-project-conventions.sh detects per-language: framework, ORM, auth library, API patterns, naming conventions ↓ Results feed into Code Auditor and CLAUDE.md generation

Where language support applies

  • /onboard — Code Auditor detects language, conventions, frameworks, and test gaps for all 7 languages
  • /audit — Security Auditor runs language-specific dependency audit tools and adapts OWASP scanning patterns
  • PostToolUse formatting — format-code.sh auto-formats with the correct tool: Prettier (JS/TS), Black (Python), rustfmt (Rust), gofmt (Go)
  • /new-project — Stack Scout research adapts to the detected or chosen language ecosystem
Non-Node.js confidence levels

Node.js/TypeScript projects receive “high” confidence from the Code Auditor due to deeper ecosystem integration. Other languages receive “medium” confidence — the core workflow (Tier 1 foundation, Tier 2 cycle, Vibe Score, hooks) works identically, but framework-specific patterns may need manual refinement in CLAUDE.md.

Progression

Gamification System

VibeCrew includes a persistent progression layer that motivates across sessions and teaches vibe-coding skills over time. Built on three principles: artifacts over actions (rewards map to real outputs), teaching over tracking (every mechanic helps you improve), and sustainable over addictive (grace periods, opt-in challenges, no toxic leaderboards).

The gamification system uses the existing Vibe Score as its primary data source. Every metric flows from real work artifacts — shipped features, passing tests, clean sessions — not arbitrary actions.

How it integrates

The gamification pipeline runs automatically at the end of every /wrap. Six scripts execute sequentially: award XP, check badges, update streak, distribute skill XP, update challenges, and check level-ups. The /achievements command shows a compact CLI summary, and the VitePress dashboard provides the full visual experience.

Streaks

Streaks track consecutive days of coding, designed to be encouraging rather than punitive.

  • Increment on calendar days where /wrap is run
  • Weekend auto-grace: Saturdays and Sundays don’t break streaks and don’t consume grace credits
  • 2 grace days/month: Missing one weekday preserves the streak (resets on the 1st)
  • No penalty for broken streaks — the counter resets to 0 but no XP is lost
  • Streak reminders are opt-in (disabled by default in config.json)
Sustainable by design

The weekend auto-grace and monthly grace days ensure that taking time off doesn’t feel punishing. The system celebrates consistency without demanding it — a broken streak is just a number, not a loss.

Configuration

All gamification settings live in .vibecrew/config.json:

"gamification": {
  "enabled": true,            // Master toggle
  "streak_reminders": false,  // Opt-in daily reminders
  "quiz_frequency": "weekly", // How often quizzes are suggested
  "show_xp_in_status": true   // Show XP in /status output
}

Set "enabled": false to suppress all gamification output. The Vibe Score and Performance Coach continue to operate independently.

Team features (optional, non-competitive)

  • Aggregated team stats (average score trend, total features shipped)
  • Team badges for collective achievements (“Team ships 10 features”)
  • No individual rankings or comparisons — the system is collaborative, not competitive
Best Practices

Maximizing Efficiency

VibeCrew is designed to make each session more efficient than the last. Here's how to get the most out of the system and why each practice matters.

Context Window Discipline

VibeCrew targets <50% context usage per session. Three mechanisms enforce this automatically:

60%

Warning at 60%

check-context.sh emits a warning. Start thinking about wrapping up. Commit working code.

80%

Critical at 80%

Stronger warning. Commit and run /wrap. Consider delegating remaining work to a sub-agent.

90%

Danger at 90%

Agent quality severely degraded. Immediately run /wrap. Do not attempt complex operations.

When context compaction occurs, compact-reinject.sh automatically re-injects the current project state, active feature, and phase — so you don’t lose context on what you were working on.

Token Efficiency

Use Context7 for everything

This is consistently the single biggest token saver. Every time you paste documentation into chat, you burn ~1,500 tokens that Context7 could fetch on-demand. The Performance Coach will flag this — listen to it.

Write clear initial prompts

Prompt churn (-5 points each) comes from vague instructions. Spend 30 seconds writing a precise prompt instead of 3 follow-up corrections. The first prompt is the cheapest prompt.

Respect context warnings

At 60%: start thinking about wrapping. At 80%: definitely wrap. Pushing to 100% forces a /clear and loses all accumulated understanding. A fresh context + CLAUDE.md = fast restart.

Let agents run in isolation

Stack Scout, Builder, and Code Simplifier run in separate worktree context windows. Don’t duplicate their work in the main session. Their research tokens never touch your context.

Workflow Efficiency

Always /wrap

Never close the terminal without wrapping. The session log feeds the learning system, the commit preserves your work, and the Vibe Score identifies improvements. Skipping /wrap means the session is invisible.

Use /idea aggressively

Mid-feature inspiration should be captured, not pursued. /idea takes 1 second and produces 1 line of output. The idea is safe in the backlog. Your flow is preserved.

Trust the phase gate

It feels restrictive at first. But the 15–30 minutes spent on the foundation prevents hours of rework from wrong architectural assumptions. Every seasoned VibeCrew user says the same thing: "I'm glad it forced me to plan."

Review CLAUDE.md monthly

Remove stale rules, consolidate duplicates, promote critical rules to the top. The Performance Coach adds rules — you curate them. A well-maintained CLAUDE.md is the most powerful file in your project.

For Teams

  • One person owns the foundation. The project lead runs /new-project and establishes the TDR. Don't debate architecture in separate sessions.
  • Share the backlog. Use /plan-features as a team exercise. Commit backlog.json so everyone works from the same list.
  • Commit Vibe Scores. Make scores visible to the team — not as competition, but as a shared learning signal for retrospectives.
  • Standardize on Warp. The deep-link notifications are worth it when running parallel sessions across a team.
  • Do score retros. Even 15 minutes every two weeks reviewing score trends and adding team rules to CLAUDE.md compounds into massive efficiency gains.
Help

Troubleshooting

Common issues related to advanced workflows, gamification, and efficiency features.

Vibe Score seems inaccurate

  • New projects: Scores are less meaningful in the first few sessions as the system establishes baselines
  • Complex features: Large features naturally have more tool calls and corrections — the score accounts for this but may seem low
  • Override deductions: If the coach flags something unavoidable, say so during the coaching dialogue — it factors into the next proposal

/heal can't fetch CI logs

  1. Verify GitHub CLI is authenticated: gh auth status
  2. Ensure the repo has a remote: git remote -v
  3. Check that a recent CI run exists: gh run list --limit 5
  4. If the failure is on a different branch, switch to it first

/simplify shows no suggestions

  • The agent only analyzes files changed on the current feature branch vs. the default branch
  • Verify you're on a feature branch (not main/master): git branch --show-current
  • Check that source files were changed (config and docs are excluded)
  • The minimum files threshold is configurable in .vibecrew/config.json under simplify.min_files_for_analysis

/replay can't find eligible sessions

  • Only sessions with a Vibe Score ≥ 70 are eligible for template extraction
  • Verify session logs exist in .vibecrew/sessions/ and score files in .vibecrew/scores/
  • Run /wrap at the end of sessions to generate the required data

Gamification not showing after /wrap

  1. Check that gamification is enabled: jq '.gamification.enabled' .vibecrew/config.json should return true
  2. Verify .vibecrew/gamification.json exists. If not, run /setup to create it
  3. Check that the gamification scripts are executable: ls -la scripts/award-xp.sh
  4. Run a script manually to debug: bash scripts/award-xp.sh — it outputs JSON with the XP breakdown

/quiz shows "Unlocks at Level 3"

  • The /quiz command requires Level 3 (approximately 3–4 completed sessions)
  • Check your level: jq '.level' .vibecrew/gamification.json
  • Keep running /wrap at the end of sessions to earn XP and level up

Streak broke unexpectedly

  • Streaks increment on calendar days where /wrap runs. If you didn’t wrap, the day doesn’t count
  • Weekends never break streaks. Check if you missed a weekday
  • Grace days reset on the 1st of each month: jq '.streak.grace_days_remaining' .vibecrew/gamification.json
  • If the streak counter seems wrong, check .streak.last_session_date in gamification.json

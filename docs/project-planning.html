Project Planning

Before VibeCrew writes a single line of source code, it builds a foundation: a shared understanding of what you're building, who it's for, how it should look, and which technologies to use. This page explains how to make the most of that process.

What Happens in Tier 1

When you run /new-project, VibeCrew walks you through creating 6 artifacts in order. Each one builds on the previous. No source code writes are allowed until all 6 are complete — this is enforced by the phase-gate hook, not by suggestion.

1

VISION.md

Problem, personas, core features, success metrics, constraints. This is the single most important artifact — every other decision flows from it.

2

Design System + Brief

Visual tokens (design-system.css) and design rationale (design-brief.md). Created via a design interview or by importing your existing style guide.

3

Technology Decision Record

Framework, database, auth, hosting — every choice documented with trade-offs. The Stack Scout agent researches options; the Opponent Processor stress-tests them.

4

Architecture Diagrams

5 Mermaid diagrams: system topology, entity-relationship, user flows, API sequences, component tree. Generated from your vision and tech stack.

5

Roadmap

Features from your vision, prioritized into MVP (Tier 1), Growth (Tier 2), and Future (Tier 3). Dependencies mapped between features.

6

CLAUDE.md

Project conventions synthesized from all prior artifacts. Under 200 lines — every line earns its token cost.

You can skip artifacts

Each artifact can be marked "skipped" if you want to move fast. But the more you skip, the less context VibeCrew's agents have when building features later. The vision and design system have the highest impact.

Writing a Great Vision

VibeCrew asks you 6 questions to generate VISION.md. The quality of your answers directly determines how well every subsequent step works. Here's how to make them count.

Be Specific About the Problem

Weak: "People have trouble managing their time."

Strong: "Freelance designers lose 5+ hours per week switching between invoicing, time-tracking, and project management tools that don't talk to each other."

Specific problems lead to specific features. Vague problems lead to feature creep.

Define Real Personas, Not Demographics

Weak: "Target: 25-40 year old professionals."

Strong: "Freelance designer who juggles 3-5 clients. Pain: enters the same time data into 3 different apps. Goal: one place for time, invoices, and project status."

A persona with a pain point and a goal gives agents enough context to make UI and feature decisions on your behalf.

Name Features as User Actions

Weak: "AI features, analytics dashboard, social integration."

Strong: "Auto-generate invoice from tracked hours. Show weekly earnings trend. Share project status link with client."

Action-oriented features become acceptance criteria. Abstract categories don't.

Make Success Measurable

Weak: "Get lots of users and good retention."

Strong: "70% of users who complete onboarding create their first invoice within 24 hours. 60% weekly retention at month 2."

Measurable goals help the roadmap prioritize: features that move the metrics get built first.

Nail the First Value Action

Weak: "Users sign up and explore the dashboard."

Strong: "Start a timer on their first project and see it reflected on the dashboard within 30 seconds."

This single sentence defines your onboarding flow and what VibeCrew builds first.

State Constraints Up Front

Examples: Mobile-first. Must integrate with Stripe. Offline support required. No vendor lock-in. Budget under $50/month for infrastructure.

Constraints guide the TDR. Without them, the Stack Scout has to guess — and might guess wrong.

Concrete Example: Mealwise

Here's what a well-written VISION.md looks like for a fictional meal-planning app. Notice how every section gives VibeCrew enough detail to make decisions autonomously.

VISION.md — Mealwise (example)# VISION.md — Mealwise

## Problem Statement
Home cooks waste an average of 30% of groceries because they shop without
a plan and forget what's already in their fridge. Existing meal-planning
apps assume users want to follow rigid recipes, ignoring the reality that
most people cook with what they have on hand.

## Target Users

### Persona 1 — Busy Parent (Primary)
- **Role:** Works full-time, cooks dinner most weeknights
- **Pain:** Spends 20 minutes every evening staring at the fridge
- **Goal:** "Tell me what I can make with what I already have"

### Persona 2 — Budget-Conscious Student
- **Role:** Limited kitchen, tight grocery budget
- **Pain:** Buys ingredients for one recipe, the rest goes to waste
- **Goal:** "Use everything I buy before it expires"

## Core Features
1. **Pantry Scanner** — Photograph your fridge/pantry, AI identifies ingredients
2. **Smart Suggestions** — Recipes ranked by how many ingredients you already own
3. **Grocery Optimizer** — Shopping list that fills gaps across multiple meals
4. **Expiry Alerts** — Push notifications before food expires

## Success Metrics
- 50% reduction in reported food waste (user survey, month 3)
- 70% weekly retention after first meal planned
- Average 3 meals planned per week by active users

## First Value Action
Scan their pantry and see the first 3 meal suggestions within 60 seconds.

## Constraints
- Mobile-first (iOS + Android via React Native or PWA)
- Must work offline for pantry scanning (on-device model)
- No subscription required for core features (freemium)

Why This Works

SectionWhat VibeCrew Does With It
Problem StatementFrames the entire product. Agents reference this when evaluating feature priorities and UI decisions.
Persona 1 — Busy ParentDrives the "quick daily check" usage pattern → mobile-first design, fast load times, minimal taps to core action.
Persona 2 — StudentDrives the "budget" angle → grocery optimizer becomes high-priority, premium upsell opportunities identified.
Core Features (4 items)Becomes the initial backlog. Each feature gets a spec during /plan-features. Numbered order hints at priority.
Success MetricsDefines what "done" looks like. The roadmap prioritizes features that move these numbers.
First Value ActionDefines the onboarding flow. The Builder agent builds this first. The E2E test validates it.
ConstraintsThe Stack Scout uses these as hard requirements when evaluating technology options in the TDR.

What Not to Write

Vague inputs produce vague outputs. Here's what to avoid.

Common anti-patterns# Bad examples — too vague for VibeCrew to act on

## ❌ "I want to build an app for food"
  → What about food? Ordering? Cooking? Reviews? Delivery?

## ❌ "Target users: everyone"
  → No one builds for everyone. Who has the sharpest pain?

## ❌ "Features: social features, AI, analytics"
  → These are categories, not features. What does the user DO?

## ❌ "Success: lots of users"
  → How many? Doing what? By when?

Dealing with an Existing Style Guide

Step 2 of the foundation creates your design tokens (design-system.css) and design rationale (design-brief.md). If you already have a style guide, brand kit, or component library, you don't need to go through the full 10-question design interview — VibeCrew can import your existing tokens directly.

The Pre-Design Gate

Before the design interview starts, VibeCrew asks one question: "Do you have an existing design system or style guide you'd like to import?"

No existing system

You go through the full 3-phase interview:

  1. Product & Audience Context (6 questions) — what you're building, who uses it, how it should feel
  2. Visual Direction — choose 1 of 3 generated palettes (Safe, Modern, Signature)
  3. Component Preferences (2-3 questions) — navigation style, data display, interaction density

Takes about 5 minutes. Output: complete design-system.css + design-brief.md.

Importing existing tokens

Point VibeCrew at your source material. Supported formats:

FormatWhat Gets Extracted
CSS fileCustom properties (colors, spacing, typography, radii, shadows)
Tailwind configTheme values: colors, fonts, spacing scale, border-radius
JSON tokensDesign token files (Style Dictionary, Figma Tokens, custom)
URLFetches the page, extracts computed styles and token patterns
Figma fileStyles and variables via Figma MCP server (if connected)
Brand PDFColors, typography, and spacing from brand guidelines

After extraction, VibeCrew shows a gap analysis — which tokens were found and which need defaults. You then answer only the component preference questions (Phase 3: navigation style, data display, interaction density), since those are UX choices your style guide doesn't cover.

Partial style guides are fine

If your brand kit only has colors and a logo, that's enough. VibeCrew imports what it can and fills in the gaps (typography scale, spacing, shadows, etc.) with sensible defaults that match your color palette. The gap analysis shows exactly what was imported vs. generated.

Tips for Importing

CSS files work best. If you have design tokens as CSS custom properties, that's the most direct path. VibeCrew maps them 1:1 without guessing.
Tailwind configs are fully supported. Your tailwind.config.js theme section maps directly to VibeCrew's token structure. Color aliases, custom spacing, and font families are all extracted.
Brand PDFs need clear structure. A well-organized brand guide with labeled color swatches and type specimens works great. A 50-page brand book with mostly photography and marketing copy will produce sparse results — supplement with a CSS file if possible.
URLs extract computed styles. Pointing at a live site works if the site uses consistent CSS custom properties or a recognizable framework. Static marketing pages with inline styles produce mixed results.
Both paths produce identical outputs. Whether you import or go through the interview, you get the same two files: design-system.css (tokens) and design-brief.md (rationale). The Builder agent doesn't know or care which path you took.

Technology Decisions

Step 3 creates the Technology Decision Record (TDR). The Stack Scout agent researches technology options based on your vision and constraints, then documents every choice with trade-offs.

What Gets Decided

The TDR covers every major technical choice: frontend framework, database, ORM, authentication, hosting, styling approach, and testing strategy. For each decision, the document includes at least 2 options considered, pros and cons, and a justified recommendation.

The Opponent Processor

After the TDR is generated, VibeCrew offers to run the Opponent Processor — a devil's advocate agent that stress-tests every decision. It produces a counter-analysis with a 6-criteria debate matrix and alternative recommendations.

This step is optional but recommended, especially for projects where technology choices have long-term consequences (e.g., database selection, auth provider lock-in).

Don't over-engineer the stack

For MVPs, boring technology is good technology. If your constraints don't demand something specific, the Stack Scout will default to well-documented, widely-adopted tools with strong Context7 coverage. That means fewer surprises during feature development.

Prioritizing Your Roadmap

Step 5 takes the features from your vision and asks you to sort them into three tiers.

TierPurposeGuideline
MVP What users need on day one If a user can't get value without it, it's MVP. Keep this list short — 3-5 features is ideal.
Growth What makes users stay and recommend Features that improve retention, enable sharing, or add polish. Build these after launch.
Future Nice-to-have ideas Capture them so they're not forgotten, but don't let them slow down MVP delivery.

Mapping Dependencies

VibeCrew also asks about dependencies between features. If "Grocery Optimizer" needs data from "Pantry Scanner," that dependency is recorded in the roadmap so /run-backlog builds them in the right order.

Resist the urge to put everything in MVP

The most common planning mistake is an overloaded MVP. If your Tier 1 list has more than 5 features, ask yourself: "Could a user get value without this?" If yes, move it to Growth.

EARS Acceptance Criteria

VibeCrew uses the EARS (Easy Approach to Requirements Syntax) format for acceptance criteria. EARS makes every criterion directly testable and eliminates ambiguity.

PatternTemplateExample
Event-drivenWHEN {event} THE SYSTEM SHALL {behavior}When the user clicks Submit, the system shall validate all required fields.
UbiquitousTHE SYSTEM SHALL {behavior}The system shall display timestamps in the user’s local timezone.
State-drivenWHILE {state} THE SYSTEM SHALL {behavior}While unauthenticated, the system shall redirect protected routes to /login.
UnwantedIF {condition} THEN THE SYSTEM SHALL {behavior}If the API returns 429, then the system shall retry with exponential backoff.
OptionalWHERE {condition} THE SYSTEM SHALL {behavior}Where dark mode is enabled, the system shall apply the dark color palette.

The /plan-features command guides users to write criteria in EARS format during interactive planning. validate-plan.sh checks for EARS compliance when validating plans.

Common Mistakes

MistakeWhat HappensHow to Avoid It
Vague vision Agents make assumptions. Features miss the mark. You spend more time course-correcting than building. Spend 10 extra minutes on specific personas and measurable goals. Re-read your vision and ask: "Could someone who isn't me build this from this document?"
Skipping the design system Every feature gets a different visual treatment. Consistency issues compound across sessions. Even 5 minutes in the design interview produces a coherent token set. If you have existing brand colors, import them.
Overloaded MVP /run-backlog takes many sessions. Context quality degrades. Motivation drops. 3-5 MVP features. Everything else goes to Growth or Future. You can always promote later.
Skipping the Opponent Processor Assumptions in the TDR go unchallenged. You discover issues during implementation when they're expensive to fix. Take 2 minutes to review the counter-analysis. You don't have to change anything — just being aware of trade-offs helps.
500-line CLAUDE.md Research shows oversized context files increase agent cost 20%+ without improving success rates. Agents waste tokens parsing rules they don't need. Let VibeCrew generate the CLAUDE.md. It targets under 200 lines. Only add conventions, not documentation.

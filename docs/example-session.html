Getting Oriented

Terminal Setup — How Many Windows?

VibeCrew is designed for parallel work across multiple terminal tabs. The number of tabs depends on your experience level and what you're doing.

Starter layout: 1 tab

If you're new to VibeCrew, start with a single terminal. Run /setup, /new-project, and your first few features sequentially. Learn the rhythm before adding parallelism.

Tab 1 — Main Session
$ claude Session startup agent detects project state... VibeCrew v1.4.0 | Foundation: complete | Feature: user-auth (Code phase) Ready. Type /status for full dashboard.

Recommended layout: 2–3 tabs

Once comfortable, use 2–3 tabs. This is the sweet spot for most developers. One tab builds a feature while another handles planning, research, or a second feature.

Tab 1 — Feature A
Building: user-auth Code phase active Builder agent working...
Tab 2 — Feature B
Building: trip-creation Plan phase active Writing feature spec...
Tab 3 — Quick Tasks
Utility session /idea, /status, /check /heal (if CI fails)
How notifications keep this manageable

You don't need to watch all tabs. The Interrupt Protocol sends a native OS notification when any tab needs you (permission prompt, task complete, or error). Click the notification to jump directly to that tab. Work in your active tab until you're interrupted — that's the whole system.

Power layout: 4+ tabs

Experienced users can run 4 or more tabs. Two feature tabs, one for planning/backlog, and one for auditing or CI healing. Beyond 4, the bottleneck shifts to code review rather than building — you'll have more PRs to review than you can keep up with.

Each tab is an independent Claude Code session

Every tab runs its own context window. They share the filesystem (git branches, .vibecrew/ state, CLAUDE.md) but not conversation history. This is by design — it means research in one tab doesn't consume context in another. But it also means you need to coordinate via branches: each feature gets its own branch.

Example Walkthrough

Day 1: Project Foundation (Tier 1)

Let's build a travel planning SaaS called TripFlow. Day 1 is entirely Tier 1 — no source code, only architecture. This takes one session, typically 20–40 minutes.

The session

Open a single terminal tab.

You describe TripFlow: a collaborative trip planner for groups. Target users are friend groups planning vacations. Key constraint: mobile-first. VibeCrew produces VISION.md.

You pick a warm blue primary color, Inter font, 8px radius. The UI Designer agent generates 80+ CSS custom properties: colors, typography, spacing, shadows, breakpoints.

The Stack Scout agent launches in a separate context window. It researches Next.js vs. Remix vs. SvelteKit, compares auth solutions, evaluates databases. You can work on something else while it runs. It produces docs/tdr-001-tech-stack.md recommending Next.js + Supabase + Tailwind.

~3 min
Step 3.5: Opponent Processor

The Opponent challenges the TDR: "Supabase row-level security has sharp edges with complex group permissions." You review both sides and decide to keep the choices. The counter-analysis is saved for reference.

~5 min
Step 4: Roadmap

You list features: user auth, trip creation, itinerary builder, group invites, expense splitting. VibeCrew organizes them into priority tiers in docs/roadmap.md.

~2 min
Step 5: CLAUDE.md

VibeCrew synthesizes everything: tech stack rules, design system reference, file conventions, testing strategy. The master rules file is ready.

~1 min
Step 6: Git commit

git commit -m "plan: project foundation" — Phase gate unlocks. Source code writes are now allowed.

Tab 1> /wrap
Vibe Score: 95/100
Session logged. Foundation complete. You can now run /plan-features or /new-feature.
Why this matters

Every session after this starts with Claude reading CLAUDE.md. It knows your stack is Next.js + Supabase + Tailwind. It knows your design tokens. It knows your file conventions. You never explain these again. The 30 minutes you spent on the foundation saves hours of corrections across every future session.

Planning

Day 2: Planning Session

Before building features, invest one session in creating structured specifications. This session is short (15–20 min) and pays for itself immediately.

Tab 1$ claude
VibeCrew v1.4.0 | Foundation: complete | No active feature
Ready. 5 features in roadmap, 0 planned.

> /plan-features

VibeCrew reads your roadmap and walks through each feature. For each one, you provide or confirm:

  • Name and description — one sentence
  • Acceptance criteria — when is this feature "done"?
  • Priority — P0 (must have) through P3 (nice to have)
  • Complexity — S / M / L / XL
  • Dependencies — which features must exist first?

The output is .vibecrew/backlog.json — a structured file that /new-feature and /run-backlog read to determine what to build next.

Advanced

Day 4: Building Multiple Features in Parallel

Once you've shipped a couple of features sequentially and feel comfortable with the rhythm, try parallel execution. This is where VibeCrew's multi-session design really shines.

The setup: 3 tabs

1

Tab 1: Trip Creation

Your primary focus. You're actively guiding this feature through the 6 phases, making decisions, reviewing output.

2

Tab 2: Itinerary Builder

Running more autonomously. You started /new-feature "itinerary-builder" and let the agents work. You check in when notifications fire.

3

Tab 3: Utility

Quick commands: /idea to capture thoughts, /status to check progress, /check to run quality gates, /heal if CI breaks.

How a parallel session flows

9:00 Open Tab 1. /new-feature "trip-creation" Open Tab 2. /new-feature "itinerary-builder" 9:05 Tab 1: You guide the Plan phase for trip-creation. Tab 2: Agent writes the feature spec autonomously. 9:10 Notification: "Tab 2 — Plan phase complete. Ready for review." You glance at the spec, approve it. Tab 2 moves to UI Design. 9:12 Tab 1: You finish the plan, start UI Design. Tab 2: Agent designs components autonomously. 9:20 Notification: "Tab 2 — needs permission to create files." Click notification. Approve file creation. Tab 2 continues. 9:25 Tab 1: Code phase starts. Builder agent working. You switch to Tab 3: /status Dashboard: trip-creation (Code), itinerary-builder (Code) 9:30 Notification: "Tab 1 — Code phase complete." You review the code, start the Test phase. 9:35 While Tab 1 runs tests, you capture an idea: Tab 3: /idea "add map view to itinerary with Mapbox" 9:45 Tab 1: All phases done. /wrap → Score 88 Tab 2: Still in Test phase. 9:50 Notification: "Tab 2 — Tests complete. Docs phase done." Switch to Tab 2. /wrap → Score 85 9:55 Two features shipped in under an hour. Tab 3: /status Dashboard: 4/5 features done, 1 remaining.
Can I run /run-backlog across multiple tabs?

Yes, but carefully. /run-backlog picks the next planned feature from the backlog automatically. If you run it in two tabs simultaneously, they'll pick different features (the backlog is file-locked to prevent duplicates). This is the fastest way to burn through a backlog, but each tab's work should be reviewed when it completes.

When to build in parallel vs. sequentially

Build in parallel when:

Features are independent (no shared components), you're comfortable with the workflow, and you can context-switch without confusion. Best for: CRUD features, isolated pages, utility features.

Build sequentially when:

Feature B depends on Feature A's code, you're working on core shared infrastructure (auth, database schema, API layer), or you're learning VibeCrew. Merge conflicts from parallel branches cost more time than they save.

Running Dev & Test Servers

While VibeCrew builds your code, you'll want to see it running in the browser. Here's how to set up a dedicated tab for your dev server and run tests against it.

Dedicated dev server tab

Keep one terminal tab exclusively for your development server. This tab runs outside Claude Code — it's just a normal shell running your framework's dev command.

Tab — Dev Server
$ npm run dev ▲ Next.js 15.1.0 - Local: http://localhost:3000 - Network: http://192.168.1.42:3000 ✓ Ready in 1.2s
Tab — VibeCrew Session
$ claude VibeCrew v1.4.0 | Feature: user-auth (Code phase) > "Implement the login page" Builder agent working... Creating src/app/(auth)/login/page.tsx # Hot-reload updates your browser automatically
Hot reload is your friend

Next.js, Vite, and most modern frameworks hot-reload when files change. As VibeCrew writes code in one tab, your browser updates in real time. Keep your browser and dev server tab visible alongside your Claude Code tab to watch the UI take shape as it's built.

Running tests during development

VibeCrew runs tests automatically during the Test phase and when you use /check or /wrap. But you can also run a test watcher in a separate tab for continuous feedback.

Tab — Dev Server
▲ Next.js 15.1.0 - Local: http://localhost:3000 ✓ Ready
Tab — Test Watcher
$ npm run test:watch PASS src/__tests__/auth/login.test.tsx PASS src/__tests__/auth/signup.test.tsx Tests: 12 passed, 12 total Watching for changes...
Tab — VibeCrew Session
Building: user-auth Code phase active Builder agent working... # Tests re-run as files change

Common dev server commands by framework

Reference# Next.js

# Vite (React, Vue, Svelte)

# Supabase (local development)

Workflow Tip

Capturing Ideas for the Backlog

Ideas come at the worst times — mid-implementation, during testing, while reviewing code. VibeCrew gives you two tools to capture without losing flow.

/idea — instant capture

The fastest way. One line in, one line out. Zero context consumed. Use it anytime, in any tab.

any tab> /idea "add dark mode toggle to settings page"
Added to backlog: "add dark mode toggle to settings page" (unplanned)

> /idea "export trip itinerary as PDF"
Added to backlog: "export trip itinerary as PDF" (unplanned)

> /idea "rate limiting on auth endpoints"
Added to backlog: "rate limiting on auth endpoints" (unplanned)

Ideas land in .vibecrew/backlog.json with status "unplanned". They sit there until your next planning session.

/plan-features — structured planning

When you've accumulated several ideas, run /plan-features to promote them to structured specs with acceptance criteria, priority, and complexity. This is best done in a dedicated planning session (see Day 2 above).

The capture habit

✓

Do this

See something? /idea "short description" immediately. Don't stop to elaborate. Don't open the backlog file. Don't discuss it with the agent. Capture and continue.

✗

Don't do this

"Actually, let me also build dark mode real quick." Mid-feature diversions wreck your Vibe Score (prompt churn, context waste) and leave you with two half-finished features instead of one shipped one.

Habits

Best Practices & Guardrails

VibeCrew enforces many rules automatically through hooks, but some habits need to be built by you. These tips prevent the most common mistakes that cost time, tokens, and Vibe Score points.

Never close a tab without wrapping

Closing a terminal kills the Claude Code session instantly — there's no chance to run /wrap. You lose the Performance Coach analysis, Vibe Score, session log, and any uncommitted work. Set up guardrails to prevent this.

Option 1: Warp close confirmation

Warp Terminal can warn you before closing a tab that has a running process. Go to Settings → Features → "Warn before closing a tab with a running process" and enable it. You'll get a confirmation dialog every time you try to close a tab with Claude Code running.

Option 2: Shell exit reminder

Add a trap to your shell config that fires when the terminal is about to close:

.zshrc# Remind to /wrap before closing
vibecrew_exit_check() {
  if [ -f ".vibecrew/state.json" ]; then
    echo ""
    echo "Warning: Did you /wrap your VibeCrew session?"
    echo "Run /wrap to save your Vibe Score and session log."
    echo ""
  fi
}
trap vibecrew_exit_check EXIT

Option 3: Lightweight Stop hook (automatic)

Extend the existing Stop hook to run a basic quality gate and save what it can. This runs automatically when Claude Code exits — even if you forget.

scripts/auto-wrap-lite.sh#!/bin/bash
# Runs on session Stop event — lightweight /wrap fallback
# Cannot run agent tasks (Performance Coach, Vibe Score)
# but captures the basics.

SESSION_ID=$(date +%Y%m%d-%H%M%S)
LOG_DIR=".vibecrew/sessions"
mkdir -p "$LOG_DIR"

# Save basic session metadata
echo "{
  \"id\": \"$SESSION_ID\",
  \"type\": \"auto-wrap-lite\",
  \"timestamp\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\",
  \"branch\": \"$(git branch --show-current 2>/dev/null)\",
  \"uncommitted_files\": $(git status --porcelain 2>/dev/null | wc -l | tr -d ' '),
  \"note\": \"Session ended without /wrap\"
}" > "$LOG_DIR/$SESSION_ID.json"

# Warn if there are uncommitted changes
DIRTY=$(git status --porcelain 2>/dev/null | wc -l | tr -d ' ')
if [ "$DIRTY" -gt 0 ]; then
  echo "auto-wrap-lite: $DIRTY uncommitted files on $(git branch --show-current)"
fi
Use all three together

These aren't mutually exclusive. Warp's confirmation is your first line of defense, the shell trap is a visual reminder if you bypass it, and the Stop hook is the automatic fallback that always runs. Layer them for maximum safety.

Detect unwrapped sessions on startup

The Session Startup agent already checks project state when you run claude. It can also detect if the last session ended without /wrap by checking the session logs. If it finds an unwrapped session, it warns you and offers to run a retroactive analysis.

What you'll see$ claude
Warning: Previous session (2026-02-24 14:32) ended without /wrap.
  Branch: feat/trip-creation
  Uncommitted files: 4
  Session log: partial (auto-wrap-lite)
Recommendation: Review uncommitted changes, then continue or /wrap.
VibeCrew v1.4.0 | Feature: trip-creation (Code phase)
This is automatic

You don't need to configure anything. The Session Startup agent reads .vibecrew/sessions/ on every launch and flags incomplete sessions. It's one of the reasons every session should start with claude (not by resuming a detached process).

Never build features on main

VibeCrew creates a feature branch automatically when you run /new-feature. But if you skip that and start coding directly, you might be on main. The phase gate hook can catch this.

What happens if you try> "Add a login form to the homepage"

Phase gate blocked: You're on the 'main' branch.
Source code writes are only allowed on feature branches (feat/*).
Run /new-feature "feature-name" to create a branch and start building.
Why this matters

Building on main means no PR, no code review, no isolation from other work. If something goes wrong, you can't just delete the branch — you have to revert commits on main. The branch guard prevents this entire class of mistakes.

Handle uncommitted changes before starting

Starting a new feature with uncommitted changes from a previous feature is a recipe for tangled commits and merge conflicts. The Session Startup agent checks for this.

What you'll see$ claude
Warning: 7 uncommitted files detected on feat/user-auth.
  Modified: src/components/auth/LoginForm.tsx
  Modified: src/lib/supabase/client.ts
  ... and 5 more
Options:
  1. Continue working on feat/user-auth
  2. Commit changes and start a new feature
  3. Stash changes and start fresh

Review PRs before building more features

It's tempting to keep shipping features, but unreviewed PRs pile up fast — especially in parallel mode. Stale PRs lead to merge conflicts and integration bugs. Build a cadence: review first, then build.

✓

Good cadence

Morning: review and merge yesterday's PRs. Then start new features. Use /status to see open PRs. Keep the PR queue under 3 at all times.

✗

Danger zone

5+ unmerged PRs across different feature branches. Each new feature increases the chance of conflicts. Merging becomes a full-day task instead of 10 minutes per PR.

Quick PR check> /status

Open PRs:
  #12 feat/user-auth        — approved, ready to merge
  #13 feat/trip-creation    — review requested, 2 days old
  #14 feat/itinerary-builder — draft, tests passing

Recommendation: Merge #12, review #13 before starting new work.

One feature per session, no exceptions

This is the single most impactful habit. Each Claude Code session has a finite context window. Cramming two features into one session means both get less attention, more token waste, and lower Vibe Scores.

✓

Do this

/new-feature "user-auth" → build all 6 phases → /wrap → close session. New session: /new-feature "trip-creation". Clean context, clean branch, clean score.

✗

Don't do this

"While I'm here, let me also start trip-creation." Mid-session feature switches waste context recapping the new feature, leave the first feature half-wrapped, and confuse the Performance Coach analysis.

Watch your context budget

The check-context.sh Stop hook warns at 60% and 80% context usage, but don't wait for the warning. Check proactively with /status, especially during long Code phases.

Context warnings> /status

Context usage: 62% (warning threshold: 60%)
Estimated remaining: ~15 tool calls
Recommendation: Finish current phase, then /wrap.
  Don't start a new phase in this session.
What happens at high context usage

Above 70%, Claude Code starts losing early conversation context. It may forget your design decisions, repeat questions, or generate code that contradicts earlier choices. Above 85%, quality degrades significantly. The rule: if you're past 60%, wrap up and start fresh. A new session with full context is always better than pushing a depleted one.

Weekly planning ritual

Every week, ideas accumulate in your backlog via /idea. If you don't process them, the backlog becomes a graveyard of forgotten thoughts. Set a recurring ritual.

Every Friday (or Monday morning): 1. Run /status to see the full picture 2. Run /plan-features to promote unplanned ideas to specs 3. Review Vibe Score trends — are scores going up or down? 4. Review CLAUDE.md rules added by Performance Coach 5. Merge any remaining PRs 6. /wrap to close the week Total: ~30 minutes. Sets up the entire next week.

Commit at every phase boundary

Don't wait until /wrap to commit. Each phase completion (Plan, UI Design, Code, Test, Docs) is a natural commit point. If something goes wrong in a later phase, you can roll back to the last clean phase instead of losing everything.

Natural commit points[x] Plan        → commit: "plan(auth): feature spec and acceptance criteria"
[x] UI Design   → commit: "design(auth): component wireframes and token usage"
[x] Code        → commit: "feat(auth): implement login, signup, and middleware"
[x] Test        → commit: "test(auth): 12 tests covering auth flows"
[x] Docs        → commit: "docs(auth): changelog and feature documentation"
VibeCrew handles this automatically

The Builder and Verifier agents commit at phase boundaries by default. But if you're guiding the session manually (typing prompts instead of letting agents drive), remember to commit after each phase. The phase-gate hook tracks which phases are complete, so commits also serve as progress checkpoints.

Commit your .vibecrew/ folder

The .vibecrew/ folder contains your project state: backlog, session logs, scores, and config. If you lose it, you lose your history. Commit it to your repo so it's backed up and shared with teammates.

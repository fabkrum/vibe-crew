Architecture

System Deep Dive

VibeCrew is a system of specialized agents, deterministic hooks, and bash scripts that work together to enforce quality, manage attention, and continuously improve your workflow. Here's how every piece fits together.

New to coding? Start here

This page explains how VibeCrew works under the hood. You don't need to understand all of this to use VibeCrew — just type the slash commands and the system handles the rest. But if you're curious about what's happening behind the scenes, or want to troubleshoot an issue, this page has the answers. Each section starts with a plain-English explanation before diving into technical details.

Plugin Manifest & Registration

What is a plugin?

A plugin is an add-on that gives Claude Code new abilities. Think of it like installing an app on your phone — your phone works fine without it, but the app adds features. VibeCrew is a plugin that adds project management, quality enforcement, and specialized AI agents to Claude Code. When you open a project with VibeCrew installed, Claude Code reads a small configuration file and automatically loads all the extra features.

VibeCrew is a Claude Code plugin. Claude Code auto-detects it from the .claude-plugin/plugin.json manifest in the project root. The manifest registers all system components:

plugin.json{
  "name": "vibe-crew",
  "version": "1.3.0",
  "description": "Autonomous vibe-coding operating system",
  "agents": "./agents/",
  "skills": "./skills/",
  "hooks": "./hooks/hooks.json",
  "mcpServers": "./.mcp.json"
}
■

agents/

12 specialized agent prompt files. Each defines a model, isolation type, tool allowlist, and turn budget. Claude Code spawns them on demand.

▶

skills/

20 slash command definitions. Each is a SKILL.md file with YAML frontmatter that registers the command name, description, and arguments.

⚙

hooks/

Event-to-script routing table. 10 hook matchers across 6 lifecycle events, triggering bash scripts for zero-token enforcement.

◉

.mcp.json

MCP server configuration for Context7 (documentation lookup) and Puppeteer (browser automation).

The 12-Agent Architecture

What are agents?

Think of agents as specialist team members, each with a specific job. Instead of one AI doing everything, VibeCrew splits work across 12 agents — just like a real development team has designers, builders, testers, and reviewers. Each agent is an AI "personality" optimized for one task. The Builder writes code. The Verifier runs tests. The Security Auditor checks for vulnerabilities. You never interact with agents directly — VibeCrew picks the right one for each job automatically.

Inline vs. Worktree: Some agents work directly in your project folder ("inline") — like a colleague sitting at your desk. Others work in a worktree, which is an isolated copy of your project files. Think of it as giving that specialist their own private office with a photocopy of all your documents. They can read, analyze, and write without affecting your real files. When they're done, only the finished result comes back to you. This isolation also saves your AI "memory" (context window) — all of their research stays in their office, not yours.

Each agent has a specific role, model selection, tool access, and context budget. Opus agents handle planning, research, code, security, and analysis — tasks where mistakes are expensive to fix later. Haiku agents handle fast, mechanical tasks (routing, running shell commands). Sonnet handles template-driven output like documentation.

Why isolated agents matter

Agents marked "Worktree" run in separate context windows. All their research tokens, documentation fetches, and analysis stay outside your main session. Only the distilled output enters your primary context — saving thousands of tokens per session.

Skills System (Slash Commands)

What are slash commands?

Slash commands are the buttons you press to make VibeCrew do things. You type a command starting with / (like /new-project or /wrap) and VibeCrew handles the rest. Each command triggers a specific workflow — some are simple (like /idea which just saves a note) and some are complex (like /new-project which orchestrates multiple agents over 6 steps). You don't need to know how they work internally, just what they do and when to use them.

Every slash command in VibeCrew is implemented as a skill — a SKILL.md file in the skills/ directory. Skills are the primary user-facing interface to the system.

How skills work

User types: /new-feature "user-auth" ↓ Claude Code discovers skills/new-feature/SKILL.md ↓ Reads YAML frontmatter: name: new-feature description: Start a new feature args: feature_name ↓ Expands SKILL.md body as agent instructions ↓ Skill executes: precondition checks, state mutations, agent handoffs ↓ Results written to .vibecrew/ state files

Skill definition format

Each skill is a Markdown file with YAML frontmatter. The body contains the full workflow: preconditions, step-by-step execution, error handling, state mutations, and agent handoffs.

skills/new-feature/SKILL.md---
name: new-feature
description: Start a new feature session on a dedicated branch
args: feature_name
---

# /new-feature workflow

1. Check foundation is complete (read state.json)
2. Check WIP limits (max 2 in-progress features)
3. Find or create feature in backlog.json
4. Create git branch: feat/{feature_name}
5. Create safety checkpoint
6. Initialize 5-phase tracking in state.json
7. Hand off to Builder agent

Script-only skills vs. agent-driven skills

Some skills (like /idea, /status, /cost) are pure script execution — they read/write JSON files and produce output with zero AI token cost. Others (like /new-project, /wrap) orchestrate multiple agents across the full workflow. The distinction keeps costs down: cheap operations stay cheap.

The Hook System

What are hooks?

Hooks are automatic safety checks that run behind the scenes. Imagine a building with security guards at every door — when someone (an AI agent) tries to walk through (write a file, run a command), the guard (hook) checks if they're allowed. If yes, they pass through. If no, they're blocked with a clear message explaining why. Hooks are small programs that run instantly and cost nothing — they don't use any AI processing power. They're the reason VibeCrew can enforce rules like "no source code before the foundation is complete" without you having to remember or check yourself.

Hooks are the enforcement layer. They run as bash scripts triggered by Claude Code lifecycle events. Because they're shell scripts, they consume zero AI context tokens — the most efficient enforcement mechanism possible.

Hook EventScript(s)When It FiresWhat It Does
SessionStart session-startup.sh, sync-state.sh, error-recovery.sh Every Claude Code start Environment check, state reconciliation, clear stale locks
SessionStart (compact) compact-reinject.sh After context compaction Re-injects project state after context compaction
PreToolUse (Write/Edit) phase-gate.sh, restrict-paths.sh Before any file write Blocks source writes before foundation; validates write targets
PreToolUse (Bash) protect-data.sh Before any shell command Blocks destructive operations (rm -rf, DROP TABLE, force push)
PostToolUse (Write/Edit) format-code.sh After every file write Auto-formats with Prettier, Black, rustfmt, gofmt
Notification notify.sh Permission blocked or task complete Sends native OS notification with Warp deep-link
PostToolUseFailure notify.sh error Any tool execution fails Sends error notification
Stop check-context.sh, cost-guardrails.sh, claude-md-lint.sh Session ending Context warnings, cost threshold checks, CLAUDE.md validation

How hooks enforce behavior

When Claude Code encounters a lifecycle event, it checks hooks.json for matching entries, passes a JSON payload to the script via stdin, and reads the exit code. Exit 0 = allow the operation. Exit 2 = block the operation. This gives hooks the power to both observe (PostToolUse) and control (PreToolUse) agent behavior.

Scripts Reference

What are scripts?

Scripts are the worker bees of VibeCrew. While agents think and make decisions, scripts do the actual mechanical work: creating files, updating project state, calculating scores, sending notifications. They're small programs that run in milliseconds and always produce the same result for the same input. This makes VibeCrew predictable and reliable — the creative AI work is separated from the bookkeeping, so nothing gets lost or corrupted.

VibeCrew includes 60+ bash scripts in the scripts/ directory. Every state mutation goes through a script — agents never write .vibecrew/ files directly. Scripts are organized by function:

Settings & Permissions

What are permissions?

Permissions control what the AI is and isn't allowed to do on your computer. VibeCrew pre-configures a list of safe operations (reading files, running tests, creating branches) and explicitly blocks dangerous ones (deleting everything, overwriting important data, installing system-wide software). This means the AI can work productively without asking you for permission every 5 seconds, while being physically unable to do anything destructive. It's like giving a contractor a key to the workshop but not the safe.

The settings.json file defines tool-level permission rules enforced by Claude Code before any hook runs. This is the outermost security boundary.

Allowed tools (66 rules)

Standard development operations are pre-approved so the agent can work without constant permission prompts:

  • File operations — All Read, Write, Edit, Glob, Grep
  • npm scripts — test, lint, build, format, type-check, audit
  • Git operations — status, log, diff, add, commit, checkout, branch, worktree, revert, reset --soft, tags
  • GitHub CLI — pr create/list/view, run list/view/watch
  • Shell utilities — jq, cat, ls, wc, sort, head, tail, mkdir, cp, mv
  • Security audits — npm audit, pip audit, bundle audit, govulncheck, cargo audit, composer audit

Denied tools (22 rules)

Destructive operations are blocked at the permission layer — even if an agent tries to run them:

⚠

Elevation

sudo, su, doas, pkexec

⚠

Force operations

git push --force, git push -f, git reset --hard, git clean -f

⚠

Destructive

rm -rf /, rm -rf ~, rm -rf $HOME, chmod 777

⚠

System modifications

npm install -g, kill -9, systemctl, crontab, mkfs, dd

Two layers of protection

The settings.json permission rules are the first layer (enforced by Claude Code). The protect-data.sh PreToolUse hook is the second layer (catches patterns like DROP TABLE that aren't tool-level commands). Together they form a defense-in-depth system.

MCP Server Integration

What are MCP servers?

MCP servers are external tools that give the AI extra abilities. Normally, the AI can only read your files and run commands. MCP servers connect it to additional services — like a reference library (Context7, for looking up documentation) or a web browser (Puppeteer, for visiting websites). They're optional: VibeCrew works fine without them, but with them, the AI works faster and uses less of its "memory" because it can look things up on demand instead of trying to remember everything.

Two MCP (Model Context Protocol) servers extend the agent's capabilities. Both are optional but strongly recommended for token efficiency.

◉

Context7

Documentation lookup. Instead of pasting library docs into chat (~1,500 tokens per paste), agents query Context7 for on-demand API references. Used by the Builder (implementation), Stack Scout (research), and Verifier (testing).

◉

Puppeteer

Browser automation. The Stack Scout uses it for web research and screenshot verification during TDR creation. Also available for visual regression testing during the Test phase.

.mcp.json{
  "mcpServers": {
    "context7": {
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp@latest"]
    },
    "puppeteer": {
      "command": "npx",
      "args": ["-y", "@anthropic/puppeteer-mcp@latest"]
    }
  }
}
Token savings from Context7

A single session might query Supabase auth docs, Next.js routing docs, and Tailwind utility references. Without Context7, that's ~4,500 tokens of pasted documentation. With Context7, the agent fetches exactly what it needs on demand — and those tokens are served from the MCP server, not your context window. The Performance Coach tracks this and deducts points (-15) for low cache utilization when Context7 isn't being used.

Runtime

Runtime Systems

These systems operate during sessions to manage context, attention, quality, cost, and cross-session continuity.

What are runtime systems?

Runtime systems are things that happen while you're working, in the background. You don't trigger them manually — they just run. The status bar updates automatically. Notifications fire when the AI needs you. The phase gate silently blocks mistakes. Cost tracking accumulates as you go. Think of them as the dashboard, warning lights, and autopilot in a car: you don't have to think about them, but they're always keeping you informed and safe.

The Status Bar

What is the status bar?

The status bar is a thin line of information at the bottom of your terminal that tells you what's happening at a glance — like the dashboard in a car showing speed, fuel, and engine status. It shows how much AI "memory" you've used, how much the session costs so far, which feature you're building, your quality score, and how long you've been working. It updates automatically after every AI response and costs nothing extra.

A persistent status line renders after every assistant message, showing six data segments at zero token cost. The script (scripts/statusline.sh) is configured via settings.json and runs as a shell command outside the AI context window.

The Interrupt Protocol

What is the Interrupt Protocol?

The Interrupt Protocol is VibeCrew's "don't bother me unless it's important" system. When you have multiple terminal tabs running, you don't want constant notifications from all of them. VibeCrew stays completely silent while things are going well. It only pings you in three situations: (1) the AI needs your permission to do something, (2) a task finished and it's waiting for your next instruction, or (3) something broke. This lets you focus on one task and trust that you'll be pulled in only when truly needed.

The Interrupt Protocol is the "Attention Economy" architecture. The terminal stays completely silent during normal operation. Notifications fire only on three conditions:

!

Permission Stalls

permission_prompt — The agent needs Y/N approval. Execution is halted. Priority: Critical.

✔

Task Completion

idle_prompt — A complex operation finished. The agent is waiting for your next instruction. Priority: High.

⚠

Critical Failures

PostToolUseFailure — A tool returned a fatal exit code or compilation error that can't be resolved autonomously. Priority: High.

Everything else — standard tool execution, file reads, successful commands — is silent. Your Deep Work state is preserved.

The Phase Gate

What is the phase gate?

The phase gate is a guardrail that prevents you from writing code too early. Before any code can be written, VibeCrew requires you to complete the project foundation: define your vision, choose your technology, plan your design system, and set up the rules. This sounds strict, but it's the most important time-saver in the entire system. Without it, the AI might start writing code using the wrong tools, wrong design, or wrong approach — and you'd waste hours fixing that. The phase gate checks automatically on every file write, so you can't accidentally skip it.

The phase gate is the architectural enforcement mechanism. It runs as a PreToolUse hook on every Write and Edit operation.

phase-gate.sh receives JSON payload from Claude Code ↓ Reads .vibecrew/state.json → checks project_foundation.status ↓ If "complete": exit 0 (allow all writes) If "incomplete": ↓ Check file path being written: .vibecrew/, CLAUDE.md, VISION.md, docs/, design-system.css → exit 0 (foundation artifacts allowed) src/, app/, lib/, components/, etc. → exit 2 (BLOCKED)

When blocked, the developer sees a clear message listing which foundation steps remain incomplete and how to complete them.

The Vibe Score & Performance Coach

What is the Vibe Score?

The Vibe Score is your session quality rating, from 0 to 100. Think of it like a fitness tracker for your coding sessions. At the end of each session, VibeCrew reviews how things went: Did you plan before coding? Did you write tests? Did you waste time going back and forth? A high score (90+) means the session was efficient and well-structured. A low score means there's room to improve. The Performance Coach then gives you a tip and suggests a new rule that will prevent the same issue next session. Over time, these rules accumulate and your sessions get more efficient automatically — the system literally learns from your habits.

The Performance Coach runs at the end of every session (triggered by /wrap). It ingests the session transcript, calculates a Vibe Score, and initiates an interactive coaching dialogue.

How the score is calculated

Starting from 100, deductions are applied for detected anti-patterns:

Anti-PatternDeductionHow It's Detected
Prompt churn -5 per sequence 3+ consecutive corrective messages without a successful tool call
Tool loops -10 per loop Same tool call with identical arguments repeated 3+ times
Low cache utilization -15 cache_read_input_tokens < 20% of total input_tokens
Context violation -20 Significant work continued after the 80% context warning
No tests written -10 Feature has coding artifacts but no test artifacts
No feature spec -5 Coding started without a plan artifact

Bonuses (up to +10): +5 for all 5 phases having artifacts, +5 for cache utilization above 50%.

Score RangeRatingMeaning
90–100ExcellentEfficient, well-structured session
75–89GoodMinor inefficiencies
60–74Needs ImprovementNotable token waste

The coaching dialogue

After calculating the score, the Performance Coach:

  1. Presents the score with the single biggest observation: "Vibe Score: 82/100. You pasted API docs 3 times (~4,500 tokens). Using Context7 MCP would have saved those tokens."
  2. Asks for feedback: "How did this session feel? Any friction points?"
  3. Proposes a CLAUDE.md rule: "Proposed rule: Always use Context7 for Dexie.js API docs. Add this? (y/n)"
  4. Mutates CLAUDE.md if approved — the rule is permanent and active from the next session onwards.
The recursive improvement loop

Session 1: paste docs, score 78, rule added. Session 2: AI reads rule, uses Context7, score 89, new rule proposed. Session 3: two rules active, score 94. Each session is more efficient than the last. Mistakes are identified, codified, and permanently prevented.

Context Compaction & Reinject

What is context compaction?

The AI has a limited "memory" for each conversation (called the context window). As your session gets longer, older messages start taking up too much space. Claude Code handles this by compacting (summarizing) older messages to free up room. The problem is: after compaction, the AI might forget what project you're working on or what feature you were building. VibeCrew solves this by automatically re-injecting a tiny summary (~300 words) of your project state after every compaction. The AI seamlessly continues without asking "wait, what were we doing?" It's like leaving a sticky note on your desk so you remember where you left off after a break.

When the context window approaches capacity, Claude Code compacts older messages. VibeCrew hooks into this event to ensure you never lose track of what you were working on.

Context window reaches ~50% capacity ↓ Claude Code triggers context compaction (older messages compressed) ↓ SessionStart "compact" hook fires ↓ compact-reinject.sh executes (5-second timeout) ↓ Outputs a <300-token summary: • Foundation status (complete/incomplete + missing steps) • Active feature (name, branch, current phase, phases completed) • Backlog summary (by Kanban column) • Recent commits (last 5) • CLAUDE.md summary (line count, section count) ↓ Agent seamlessly continues with full project awareness

This mechanism is why sessions can survive multiple compactions without degradation. The <300-token reinject costs less than a single follow-up clarification question.

The Handoff System

What is a handoff?

A handoff is a briefing document for your next session. Every time you close a session and open a new one, the AI starts with a blank slate — it doesn't remember your previous conversation. The handoff document solves this by writing down everything the next session needs to know: what you were working on, what's done, what's blocked, and what to do next. It's like writing a note to your future self (or a colleague taking over your shift). The next session reads this note and picks up exactly where you left off, without wasting time re-explaining everything.

The /handoff command generates a structured context transfer document designed for the next session. This solves the "cold start" problem where a new session has to re-discover what you were working on.

Handoff document structure

handoff-2026-02-24-001.md# Session Handoff — 2026-02-24

## Active Work
- Feature: user-auth (User Authentication)
- Phase: Test (3/5 phases complete)
- Branch: feat/user-auth

## Recent Progress
- Implemented Supabase auth client
- Created login/signup pages
- Added route middleware

## Blockers
- OAuth callback URL needs env var NEXT_PUBLIC_SUPABASE_URL

## Next Steps
- Write tests for auth middleware
- Add error states to login form
- Complete docs phase

## Decisions Made
- Using Supabase Auth (not NextAuth) per TDR
- Middleware-based route protection (not per-page)

Handoff documents are stored in .vibecrew/handoffs/ and are also generated automatically by /wrap. The Session Startup agent reads the most recent handoff to orient the new session.

Token savings from handoffs

Without a handoff, re-establishing context costs ~2,000 tokens of explanation: "I was working on auth, I'm on the feat/user-auth branch, I finished the code phase, I still need to..." With a handoff, the startup agent reads a structured file and produces a 3-line status banner. The session starts immediately productive.

Error Recovery

What is error recovery?

Sometimes things go wrong: your laptop crashes, you accidentally close a terminal, or the internet drops mid-session. Error recovery is VibeCrew's self-healing system that runs automatically every time you start a new session. It quietly cleans up any mess left behind — removing stale lock files, repairing corrupted data, and flagging unresolved issues. You don't need to do anything; it just works. If it finds something it can't fix automatically (like a merge conflict in your code), it tells you what happened and how to resolve it.

The error-recovery.sh script runs at every session start via the SessionStart hook. It silently cleans up problems left by crashed or interrupted sessions.

🔒

Stale lock cleanup

Removes .vibecrew/locks/*/ directories older than 60 seconds. Prevents deadlocks from crashed multi-agent operations.

📄

Temp file cleanup

Removes temporary files from failed atomic write operations (the .tmp files left behind when mv never executed).

⚙

Git state validation

Checks for unresolved merge conflicts and detached HEAD state. Reports issues but doesn't auto-resolve — those need human judgment.

▶

Orphaned process detection

Lists orphaned agent processes from previous sessions. Reports but doesn't kill — avoids terminating intentional background work.

Cost Guardrails

What are cost guardrails?

Using AI costs money — every message you send and every response you receive has a small price tag based on how much text is processed. Cost guardrails are VibeCrew's spending protection system. They track your costs in real time and warn you when you approach a limit — like a prepaid phone that warns you when your balance is low. You set the limits yourself (e.g., "$5 per session, $20 per day"), and VibeCrew will pause and ask before exceeding them. This prevents surprise bills from long or runaway sessions.

The cost-guardrails.sh script runs on every Stop event. It calculates per-turn costs using model-aware pricing and accumulates totals in .vibecrew/session-cost.json.

How cost tracking works

Stop hook fires after every assistant turn ↓ cost-guardrails.sh reads token counts from hook JSON payload: input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens ↓ Calculates USD cost using per-model pricing (Opus/Sonnet/Haiku) ↓ Accumulates in .vibecrew/session-cost.json ↓ Checks against thresholds: Session warning ($2.00) → emit cost warning Session max ($5.00) → agent MUST pause and ask permission Daily warning ($20.00) → emit daily spend alert

All thresholds are configurable in .vibecrew/config.json under cost_limits. The /cost command reads this data to display the full financial picture.

State Management

What is state management?

State is VibeCrew's memory between sessions. It remembers what features you've planned, which ones are done, your quality scores, session history, and configuration preferences. All of this is stored in a folder called .vibecrew/ inside your project. Unlike the AI's conversation memory (which resets every session), these files persist forever. They're plain JSON files — human-readable text — so you can always open them and see exactly what VibeCrew knows about your project.

State schema migration

When VibeCrew is upgraded, scripts/migrate-state.sh automatically detects the current schema version and applies incremental migrations (1.0.0 → 1.1.0 → 1.2.0 → 1.3.0). New fields are added with sensible defaults. No manual migration is needed.

Philosophy

Design Principles

Every architectural decision in VibeCrew follows these principles. Understanding them explains why the system works the way it does. These aren't just technical choices — they're the philosophy behind VibeCrew. If you ever wonder "why does it work this way?", the answer is usually one of these principles.

■

Fail-open design

All scripts exit 0 on error. A failing hook script never blocks your session — it silently degrades. The system reports the problem but lets you keep working. Sessions are too expensive to block with infrastructure issues.

■

Hooks over suggestions

Rules are enforced via deterministic bash scripts (zero tokens) rather than relying on the model to remember instructions. A hook that exits 2 physically blocks the operation. An instruction in CLAUDE.md can be forgotten or misinterpreted.

■

Atomic state mutations

All state mutations use the temp file + mv pattern. Scripts write to file.tmp, then mv file.tmp file.json. This prevents corruption from partial writes — critical when multiple agents may update state concurrently.

■

Advisory locking

Multi-agent state access uses mkdir-based advisory locks with 30–60 second timeouts. If a lock is stale (crashed process), error-recovery.sh cleans it up at session start. No deadlocks possible.

■

Research before code

The phase gate enforces architecture decisions (TDR) before any source code writes are allowed. The 15–30 minutes spent on the foundation prevents hours of rework from wrong assumptions.

■

Human attention is the bottleneck

The system stays completely silent during normal operation. It interrupts only when blocked, complete, or failed. Every notification is actionable — no noise, no status updates, no progress bars.

■

Context window discipline

Target <50% context usage. Worktree agents isolate expensive research. MCP servers replace pasting documentation. Warnings at 60% and 80%. Compaction reinject preserves project awareness.

■

Self-improving

Every session's Performance Coach analysis can permanently mutate CLAUDE.md rules. The system gets more efficient with every session. Mistakes are identified, codified, and prevented — recursively.

Help

Troubleshooting

Stale locks or corrupted state

  1. Run ./scripts/error-recovery.sh to clear lock files and repair corrupted JSON
  2. This resets any in-progress tasks that were interrupted by a crashed session

Git conflicts in .vibecrew/

  • state.json: Resolve by keeping the most recent active feature
  • backlog.json: Merge the feature arrays
  • scores/ and sessions/: Rarely conflict — they're timestamped per-developer

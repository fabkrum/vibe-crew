Frequently Asked Questions

Before You Start

Will I lose control of my codebase?

No. Everything runs in your terminal, in your Git repo. You see every change, approve every commit, stop any agent at any time. Run /profile to set your autonomy level — from fully supervised to fully autonomous.

Is my code private?

Yes. VibeCrew runs entirely locally. Your code goes to the Claude API (same as vanilla Claude Code) and nowhere else. No external servers, no telemetry, no data collection. Open source — verify for yourself.

What if VibeCrew makes a mistake?

Every change goes through Git. The quality gate catches type errors, lint issues, and build failures after every task. Review diffs before committing, revert commits with git revert, or use /undo to roll back an entire feature.

Can I stop using VibeCrew and keep my code?

Yes. Your project is standard code in your chosen framework. Remove the plugin symlink, delete the .vibecrew/ folder, and you have a normal codebase. No lock-in, no proprietary formats, no generated code that depends on VibeCrew to run.

Getting Started

What is VibeCrew?

VibeCrew is a Claude Code plugin that transforms Claude Code into an autonomous development team. It orchestrates multiple AI agents, enforces architecture-first development, and manages the full software development lifecycle — from project vision to deployment.

Do I need coding experience to use VibeCrew?

No. VibeCrew is designed for users at all skill levels. Run /profile to set your experience level, and VibeCrew adapts its explanations, autonomy, and output style accordingly. Non-technical founders can build production-grade apps using the Founder preset.

What terminals does VibeCrew support?

VibeCrew works with any terminal. Warp Terminal is recommended because it provides tab deep-linking (click a notification to jump to the exact session), structured output blocks, and Launch Configurations. But iTerm2, VS Code Terminal, Terminal.app, and others all work fine.

How do I install VibeCrew on multiple projects?

Clone VibeCrew once to a central location (e.g., ~/claude-plugins/vibe-crew/), then symlink into each project: ln -s ~/claude-plugins/vibe-crew/claude-plugin-vibe-crew .claude/plugins/vibe-crew.

Workflow

What's the difference between Tier 1 and Tier 2?

Tier 1 is the one-time project foundation: VISION.md, design system, TDR, architecture diagrams, roadmap, and CLAUDE.md. It runs sequentially and must complete before any source code can be written.

Tier 2 is the iterative feature cycle: Plan → UI Design → Code → Test → Review → Docs. Each feature goes through this 6-phase process.

Can I skip the foundation (Tier 1)?

No. The phase gate hook blocks source code writes until the foundation is complete. This is intentional — writing code without architecture decisions leads to rework, inconsistency, and technical debt. The foundation typically takes 15-30 minutes and saves hours of rework later.

How do I add VibeCrew to an existing project?

Use /onboard instead of /new-project. The Code Auditor agent analyzes your codebase, extracts conventions, derives a design system from existing styles, and generates a CLAUDE.md.

What does /run-backlog do?

/run-backlog auto-executes features from your backlog by priority. It runs the full Tier 2 cycle for each feature, including code review, and stops on failure for human review. VibeCrew forces a /compact between features to prevent context rot during long autonomous runs.

What are the UI and business pattern libraries?

VibeCrew includes two pattern libraries that guide agents toward production-quality output. The UI Pattern Guide covers component implementation — forms, navigation, data display, feedback, overlays, and keyboard interactions. The Business Pattern Guide covers conversion-oriented patterns — landing pages, pricing, onboarding, empty states, trust signals, and retention.

Agents automatically reference these patterns when building features, so you get proper error states, accessible interactions, and conversion-optimized layouts without having to specify them.

Cost & Performance

How much does VibeCrew cost to run?

VibeCrew itself is free and open source. You need a Claude subscription or API access to use Claude Code:

  • Claude Pro ($20/month) or Max ($100-200/month) — recommended for most users. Fixed monthly cost, no per-token billing. Max gives higher usage limits for intensive workflows like /run-backlog.
  • Claude API — pay-per-token alternative. A typical foundation session costs $5-15, feature sessions $2-8 depending on complexity. Use /cost for real-time spending and /profile to configure cost guardrails.

Both are fully supported. Start with Pro if you’re unsure.

How does VibeCrew keep token costs down?

Several mechanisms: (1) worktree agents isolate research tokens from the main session, (2) hooks enforce rules at zero token cost, (3) MCP servers like Context7 replace pasting docs (~1,500 tokens saved per query), (4) CLAUDE.md is kept under 200 lines, and (5) forced compaction between features in /run-backlog prevents context rot.

What is the Vibe Score?

A per-session quality metric starting at 100. Points are deducted for prompt churn, tool loops, skipped tests, and documentation drift. Bonuses are awarded for complete artifacts, high cache utilization, TDD discipline, and clean sessions. Range: 0-130. See Self-Improving System.

Community & Contributing

How can I contribute or suggest features?

VibeCrew is open source and community-driven. You can:

  • Propose features — open a GitHub issue with your idea
  • Report bugs — file a bug report with your /status output
  • Share your project — built something with VibeCrew? show it off in Discussions
  • Submit a PR — bug fixes, documentation improvements, and new templates are welcome
Where can I see what others have built?

Check the Show & Tell section in GitHub Discussions. Users share their projects, screenshots, and lessons learned. It’s also a great place to find inspiration for your next build.

Best Practices

Maximizing Efficiency

VibeCrew is designed to make each session more efficient than the last. Here's how to get the most out of the system and why each practice matters.

Context Window Discipline

VibeCrew targets <50% context usage per session. Three mechanisms enforce this automatically:

45%

Warning at 45%

check-context.sh emits a warning. Start thinking about wrapping up. Commit working code.

60%

Critical at 60%

Stronger warning. Commit and run /wrap. Consider delegating remaining work to a sub-agent.

80%

Danger at 80%

Agent quality severely degraded. Immediately run /wrap. Do not attempt complex operations.

When context compaction occurs, compact-reinject.sh automatically re-injects the current project state, active feature, and phase — so you don’t lose context on what you were working on.

Token Efficiency

Use Context7 for everything

This is consistently the single biggest token saver. Every time you paste documentation into chat, you burn ~1,500 tokens that Context7 could fetch on-demand. The Performance Coach will flag this — listen to it.

Write clear initial prompts

Prompt churn (-5 points each) comes from vague instructions. Spend 30 seconds writing a precise prompt instead of 3 follow-up corrections. The first prompt is the cheapest prompt.

Respect context warnings

At 45%: start thinking about wrapping. At 60%: definitely wrap. Pushing to 100% forces a /clear and loses all accumulated understanding. A fresh context + CLAUDE.md = fast restart.

Let agents run in isolation

Stack Scout, Builder, and Code Simplifier run in separate worktree context windows. Don’t duplicate their work in the main session. Their research tokens never touch your context.

Workflow Efficiency

Always /wrap

Never close the terminal without wrapping. The session log feeds the learning system, the commit preserves your work, and the Vibe Score identifies improvements. Skipping /wrap means the session is invisible.

Use /idea aggressively

Mid-feature inspiration should be captured, not pursued. /idea takes 1 second and produces 1 line of output. The idea is safe in the backlog. Your flow is preserved.

Trust the phase gate

It feels restrictive at first. But the 15–30 minutes spent on the foundation prevents hours of rework from wrong architectural assumptions. Every seasoned VibeCrew user says the same thing: "I'm glad it forced me to plan."

Review CLAUDE.md monthly

Remove stale rules, consolidate duplicates, promote critical rules to the top. The Performance Coach adds rules — you curate them. A well-maintained CLAUDE.md is the most powerful file in your project.

A Typical Day

# Morning — start fresh
claude
# Session startup agent runs, shows where you left off

Common Anti-Patterns to Avoid

Anti-PatternConsequenceFix
Skipping /wrap No session log, no Vibe Score, no CLAUDE.md improvements, uncommitted work Always wrap. Make it a habit.
Ignoring the phase gate AI makes wrong assumptions about stack, design, patterns Complete /new-project fully before any feature work
Pasting docs into chat 1,500+ tokens wasted per paste, context fills faster Use Context7 MCP — it's configured and ready
Starting features without specs Feature Developer guesses at requirements, rework later Always run /plan-features or write a spec at /new-feature
Pushing past 60% context Context exhaustion, /clear, lose all session state Wrap at 60%. Fresh context + CLAUDE.md = fast restart
Hardcoding design values Inconsistent UI, wasted tokens fixing later Always reference design-system.css tokens

For Teams

  • One person owns the foundation. The project lead runs /new-project and establishes the TDR. Don't debate architecture in separate sessions.
  • Share the backlog. Use /plan-features as a team exercise. Commit backlog.json so everyone works from the same list.
  • Commit Vibe Scores. Make scores visible to the team — not as competition, but as a shared learning signal for retrospectives.
  • Standardize on Warp. The deep-link notifications are worth it when running parallel sessions across a team.
  • Do score retros. Even 15 minutes every two weeks reviewing score trends and adding team rules to CLAUDE.md compounds into massive efficiency gains.
Meta

System Review & Cross-Project Telemetry

The /system-review command is a meta-level audit that evaluates the VibeCrew plugin itself. Unlike other commands, it operates at the plugin level and should be run from the VibeCrew repository — not from a user project.

Cross-Project Telemetry Flow

Project A (.vibecrew/) ──┐ Project B (.vibecrew/) ──┼── collect-telemetry.sh ──▶ telemetry/aggregate.json Project C (.vibecrew/) ──┘ │ ▼ /system-review (from VibeCrew repo) │ ├── Internal audit (plugin files) ├── Telemetry analysis (cross-project) ├── External research (WebSearch) │ ▼ reviews/system-review-{timestamp}.md reviews/system-review-{timestamp}.json

What Gets Analyzed

1

Internal Audit

Model routing, context budgets, pattern consistency, unreferenced components

2

Telemetry Analysis

Usage patterns, quality trends, cost analysis, systemic friction across projects

3

External Research

Anthropic updates, new MCP servers, community patterns, competitor analysis

4

Proposals

Prioritized improvements with effort estimates and implementation sketches

Running a System Review

  1. Navigate to the VibeCrew repo — /system-review operates at the plugin level, not from user projects.
  2. Run /system-review — the skill collects plugin stats, aggregates telemetry from all registered projects, and launches the System Reviewer agent.
  3. Review the output — the terminal displays a summary with finding counts and top 5 proposals. The full report is saved as markdown and JSON.
  4. Compare with previous reviews — if a previous review exists, new/recurring/resolved findings are automatically identified.

Privacy & Anonymization

All telemetry is strictly local. Projects are identified by anonymous aliases (project-001, etc.). No project names, file paths, code, or credentials are ever included in telemetry data or review reports.

Help

Troubleshooting

Common issues and solutions, from setup problems to advanced workflow questions.

The phase gate is blocking my writes

This means the Tier 1 foundation isn't complete yet. Run /status to see which foundation steps are missing, then run /new-project (or /onboard for existing projects) to complete them. The phase gate only blocks source code writes — config files, documentation, and .vibecrew/ state files are always writable.

My session state is corrupted

Run /recover-state to clear lock files and repair corrupted JSON. If that doesn't work, you can manually delete the .vibecrew/locks/ directory. Your backlog, session logs, and scores are never deleted during recovery.

Notifications aren't working

  1. Test terminal-notifier directly: terminal-notifier -message "test"
  2. Check macOS: System Settings → Notifications → terminal-notifier
  3. Verify .vibecrew/config.json has "notifications": true

An MCP server isn't connecting

Default servers (Context7, Chrome DevTools, Playwright) work via npx — try restarting Claude Code. For conditional servers (Supabase, Stripe, etc.), ensure the required environment variables are set. Run bash scripts/enable-mcp-server.sh <name> enable to activate. All MCP servers are optional — agents gracefully fall back to built-in tools.

Vibe Score seems inaccurate

  • New projects: Scores are less meaningful in the first few sessions as the system establishes baselines
  • Complex features: Large features naturally have more tool calls and corrections — the score accounts for this but may seem low
  • Override deductions: If the coach flags something unavoidable, say so during the coaching dialogue — it factors into the next proposal

/heal can't fetch CI logs

  1. Verify the CLI is authenticated: gh auth status (GitHub) or glab auth status (GitLab)
  2. Ensure the repo has a remote: git remote -v
  3. Check that a recent CI run exists: gh run list --limit 5 (GitHub) or glab ci list (GitLab)
  4. If the failure is on a different branch, switch to it first

/simplify shows no suggestions

  • The agent only analyzes files changed on the current feature branch vs. the default branch
  • Verify you're on a feature branch (not main/master): git branch --show-current
  • Check that source files were changed (config and docs are excluded)
  • The minimum files threshold is configurable in .vibecrew/config.json under simplify.min_files_for_analysis

/replay can't find eligible sessions

  • Only sessions with a Vibe Score ≥ 70 are eligible for template extraction
  • Verify session logs exist in .vibecrew/sessions/ and score files in .vibecrew/scores/
  • Run /wrap at the end of sessions to generate the required data

Gamification not showing after /wrap

  1. Check that gamification is enabled: jq '.gamification.enabled' .vibecrew/config.json should return true
  2. Verify .vibecrew/gamification.json exists. If not, run /setup to create it
  3. Check that the gamification scripts are executable: ls -la scripts/award-xp.sh
  4. Run a script manually to debug: bash scripts/award-xp.sh — it outputs JSON with the XP breakdown

/quiz shows "Unlocks at Level 3"

  • The /quiz command requires Level 3 (approximately 3–4 completed sessions)
  • Check your level: jq '.level' .vibecrew/gamification.json
  • Keep running /wrap at the end of sessions to earn XP and level up

Streak broke unexpectedly

  • Streaks increment on calendar days where /wrap runs. If you didn’t wrap, the day doesn’t count
  • Weekends never break streaks. Check if you missed a weekday
  • Grace days reset on the 1st of each month: jq '.streak.grace_days_remaining' .vibecrew/gamification.json
  • If the streak counter seems wrong, check .streak.last_session_date in gamification.json

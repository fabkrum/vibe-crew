Getting Started

Installation from Scratch

A complete walkthrough from zero to a fully operational VibeCrew environment.

Prerequisites

VibeCrew needs 3 required dependencies and has 2 optional ones:

RequirementTierMinimum VersionCheck Command
GitRequired2.30+git --version
Node.jsRequired18+node --version
jqRequired1.6+jq --version
GitHub CLIOptional2.0+gh --version
terminal-notifierOptionalanywhich terminal-notifier

Optional dependencies: GitHub CLI enables PR automation (/review, gh pr create). terminal-notifier enables desktop notifications on macOS. VibeCrew works without both.

Step-by-Step Installation

  1. Install dependencies

    Use the bootstrap script (recommended) or install manually:

    bash# Option A: Bootstrap script (detects OS, installs only what's missing)
cd claude-plugin-vibe-crew && ./install.sh

# Option B: Manual install on macOS
brew install jq node
# Optional:
brew install terminal-notifier gh && gh auth login

    Alternatively, /setup inside Claude Code can auto-install missing required dependencies.

  2. Add the plugin to your project

    The recommended approach is a central clone + symlink, especially if you'll use VibeCrew across multiple projects. See Multi-Project Setup below for the full guide.

    bash# Recommended: Central clone + symlink (see Multi-Project Setup below)
mkdir -p ~/claude-plugins && cd ~/claude-plugins
git clone https://github.com/fabkrum/vibe-crew.git
cd ~/projects/my-project
ln -s ~/claude-plugins/vibe-crew/claude-plugin-vibe-crew ./claude-plugin-vibe-crew

    For alternative approaches (direct copy, git submodule), see the comparison table in the Multi-Project section.

  3. Verify plugin detection

    Start Claude Code in your project directory. It reads the .claude-plugin/plugin.json manifest and loads VibeCrew automatically.

    bashcd /path/to/your-project
claude

    You should see the VibeCrew session startup agent run on first launch.

  4. Run the setup wizard

    Inside Claude Code, run:

    claude code/setup

    The wizard walks you through terminal selection, notification testing, MCP server verification, git checks, and creates the .vibecrew/ runtime directory.

  5. Personalize your experience (optional)

    Run the profile interview to adapt VibeCrew to your workflow. This takes about 2 minutes, or pick a preset (Builder, Explorer, Founder) for instant configuration.

    claude code/profile

    This personalizes message verbosity, autonomy level, PR format, code comments, gamification, and more. You can update it anytime by running /profile again. See User Profile & Personalization for full details.

  6. Install MCP servers (optional but recommended)

    VibeCrew ships with 10 MCP servers. Three are enabled by default: Context7 (documentation lookup, ~1,500 tokens saved per query), Chrome DevTools (browser debugging), and Playwright (E2E browser testing). All three require no authentication.

    Seven additional servers ship disabled and are auto-enabled when your TDR selects matching technologies: Semgrep (security scanning), Sentry (error tracking), Supabase (database), Stripe (payments), Vercel (deployment), Figma (design), and Stitch (Google AI design). Authenticated servers require environment variables — the setup wizard shows which variables are needed.

  7. Verify the full pipeline

    • Notifications: Tested during setup wizard
    • Session startup: Exit and restart Claude Code — the startup agent should show a 3-line status summary
    • Phase gate: Try writing a source file before running /new-project — it should be blocked

Resulting Directory Structure

treeyour-project/
  claude-plugin-vibe-crew/          # The plugin (don't modify)
    .claude-plugin/
      plugin.json                 # Plugin manifest
    .mcp.json                     # MCP server config (10 servers)
    settings.json                 # Permission rules (allowed + denied tools)
    hooks/

    ci-heals/                     # CI heal reports (/heal)
    mutation-log.json             # CLAUDE.md mutation audit log

Multi-Project Setup

Most users work on multiple projects. Instead of copying VibeCrew into every project, install it once and share it. This gives you a single source of truth, instant updates across all projects, and zero duplication.

How it works

Central install (one copy on your machine) ~/claude-plugins/vibe-crew/ # the plugin — shared by all projects Per-project (symlink + local state) ~/projects/tripflow/ claude-plugin-vibe-crew → # symlink to central install .vibecrew/ # project-specific state ~/projects/saas-dashboard/ claude-plugin-vibe-crew → # same symlink, different project .vibecrew/ # its own state ~/projects/mobile-app/ claude-plugin-vibe-crew → # same symlink, different project .vibecrew/ # its own state

The plugin code (agents, hooks, scripts, commands) lives in one place. Each project gets its own .vibecrew/ folder with its own backlog, session logs, scores, and config. Projects are fully isolated from each other.

Step-by-step

  1. Clone VibeCrew to a central location

    Pick a permanent home for the plugin. ~/claude-plugins/ is a good convention.

    bashmkdir -p ~/claude-plugins
cd ~/claude-plugins
git clone https://github.com/fabkrum/vibe-crew.git

  2. Symlink into your first project

    Create a symbolic link from your project to the central install. Use an absolute path so the link works regardless of where you open the terminal.

    bashcd ~/projects/my-project
ln -s ~/claude-plugins/vibe-crew/claude-plugin-vibe-crew ./claude-plugin-vibe-crew

  3. Run /setup in the project

    Start Claude Code and run the setup wizard. This creates the .vibecrew/ folder with project-specific state. Each project runs /setup once.

    bashclaude
    claude code/setup

  4. Repeat for each new project

    For every new project, just create the symlink and run /setup. Two commands, under 30 seconds.

    bashcd ~/projects/another-project
ln -s ~/claude-plugins/vibe-crew/claude-plugin-vibe-crew ./claude-plugin-vibe-crew

Updating VibeCrew across all projects

Since every project symlinks to the same central location, updating is one command:

bashcd ~/claude-plugins/vibe-crew && git pull

Every project picks up the changes instantly. No need to copy files, run installers, or touch individual projects. Check the Release Notes after updating to see what changed.

Make it even faster with a shell alias

Add this to your ~/.zshrc to create new VibeCrew projects in one command:

.zshrc# Add to ~/.zshrc
vibecrew-init() {
  ln -s ~/claude-plugins/vibe-crew/claude-plugin-vibe-crew ./claude-plugin-vibe-crew
  echo "VibeCrew linked. Run 'claude' then '/setup' to initialize."
}

vibecrew-update() {
  (cd ~/claude-plugins/vibe-crew && git pull)
  echo "VibeCrew updated to $(cd ~/claude-plugins/vibe-crew && git describe --tags 2>/dev/null || git log -1 --format=%h)"
}

Then for any new project: cd ~/projects/new-project && vibecrew-init

Git and symlinks

By default, Git tracks symlinks as tiny pointer files (not the target contents). This means:

  • Your project repo stays small — only the symlink is committed, not the entire plugin
  • Teammates need their own central install — the symlink points to your local path, so each person clones the plugin to the same location or updates the symlink
For teams: standardize the path

Agree on a team-wide convention like ~/claude-plugins/vibe-crew/. If everyone uses the same path, symlinks work across the entire team with zero config. Document this in your project's README or onboarding guide.

Comparing installation approaches

ApproachBest ForUpdate MethodDuplication
Central clone + symlink Solo devs, small teams git pull once → all projects updated None
Git submodule Teams needing pinned versions git submodule update per project Full copy per project
Direct copy Quick experiments, air-gapped Manual copy per project Full copy per project
Don't mix approaches

Pick one method and stick with it. If some projects use symlinks and others use submodules, updates become confusing and you risk running different VibeCrew versions across projects without realizing it.

What's shared vs. what's project-specific

⇄

Shared (via symlink)

Agent prompts, hook scripts, slash commands, plugin manifest, MCP config, templates. These are the same across all projects and update together.

☗

Project-specific (.vibecrew/)

Backlog, session logs, Vibe Scores, config, state, handoffs, workflows. Each project has its own isolated state folder that's never shared.

✍

Project-specific (project root)

CLAUDE.md, VISION.md, design-system.css, TDR, roadmap. These are created by VibeCrew during the foundation phase and are unique to each project.

⚙

Machine-specific (~/.zshrc)

Shell aliases (vibecrew-init, vibecrew-update), shell traps, Warp Terminal config. Each developer sets these up once on their machine.

Terminal Setup

Warp Terminal

Warp is the recommended terminal for VibeCrew. It provides tab deep-linking (click a notification and land on the exact session that needs attention), structured output blocks, Launch Configurations for instant workspace setup, and session restoration.

Everything you need — installation, deep-linking setup, keyboard shortcuts, Warp Drive, window layouts, and more — is covered on the dedicated Warp page:

Warp Tips & Tricks →

Using a different terminal?

VibeCrew works with any terminal. You'll get macOS banner notifications regardless. The only difference is that non-Warp terminals can't deep-link to a specific tab — clicking the notification brings the terminal app to focus but you'll need to find the tab manually.

Optional MCP Server

Enabling Google Stitch (UI Design)

Google Stitch is an AI design tool from Google Labs that transforms text prompts into complete UI designs and production-ready HTML/CSS. VibeCrew ships with the Stitch MCP server disabled by default — here's how to enable it and use it in your workflow.

What does Stitch add?

Without Stitch, VibeCrew's Builder agent generates UI code from your design system tokens and feature specs. With Stitch, you get an additional option: generate a visual UI design first in Google Stitch, preview it, then pull the production HTML/CSS into your project. This is especially useful for complex layouts, landing pages, and when you want to iterate on the visual design before writing any code.

Prerequisites

  • Node.js 18+ (already required for VibeCrew)
  • A Google account to access Google Stitch

Setup

  1. Authenticate with Stitch

    Run the Stitch CLI init command to set up OAuth authentication or provide an API key.

    bashnpx @_davideast/stitch-mcp init

  2. Enable the MCP server

    Open claude-plugin-vibe-crew/.mcp.json and change "disabled": true to "disabled": false for the Stitch entry.

    .mcp.json{
  "mcpServers": {
    "context7": { ... },
    "chrome-devtools": { ... },
    "stitch": {
      "command": "npx",
      "args": ["-y", "@_davideast/stitch-mcp", "proxy"],
      "env": {},
      "disabled": false    ← change this from true to false
    }
  }
}

  3. Restart Claude Code

    MCP servers are loaded on startup. Exit and relaunch Claude Code so it picks up the Stitch server.

UI Design Workflow with Stitch

Once enabled, Stitch integrates into VibeCrew's Tier 2, Phase 2 (UI Design) workflow. Here's how a typical feature development cycle looks:

Phase 1: Plan Feature spec written → requirements defined | Phase 2: UI Design (with Stitch) | 1. Create designs in labs.google/stitch Describe your UI in natural language. Stitch generates screens with full visual fidelity. | 2. Preview screens locally npx @_davideast/stitch-mcp serve -p <project-id> | 3. Pull design code via MCP The Builder agent calls get_screen_code to retrieve production HTML/CSS for each screen. | 4. Integrate into your project Builder adapts the Stitch output to match your design-system.css tokens and component structure. | Phase 3: Code Builder implements business logic on top of the UI | Phase 4: Test → Phase 5: Docs

Stitch MCP Tools

ToolDescriptionUsed By
build_siteMaps Stitch screens to routes and returns design HTML for each pageBuilder agent
get_screen_codeRetrieves the HTML/CSS code for a single screenBuilder agent
get_screen_imageDownloads a screenshot of a screen as base64 for visual reviewBuilder agent, Verifier
When to use Stitch vs. direct coding

Use Stitch for landing pages, complex multi-screen layouts, and when you want to iterate on visuals before writing code. Skip Stitch for simple CRUD interfaces, API-heavy features, or when your design system already has the components you need. The Builder agent handles both paths — Stitch is an accelerator, not a requirement.

Stitch is experimental

Google Stitch is a Google Labs experiment and may change or be discontinued. VibeCrew treats it as a fully optional enhancement — nothing in the core workflow depends on it. If Stitch is unavailable, the Builder agent generates UI code directly from your design system tokens and feature spec as usual.

Help

Troubleshooting

Notifications don't appear

  1. Test terminal-notifier directly: terminal-notifier -message "test"
  2. If nothing appears, reinstall: brew install terminal-notifier
  3. Check macOS: System Settings → Notifications → terminal-notifier → Allow Notifications
  4. Check VibeCrew config: verify .vibecrew/config.json has "notifications": true
  5. Warp deep-links not working: see the deep-linking guide on the Warp page

MCP servers not available

  1. Default servers (Context7, Chrome DevTools, Playwright): These should work out of the box via npx. Try restarting Claude Code.
  2. Bundled conditional servers (Supabase, Stripe, Vercel, Figma, Sentry, etc.): Set the required environment variables, then run bash scripts/enable-mcp-server.sh <name> enable.
  3. Registry servers not yet in .mcp.json (Firebase, Clerk, MongoDB, etc.): Add from the registry with bash scripts/add-mcp-server.sh <key>, or see all available servers with bash scripts/add-mcp-server.sh --list.
  4. All MCP servers are optional. VibeCrew agents gracefully fall back to built-in tools when servers are unavailable.

Stale locks or corrupted state

  1. Run ./scripts/error-recovery.sh to clear lock files and repair corrupted JSON
  2. This resets any in-progress tasks that were interrupted by a crashed session

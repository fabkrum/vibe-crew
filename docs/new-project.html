New Projects

Using VibeCrew with New Projects

New projects follow the Two-Tier Workflow. Tier 1 creates the architectural foundation. Tier 2 builds features on top of it. The phase gate enforces this order — you cannot write source code until the foundation is complete.

Tier 1: The Project Foundation

Run /new-project to start a guided, 6-step process. Each step produces a concrete artifact before the next begins.

  1. VISION.md — Define project goals

    VibeCrew asks: What problem does this solve? Who are the target users? What's the value proposition? What are the constraints? What does success look like?

    The output is VISION.md — a document every agent reads. When the Feature Developer writes code, it knows who your users are. When the Stack Scout evaluates technologies, it factors in your constraints.

  2. Design Discovery — Establish visual identity

    VibeCrew runs a 3-phase design interview tailored to your product. First, it asks about your product category, audience, usage patterns, and emotional direction. Then it generates 3 visual directions specifically adapted to your answers — not generic options. Finally, it collects component preferences (navigation style, data display, interaction density) filtered by your earlier choices. The output: design-system.css (CSS custom properties) and design-brief.md (design rationale for agents to reference). Learn more about Design Discovery →

  3. TDR — Research and lock the tech stack

    The Stack Scout agent activates. This is a read-only research agent that runs in an isolated context window. It uses WebSearch, Context7, Chrome DevTools, and Supabase MCP (when available) to evaluate technology options against your requirements, then produces a Technology Decision Record at docs/tdr-001-tech-stack.md.

    The TDR documents what was considered, what was chosen, and why. Once approved, every agent works within these boundaries. The research costs 8,000–15,000 tokens but none of them touch your main session — only the distilled decision enters your context window.

    Step 3.5: Opponent Processor — Immediately after the TDR, VibeCrew invokes the Opponent Processor agent to stress-test every technology decision. You see both the TDR and the counter-analysis side by side, then choose: keep all decisions, reconsider specific ones, or skip. See Opponent Processor for details.

    Step 3.6: MCP Server Sync — After TDR approval, VibeCrew scans the TDR for technology mentions. Bundled servers (Supabase, Stripe, Vercel, Figma, Sentry, etc.) are auto-enabled. Additional servers from the registry (Firebase, Clerk, MongoDB, Netlify, and 11 more) are recommended if they match your TDR — you choose to add all, pick specific ones, or skip. You'll be prompted to set environment variables for authenticated servers. This is non-blocking — the workflow continues regardless.

  4. Roadmap — Map out features

    List your planned features in rough priority order. VibeCrew generates docs/roadmap.md with priority tiers (Must Have, Should Have, Nice to Have, Out of Scope). This becomes the input for /plan-features later.

  5. Architecture Diagrams — Visualize the architecture

    VibeCrew generates 5 Mermaid diagrams in .vibecrew/architecture/ that give agents a compact visual architecture reference (~250–600 tokens for all 5, vs 2,000–5,000 for the full TDR):

    • system.mmd — Infrastructure topology (services, boundaries, data flow)
    • schema.mmd — Database entity-relationship diagram
    • state-flows.mmd — Authentication states and primary user journeys
    • api-sequences.mmd — API request/response patterns
    • component-tree.mmd — Component hierarchy with data flow direction (extended during Tier 2)

  6. CLAUDE.md — Codify project rules

    VibeCrew synthesizes everything into a minimal rules file (~31 lines). It includes your tech stack, conventions, architecture rules, and a “Session Learnings” section (capped at 15 rules, oldest auto-pruned). Deliberately kept small — research shows oversized context files increase agent cost 20%+ without improving outcomes. No directory enumerations, no rules that hooks already enforce.

  7. Git commit — Version the foundation

    Everything is committed: git commit -m "plan: project foundation". The phase gate unlocks. Source code writes are now allowed.

The Phase Gate
Until all 6 steps are complete, a PreToolUse hook blocks all writes to source directories (src/, app/, lib/, components/). Configuration files (.vibecrew/, CLAUDE.md, docs/) are allowed. This is enforced by phase-gate.sh — it's a hard block, not a suggestion.

Tier 2: Building Features

With the foundation in place, you enter the iterative feature loop.

Planning the backlog

Run /plan-features to create structured specifications for each feature: name, description, problem statement, acceptance criteria, priority, complexity (S/M/L/XL), and dependencies. These are stored in .vibecrew/backlog.json.

Starting a feature

claude code/new-feature "user authentication"

This creates a feature branch (feat/user-authentication), initializes 6-phase tracking, and loads the feature spec. You're now in the development loop.

The 6-phase cycle

Plan → UI Design → Code → Test → Review → Docs Phases can be worked in any order. Review is optional in manual workflows, automatic in /run-backlog. Completeness is checked at /wrap, not during work.

Plan

Problem statement, acceptance criteria, edge cases, and technical notes at docs/features/<name>.md.

UI Design

Component hierarchy, props, variants. Uses design system tokens. Mobile-first, WCAG AA compliant.

Code

Implementation within TDR boundaries. Checks Context7 before using any library API. Follows CLAUDE.md conventions.

Test

TDD-hybrid: spec tests for business logic (written first), implementation tests for UI (written after). Tests behavior, not implementation.

Review

Automated code review against feature spec, TDR compliance, project conventions, security, and performance. Findings ranked by severity.

Docs

Feature documentation, CHANGELOG entries, session logs. Drift detection ensures docs stay current with code changes.

Wrapping a session

claude code/wrap

Checks completeness, runs the quality gate (tests + build + lint), triggers the Performance Coach for your Vibe Score, logs the session, and creates a conventional commit. Never close the terminal without wrapping.

Automated execution

claude code/run-backlog

Automatically picks the next planned feature by priority, executes it through Plan → Design → Code → Test, runs the quality gate, and loops. Stops on failure so you can fix and resume.

Phase gate blocks when it shouldn't

The phase gate message shows your progress: "Foundation progress: 2/6 artifacts complete. Missing: tdr, roadmap, architecture diagrams, claude md."

  1. Check .vibecrew/state.json — is foundation.complete set to true?
  2. If any foundation artifacts are incomplete, run /new-project to complete the missing steps or /status for details
  3. The phase gate allows writes to config paths (.vibecrew/, CLAUDE.md, docs/). If a legitimate config file is blocked, check the path patterns in phase-gate.sh

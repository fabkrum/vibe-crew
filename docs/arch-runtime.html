Runtime

Runtime Systems

These systems operate during sessions to manage context, attention, quality, cost, and cross-session continuity.

What are runtime systems?
Runtime systems are things that happen while you're working, in the background. You don't trigger them manually — they just run. The status bar updates automatically. Notifications fire when the AI needs you. The phase gate silently blocks mistakes. Cost tracking accumulates as you go. Think of them as the dashboard, warning lights, and autopilot in a car: you don't have to think about them, but they're always keeping you informed and safe.

The Status Bar

What is the status bar?
The status bar is a thin line of information at the bottom of your terminal that tells you what's happening at a glance — like the dashboard in a car showing speed, fuel, and engine status. It shows how much AI "memory" you've used, how much the session costs so far, which feature you're building, your quality score, and how long you've been working. It updates automatically after every AI response and costs nothing extra.

A persistent status line renders after every assistant message, showing six data segments at zero token cost. The script (scripts/statusline.sh) is configured via settings.json and runs as a shell command outside the AI context window.

The Interrupt Protocol

What is the Interrupt Protocol?
The Interrupt Protocol is VibeCrew's "don't bother me unless it's important" system. When you have multiple terminal tabs running, you don't want constant notifications from all of them. VibeCrew stays completely silent while things are going well. It only pings you in three situations: (1) the AI needs your permission to do something, (2) a task finished and it's waiting for your next instruction, or (3) something broke. This lets you focus on one task and trust that you'll be pulled in only when truly needed.

The Interrupt Protocol is the "Attention Economy" architecture. The terminal stays completely silent during normal operation. Notifications fire only on three conditions:

!

Permission Stalls

permission_prompt — The agent needs Y/N approval. Execution is halted. Priority: Critical.

✔

Task Completion

idle_prompt — A complex operation finished. The agent is waiting for your next instruction. Priority: High.

⚠

Critical Failures

PostToolUseFailure — A tool returned a fatal exit code or compilation error that can't be resolved autonomously. Priority: High.

Everything else — standard tool execution, file reads, successful commands — is silent. Your Deep Work state is preserved.

The Phase Gate

What is the phase gate?
The phase gate is a guardrail that prevents you from writing code too early. Before any code can be written, VibeCrew requires you to complete the project foundation: define your vision, choose your technology, plan your design system, and set up the rules. This sounds strict, but it's the most important time-saver in the entire system. Without it, the AI might start writing code using the wrong tools, wrong design, or wrong approach — and you'd waste hours fixing that. The phase gate checks automatically on every file write, so you can't accidentally skip it.

The phase gate is the architectural enforcement mechanism. It runs as a PreToolUse hook on every Write and Edit operation.

phase-gate.sh receives JSON payload from Claude Code ↓ Reads .vibecrew/state.json → checks project_foundation.status ↓ If "complete": exit 0 (allow all writes) If "incomplete": ↓ Check file path being written: .vibecrew/, CLAUDE.md, VISION.md, docs/, design-system.css → exit 0 (foundation artifacts allowed) src/, app/, lib/, components/, etc. → exit 2 (BLOCKED)

When blocked, the developer sees a clear message listing which foundation steps remain incomplete and how to complete them.

The Vibe Score & Performance Coach

What is the Vibe Score?
The Vibe Score is your session quality rating, from 0 to 100. Think of it like a fitness tracker for your coding sessions. At the end of each session, VibeCrew reviews how things went: Did you plan before coding? Did you write tests? Did you waste time going back and forth? A high score (90+) means the session was efficient and well-structured. A low score means there's room to improve. The Performance Coach then gives you a tip and suggests a new rule that will prevent the same issue next session. Over time, these rules accumulate and your sessions get more efficient automatically — the system literally learns from your habits.

The Performance Coach runs at the end of every session (triggered by /wrap). It ingests the session transcript, calculates a Vibe Score, and initiates an interactive coaching dialogue.

How the score is calculated

Starting from 100, deductions are applied for detected anti-patterns:

The coaching dialogue

After calculating the score, the Performance Coach:

  1. Presents the score with the single biggest observation: "Vibe Score: 82/100. You pasted API docs 3 times (~4,500 tokens). Using Context7 MCP would have saved those tokens."
  2. Asks for feedback: "How did this session feel? Any friction points?"
  3. Proposes a CLAUDE.md rule: "Proposed rule: Always use Context7 for Dexie.js API docs. Add this? (y/n)"
  4. Mutates CLAUDE.md if approved — the rule is permanent and active from the next session onwards.
The recursive improvement loop
Session 1: paste docs, score 78, rule added. Session 2: AI reads rule, uses Context7, score 89, new rule proposed. Session 3: two rules active, score 94. Each session is more efficient than the last. Mistakes are identified, codified, and permanently prevented.

Context Compaction & Reinject

What is context compaction?
The AI has a limited "memory" for each conversation (called the context window). As your session gets longer, older messages start taking up too much space. Claude Code handles this by compacting (summarizing) older messages to free up room. The problem is: after compaction, the AI might forget what project you're working on or what feature you were building. VibeCrew solves this by automatically re-injecting a tiny summary (~300 words) of your project state after every compaction. The AI seamlessly continues without asking "wait, what were we doing?" It's like leaving a sticky note on your desk so you remember where you left off after a break.

When the context window approaches capacity, Claude Code compacts older messages. VibeCrew hooks into this event to ensure you never lose track of what you were working on.

Context window reaches ~50% capacity ↓ Claude Code triggers context compaction (older messages compressed) ↓ SessionStart "compact" hook fires ↓ compact-reinject.sh executes (5-second timeout) ↓ Outputs a <300-token summary: • Foundation status (complete/incomplete + missing steps) • Active feature (name, branch, current phase, phases completed) • Backlog summary (by Kanban column) • Architecture diagrams (all 5 Mermaid files, via inject-architecture.sh) • Recent commits (last 5) • CLAUDE.md summary (line count, section count) ↓ Agent seamlessly continues with full project awareness

This mechanism is why sessions can survive multiple compactions without degradation. The <300-token reinject costs less than a single follow-up clarification question.

Inter-feature context hygiene (/run-backlog)

During autonomous backlog processing via /run-backlog, the context window accumulates stale conversation history from each completed feature — planning discussions, build output, test results, review findings. Left unchecked, this "context rot" degrades quality for later features as the model operates with an increasingly polluted window.

VibeCrew solves this with forced inter-feature compaction. After each feature passes its quality gate and state is cleared, the agent triggers /compact before starting the next feature. This compresses the stale history and fires compact-reinject.sh to re-inject fresh project state and architecture diagrams. Each feature effectively begins with a near-fresh context window.

/run-backlog picks next feature from backlog ↓ Feature N: Plan → UI Design → Code → Test → Review → Docs → quality gate passes ↓ State cleared, commit created ↓ /compact triggered → stale history compressed ↓ compact-reinject.sh fires → project state + architecture diagrams re-injected ↓ Feature N+1 begins with near-fresh context Last feature skips compaction (session ends with /wrap instead)
Why the last feature skips compaction
The final feature in a backlog run is followed by /wrap, which generates the session log, Vibe Score, and handoff document. Compacting before /wrap would discard the context the Performance Coach needs to analyze the session. The last feature’s context is preserved so the wrap phase has full visibility.

The Handoff System

What is a handoff?
A handoff is a briefing document for your next session. Every time you close a session and open a new one, the AI starts with a blank slate — it doesn't remember your previous conversation. The handoff document solves this by writing down everything the next session needs to know: what you were working on, what's done, what's blocked, and what to do next. It's like writing a note to your future self (or a colleague taking over your shift). The next session reads this note and picks up exactly where you left off, without wasting time re-explaining everything.

The /handoff command generates a structured context transfer document designed for the next session. This solves the "cold start" problem where a new session has to re-discover what you were working on.

Handoff document structure

handoff-2026-02-24-001.md# Session Handoff — 2026-02-24

## Active Work
- Feature: user-auth (User Authentication)
- Phase: Test (3/6 phases complete)
- Branch: feat/user-auth

## Recent Progress
- Implemented Supabase auth client
- Created login/signup pages
- Added route middleware

## Blockers
- OAuth callback URL needs env var NEXT_PUBLIC_SUPABASE_URL

## Next Steps
- Write tests for auth middleware
- Add error states to login form
- Complete docs phase

## Decisions Made
- Using Supabase Auth (not NextAuth) per TDR
- Middleware-based route protection (not per-page)

Handoff documents are stored in .vibecrew/handoffs/ and are also generated automatically by /wrap. The Session Startup agent reads the most recent handoff to orient the new session.

Token savings from handoffs
Without a handoff, re-establishing context costs ~2,000 tokens of explanation: "I was working on auth, I'm on the feat/user-auth branch, I finished the code phase, I still need to..." With a handoff, the startup agent reads a structured file and produces a 3-line status banner. The session starts immediately productive.

Error Recovery

What is error recovery?
Sometimes things go wrong: your laptop crashes, you accidentally close a terminal, or the internet drops mid-session. Error recovery is VibeCrew's self-healing system that runs automatically every time you start a new session. It quietly cleans up any mess left behind — removing stale lock files, repairing corrupted data, and flagging unresolved issues. You don't need to do anything; it just works. If it finds something it can't fix automatically (like a merge conflict in your code), it tells you what happened and how to resolve it.

The error-recovery.sh script runs at every session start via the SessionStart hook. It silently cleans up problems left by crashed or interrupted sessions.

🔒

Stale lock cleanup

Removes .vibecrew/locks/*/ directories older than 60 seconds. Prevents deadlocks from crashed multi-agent operations.

📄

Temp file cleanup

Removes temporary files from failed atomic write operations (the .tmp files left behind when mv never executed).

⚙

Git state validation

Checks for unresolved merge conflicts and detached HEAD state. Reports issues but doesn't auto-resolve — those need human judgment.

▶

Orphaned process detection

Lists orphaned agent processes from previous sessions. Reports but doesn't kill — avoids terminating intentional background work.

Cost Guardrails

What are cost guardrails?
Using AI costs money — every message you send and every response you receive has a small price tag based on how much text is processed. Cost guardrails are VibeCrew's spending protection system. They track your costs in real time and warn you when you approach a limit — like a prepaid phone that warns you when your balance is low. You set the limits yourself (e.g., "$5 per session, $20 per day"), and VibeCrew will pause and ask before exceeding them. This prevents surprise bills from long or runaway sessions.

The cost-guardrails.sh script runs on every Stop event. It calculates per-turn costs using model-aware pricing and accumulates totals in .vibecrew/session-cost.json.

How cost tracking works

Stop hook fires after every assistant turn ↓ cost-guardrails.sh reads token counts from hook JSON payload: input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens ↓ Calculates USD cost using per-model pricing (Opus/Sonnet/Haiku) ↓ Accumulates in .vibecrew/session-cost.json ↓ Checks against thresholds: Session warning ($2.00) → emit cost warning Session max ($5.00) → agent MUST pause and ask permission Daily warning ($20.00) → emit daily spend alert

All thresholds are configurable in .vibecrew/config.json under cost_limits. The /cost command reads this data to display the full financial picture.

Quality Gate

What is the quality gate?
The quality gate is an automatic code checker that runs every time the AI finishes a task. It catches type errors, lint violations, and build failures immediately — before they pile up. Think of it as a spell-checker that runs after every paragraph instead of waiting until you're done writing the entire essay. If it finds problems, it tells the AI exactly what's wrong so it can fix them right away.

The quality-gate.sh script runs as the final Stop hook, after context warnings, cost guardrails, and CLAUDE.md linting. Unlike the other Stop hooks, it can block (exit non-zero) to signal errors back to the agent.

How it works

Stop hook fires after every assistant turn ↓ quality-gate.sh checks prerequisites: • Foundation must be complete (no checks during Tier 1) • User profile autonomy must be full_auto or checkpoints ↓ Detects modified source files via git diff (skips if no .ts/.tsx/.js/.jsx/.vue/.svelte/.py etc. changed) ↓ Discovers check commands from package.json scripts: typecheck → lint → build (runs in order, stops on first failure) ↓ Auto-detects package manager (npm/bun/pnpm/yarn) ↓ Pass: exits 0 silently — no output, no interruption Fail: exits 1 with error report (last 80 lines) — agent sees it and fixes

The quality gate complements the Verifier agent (which runs full test suites via /check and /wrap). The Stop hook catches fast signals (typecheck, lint, build) on every turn, while the Verifier handles deep signals (unit tests, integration tests, coverage) on demand.

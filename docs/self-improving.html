Self-Improving System

VibeCrew doesn't just build software — it learns from every session. The Performance Coach analyzes each session's patterns, proposes permanent rule changes to CLAUDE.md, and aggregates anonymized metrics across all your projects. Each session makes the next one better.

■
What it is

A feedback loop: the Performance Coach scores each session, detects anti-patterns, and proposes CLAUDE.md mutations. Cross-project telemetry tracks trends across all your VibeCrew projects. The /system-review command analyzes the plugin's own performance.

✓
What problem it solves

AI agents make the same mistakes across sessions because they start fresh each time. The self-improving loop captures what went wrong (and right), encodes fixes as permanent CLAUDE.md rules, and tracks whether those fixes actually work over time.

Performance Coach

The Performance Coach is an Opus agent that runs during /wrap at the end of every session. It analyzes what happened during the session and produces actionable coaching.

What It Analyzes

DimensionWhat It ChecksExample Finding
Prompt Efficiency Prompt churn (repeated similar prompts), tool loops (same tool called 3+ times) "You re-prompted the Builder 4 times for the same component — next time, include acceptance criteria in the spec."
Cache Utilization Cache hit ratio across the session "Cache utilization was 23% — consider keeping CLAUDE.md stable to improve prompt caching."
Phase Completeness Missing artifacts (tests, docs, review) for each phase "Feature shipped without E2E tests — consider adding /e2e to your workflow."
Context Discipline Context window usage at session end, number of compactions "Session hit 82% context usage — offload research to Stack Scout earlier."
Anti-patterns Recurring mistakes across 3+ sessions "This is the 3rd session with skipped code review — proposing a CLAUDE.md rule to make review mandatory."

Session Learnings & CLAUDE.md Mutations

When the Performance Coach detects a recurring anti-pattern (appears in 3+ sessions), it proposes a permanent rule change to the project's CLAUDE.md file. These mutations are the mechanism by which VibeCrew gets smarter over time.

How Mutations Work

StepWhat Happens
1. DetectionPerformance Coach identifies a pattern appearing in 3+ sessions (e.g., "tests always written after code" or "docs consistently skipped").
2. ProposalCoach drafts a concrete CLAUDE.md rule using a standard template. Example: "Always run /tdd before implementing — write the test first."
3. ApprovalThe proposal is shown to the user for approval. Mutations never auto-apply — the user always has final say.
4. Applicationapply-mutation.sh appends the rule to the Session Learnings section of CLAUDE.md.
5. PruningSession Learnings are capped at 15 entries. When a new rule is added past the limit, the oldest entry is removed to keep CLAUDE.md lean.
⚠
Why 15 learnings max?

Research shows oversized CLAUDE.md files increase agent cost 20%+ without improving success rates. The cap ensures the file stays under 200 lines. Old learnings that haven't prevented their anti-pattern get pruned first.

Cross-Project Telemetry

VibeCrew tracks anonymized performance data across all your projects. This isn't sent anywhere — it lives locally in the plugin directory and powers the /system-review command.

How It Works

StepWhat Happens
Auto-registrationDuring /setup, the project registers itself in the central plugin's project-registry.json. Project paths are replaced with anonymous aliases (project-001, project-002).
Data collectionAfter each /wrap, anonymized metrics (Vibe Score, agent usage, token counts, cost) are appended to telemetry/aggregate.json in the plugin directory.
Aggregation/system-review reads all registered projects' telemetry to compute cross-project trends: average scores, most-used agents, cost patterns, MCP adoption rates.

What /system-review Shows

SectionWhat It Contains
Score TrendsAverage Vibe Score trajectory across all projects — are you getting better over time?
Agent UsageWhich agents are used most, which are underutilized, and cost breakdown by agent.
Cost AnalysisPer-project and aggregate cost metrics. Identifies expensive patterns and cost-saving opportunities.
MCP AdoptionWhich MCP servers are active across projects and their impact on session efficiency.
Ecosystem ResearchThe System Reviewer agent checks for VibeCrew updates, new MCP servers, and community best practices.

Structured Expertise Accumulation

Session Learnings in CLAUDE.md are limited to 15 entries and use simple oldest-out pruning. Structured Expertise replaces this flat list with a typed, tiered knowledge base stored as JSONL records in .vibecrew/expertise/. Every convention discovered, pattern learned, failure debugged, and decision made is captured as a structured record that survives across sessions.

Record Types

TypePurposeExample
conventionCoding standards and project-specific patterns"Always use named exports in this project"
patternReusable solutions that worked well"Wrap Supabase calls in a retry helper with exponential backoff"
failureMistakes made and how they were fixed"Forgot to invalidate React Query cache after mutation — always call invalidateQueries"
decisionArchitectural choices and their rationale"Chose server actions over API routes for form submissions — simpler error handling"
referenceExternal docs, APIs, or resources worth remembering"Stripe webhook signature verification: docs.stripe.com/webhooks/signatures"
guideStep-by-step procedures for recurring tasks"Database migration checklist: schema → types → seed → test"

Tiered Pruning

Records are assigned to one of three tiers based on importance. When the expertise store grows large, pruning removes lower-tier records first while preserving critical knowledge.

TierPruning PriorityWhat Belongs Here
FoundationalLast to be prunedCore conventions, architectural decisions, critical failure lessons
TacticalPruned after observationalPatterns, references, and guides that are useful but replaceable
ObservationalFirst to be prunedMinor notes, one-off observations, low-impact findings

Session Learnings Regeneration

The Session Learnings section in CLAUDE.md is no longer manually curated. Instead, expertise-sync-learnings.sh automatically regenerates it from the top 15 foundational records in the expertise store. This means CLAUDE.md always contains the most important knowledge, and the full history lives in the JSONL files.

Scripts

ScriptPurpose
expertise-write.shAppend a new typed record to the expertise store
expertise-read.shQuery records by type, tier, or keyword
expertise-prime.shLoad relevant expertise into agent context at session start
expertise-compact.shRun tiered pruning to keep the store lean
expertise-migrate.shConvert legacy Session Learnings into typed records
expertise-sync-learnings.shRegenerate CLAUDE.md Session Learnings from top 15 foundational records
expertise-update.shModify an existing record (change tier, update content)
✓
Backward compatible

Existing projects with plain-text Session Learnings continue to work. Run expertise-migrate.sh to convert them into structured records. The migration is non-destructive — it reads CLAUDE.md and creates JSONL records without modifying the original file until you run expertise-sync-learnings.sh.

Agent Drift Detection (Circuit Breakers)

Agents sometimes lose focus — exploring tangential code paths, reading unrelated files, or looping on research when they should be writing code. Drift detection catches this automatically using a two-hook circuit breaker system that tracks every tool call and enforces per-phase exploration limits.

How It Works

ComponentHook TypeWhat It Does
drift-tracker.shPostToolUseClassifies every tool call as progress (advancing the task), exploration (reading, searching, researching), or neutral (formatting, navigation). Updates running totals in .vibecrew/drift-tracker.json.
drift-circuit-breaker.shStopAfter each agent turn, checks exploration ratio against per-phase thresholds. Issues a warning at the soft limit and escalates at the hard limit.

Per-Phase Thresholds

Each development phase has different expectations for how much exploration is acceptable. Planning naturally involves more reading than coding does. Thresholds are expressed as percentages of total tool calls that are classified as exploration.

PhaseSoft Limit (warning)Hard Limit (escalation)Rationale
Plan40%60%Planning requires research, but should converge on a spec
Design30%50%UI design references are expected, but most work is creative output
Code20%35%Coding should be mostly writes — exploration indicates confusion
Test25%40%Test setup needs some exploration; excessive reading suggests unclear specs
ReviewSKIPCode review is inherently exploratory — no limits applied
Docs25%40%Doc writing may reference code, but should be mostly generation
⚠
Tier 1 (foundation) is exempt

Drift detection is disabled during Tier 1 foundation setup. Foundation work is inherently exploratory — researching tech stacks, interviewing users for design preferences, and generating architecture diagrams. Circuit breakers only activate during Tier 2 feature development.

State Tracking

Drift state is stored in .vibecrew/drift-tracker.json and is ephemeral — it resets at the start of each session. The file tracks per-phase tool call counts (progress, exploration, neutral), current warning level, and escalation history. Vibe Score deductions are applied during /wrap based on the escalation count.

Code Erosion Tracking

Code quality degrades gradually. Files grow longer, functions accumulate complexity, dependencies multiply, and hot files get patched repeatedly without refactoring. Code erosion tracking measures this drift with heuristic-based metrics collected automatically during /wrap, producing an erosion score from 0 to 100.

Metrics Collected

MetricWhat It MeasuresErosion Signal
LOC per fileLines of code in each source fileFiles over 300 LOC suggest the file is doing too much
Cyclomatic complexityNumber of independent paths through a functionComplexity above 10 makes functions hard to test and reason about
Function lengthLines of code per functionFunctions over 50 LOC should be decomposed
Import countNumber of import statements per fileHigh import counts indicate excessive coupling
Dependency countTotal package.json dependenciesSpikes of more than 3 new dependencies in one session warrant review
File churnNumber of sessions that modified each fileFiles changed 5+ times without /simplify are accumulating debt

Erosion Score

The erosion score starts at 100 (pristine) and applies deductions based on the metrics above. It provides a single number that tracks codebase health over time.

Trend Tracking

Erosion scores are recorded after every /wrap and stored in .vibecrew/erosion/trends.json as a rolling 20-session window. The Performance Coach uses these trends to detect whether erosion is improving, stable, or worsening. A downward trend across 3+ sessions triggers a CLAUDE.md mutation proposal suggesting proactive simplification.

■
Erosion vs. Vibe Score

The erosion score measures codebase health over time, while the Vibe Score measures session quality. They are complementary: a session can score well (clean process, all phases complete) but still produce code that increases erosion. The erosion metrics feed into the Vibe Score as deductions and bonuses, connecting the two systems.

The Self-Improvement Loop

Every session feeds back into the system, making the next session more efficient. The loop runs automatically during /wrap — no manual intervention required.

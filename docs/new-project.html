New Projects

Using VibeOS with New Projects

New projects follow the Two-Tier Workflow. Tier 1 creates the architectural foundation. Tier 2 builds features on top of it. The phase gate enforces this order — you cannot write source code until the foundation is complete.

Tier 1: The Project Foundation

Run /new-project to start a guided, 6-step process. Each step produces a concrete artifact before the next begins.

  1. VISION.md — Define project goals

    VibeOS asks: What problem does this solve? Who are the target users? What's the value proposition? What are the constraints? What does success look like?

    The output is VISION.md — a document every agent reads. When the Feature Developer writes code, it knows who your users are. When the Stack Scout evaluates technologies, it factors in your constraints.

  2. design-system.css — Establish visual identity

    The UI Designer agent asks about your brand preferences: primary color, font, border radius, density. It generates a complete set of CSS custom properties (colors, typography, spacing, radii) that every component will use. No hardcoded values, ever.

  3. TDR — Research and lock the tech stack

    The Stack Scout agent activates. This is a read-only research agent that runs in an isolated context window. It uses WebSearch, Context7, and Puppeteer to evaluate technology options against your requirements, then produces a Technology Decision Record at docs/tdr-001-tech-stack.md.

    The TDR documents what was considered, what was chosen, and why. Once approved, every agent works within these boundaries. The research costs 8,000–15,000 tokens but none of them touch your main session — only the distilled decision enters your context window.

    Step 3.5: Opponent Processor — Immediately after the TDR, VibeOS invokes the Opponent Processor agent to stress-test every technology decision. You see both the TDR and the counter-analysis side by side, then choose: keep all decisions, reconsider specific ones, or skip. See Opponent Processor for details.

  4. Roadmap — Map out features

    List your planned features in rough priority order. VibeOS generates docs/roadmap.md with priority tiers (Must Have, Should Have, Nice to Have, Out of Scope). This becomes the input for /plan-features later.

  5. CLAUDE.md — Codify project rules

    VibeOS synthesizes everything into the master rules file. It includes your tech stack, architecture conventions, design system reference, and a "Session Learnings" section that the Performance Coach populates over time. This is the first file Claude Code reads every session.

  6. Git commit — Version the foundation

    Everything is committed: git commit -m "plan: project foundation". The phase gate unlocks. Source code writes are now allowed.

The Phase Gate

Until all 6 steps are complete, a PreToolUse hook blocks all writes to source directories (src/, app/, lib/, components/). Configuration files (.vibeos/, CLAUDE.md, docs/) are allowed. This is enforced by phase-gate.sh — it's a hard block, not a suggestion.

Tier 2: Building Features

With the foundation in place, you enter the iterative feature loop.

Planning the backlog

Run /plan-features to create structured specifications for each feature: name, description, acceptance criteria, priority, complexity (S/M/L/XL), and dependencies. These are stored in .vibeos/backlog.json.

Starting a feature

claude code/new-feature "user authentication"

This creates a feature branch (feat/user-authentication), initializes 5-phase tracking, and loads the feature spec. You're now in the development loop.

The 5-phase cycle

Plan → UI Design → Code → Test → Docs Phases can be worked in any order. Completeness is checked at /wrap, not during work.

Plan

Feature spec with acceptance criteria, edge cases, and technical notes at docs/features/<name>.md.

UI Design

Component hierarchy, props, variants. Uses design system tokens. Mobile-first, WCAG AA compliant.

Code

Implementation within TDR boundaries. Checks Context7 before using any library API. Follows CLAUDE.md conventions.

Test

TDD-hybrid: spec tests for business logic (written first), implementation tests for UI (written after). Tests behavior, not implementation.

Docs

Feature documentation, CHANGELOG entries, session logs. Structured JSON for the companion dashboard.

Wrapping a session

claude code/wrap

Checks completeness, runs the quality gate (tests + build + lint), triggers the Performance Coach for your Vibe Score, logs the session, and creates a conventional commit. Never close the terminal without wrapping.

Automated execution

claude code/run-backlog

Automatically picks the next planned feature by priority, executes it through Plan → Design → Code → Test, runs the quality gate, and loops. Stops on failure so you can fix and resume.

Phase gate blocks when it shouldn't

  1. Check .vibeos/state.json — is project_foundation.status set to "complete"?
  2. If any foundation step is null, run /new-project to complete the missing steps
  3. The phase gate allows writes to config paths (.vibeos/, CLAUDE.md, docs/). If a legitimate config file is blocked, check the path patterns in phase-gate.sh

Philosophy

Design Principles

Every architectural decision in VibeCrew follows these principles. Understanding them explains why the system works the way it does. These aren't just technical choices — they're the philosophy behind VibeCrew. If you ever wonder "why does it work this way?", the answer is usually one of these principles.

■

Fail-open design

All scripts exit 0 on error. A failing hook script never blocks your session — it silently degrades. The system reports the problem but lets you keep working. Sessions are too expensive to block with infrastructure issues.

■

Hooks over suggestions

Rules are enforced via deterministic bash scripts (zero tokens) rather than relying on the model to remember instructions. A hook that exits 2 physically blocks the operation. An instruction in CLAUDE.md can be forgotten or misinterpreted.

■

Atomic state mutations

All state mutations use the temp file + mv pattern. Scripts write to file.tmp, then mv file.tmp file.json. This prevents corruption from partial writes — critical when multiple agents may update state concurrently.

■

Advisory locking

Multi-agent state access uses mkdir-based advisory locks with 30–60 second timeouts. If a lock is stale (crashed process), error-recovery.sh cleans it up at session start. No deadlocks possible.

■

Research before code

The phase gate enforces architecture decisions (TDR) before any source code writes are allowed. The 15–30 minutes spent on the foundation prevents hours of rework from wrong assumptions.

■

Human attention is the bottleneck

The system stays completely silent during normal operation. It interrupts only when blocked, complete, or failed. Every notification is actionable — no noise, no status updates, no progress bars.

■

Context window discipline

Target <50% context usage. Worktree agents isolate expensive research. MCP servers replace pasting documentation. Warnings at 60% and 80%. Compaction reinject preserves project awareness.

■

Self-improving

Every session's Performance Coach analysis can permanently mutate CLAUDE.md rules. The system gets more efficient with every session. Mistakes are identified, codified, and prevented — recursively.

Dashboard

VitePress Documentation Dashboard

What is the dashboard?

The dashboard is a visual website that VibeCrew generates for your project. It turns all of your session data (scores, features, costs, agent activity) into charts, progress bars, and a kanban board. Think of it as a project management tool that builds itself automatically from your work. You can open it in your browser to see the big picture: how many features are done, how your quality scores are trending, which agents are doing the most work, and how your feature backlog is progressing. Teams find it especially useful for weekly retrospectives.

VibeCrew generates a VitePress-powered documentation site for every project. Beyond static docs, it includes 6 interactive Vue dashboard components that visualize cross-session data from .vibecrew/.

▲

ScoreTrend.vue

SVG line chart showing Vibe Score over the last 20 sessions with a trend indicator and target line at 80. Powered by scores.data.ts.

■

TokenBreakdown.vue

Stacked horizontal bars showing input, cache, and output tokens per session with cost overlay. Reveals cache utilization trends.

○

CoverageGauge.vue

SVG radial gauge displaying test coverage percentage with green/yellow/red color bands.

☰

FeatureProgress.vue

Horizontal bars showing features by Kanban column (planned, in-progress, done) with velocity metric calculated from session history.

⚙

SettingsPanel.vue

Interactive configuration editor with radio pills, toggles, and number inputs. Reads and writes .vibecrew/config.json including all user profile dimensions. Powered by config.data.ts.

⚙

AgentActivityPanel.vue

Agent invocation frequency bars and a session timeline with agent chips. Shows which agents are most active and their token consumption. Powered by agents.data.ts.

▶

KanbanBoard.vue

Interactive kanban view of the feature backlog from .vibecrew/backlog.json. Features move through columns as they progress through the Tier 2 cycle.

Meta

Cross-Project Telemetry

VibeCrew includes a cross-project telemetry system for self-improvement. Projects automatically register with the central plugin during /setup, contributing anonymized performance data.

How It Works

  1. Auto-Registration — During /setup, each project registers with the central VibeCrew plugin. An anonymous alias (project-001, project-002, etc.) replaces the real project path.
  2. Data Collection — The collect-telemetry.sh script reads .vibecrew/ data from all registered projects: Vibe Scores, agent usage, session costs, MCP adoption, test metrics, and mutation patterns.
  3. Aggregation — Anonymized data is aggregated into telemetry/aggregate.json at the plugin root.
  4. Analysis — The System Reviewer agent (via /system-review) analyzes the aggregate to identify cross-project patterns, unused components, and systemic friction.

Privacy

Telemetry is strictly local — no data leaves your machine. Project names, file paths, code, and credentials are never included. Only aggregate performance metrics are collected, keyed by anonymous aliases.

The /system-review Command

Run from the VibeCrew repository to trigger a comprehensive plugin audit:

  • Internal audit — model routing, context budgets, pattern consistency, unused components
  • Telemetry analysis — usage patterns, quality trends, cost analysis, systemic issues
  • External research — Anthropic updates, new MCP servers, community patterns
  • Proposals — prioritized improvement recommendations with effort estimates

Reports are saved to reviews/ in both markdown and JSON format.

Help

Troubleshooting

Stale locks or corrupted state

  1. Run ./scripts/error-recovery.sh to clear lock files and repair corrupted JSON
  2. This resets any in-progress tasks that were interrupted by a crashed session

Git conflicts in .vibecrew/

  • state.json: Resolve by keeping the most recent active feature
  • backlog.json: Merge the feature arrays
  • scores/ and sessions/: Rarely conflict — they're timestamped per-developer

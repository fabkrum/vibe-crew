How VibeCrew Gets Smarter

VibeCrew improves with every session through a recursive feedback loop. Unlike tools that reset to a blank slate, VibeCrew measures what happened, identifies patterns across sessions, proposes permanent rule changes, and transfers context to the next session — so the same mistakes never happen twice.

The system rests on four pillars:

▲

Vibe Score

Quantified measurement of every session. Starts at 100, applies deductions for anti-patterns and bonuses for best practices.

⚙

Performance Coach

Cross-session trend analysis that detects recurring anti-patterns and proposes permanent rule changes.

✎

CLAUDE.md Mutations

Approved rule proposals become permanent instructions in your project’s CLAUDE.md, read by every future agent.

⇄

Cross-Session Handoffs

Structured handoff documents, state files, and persistent memory transfer context between sessions.

Core Cycle

The Learning Loop

Every session participates in a recursive improvement cycle. What the system learns in session N directly improves behavior in session N+1:

Session Start → reads state.json + latest handoff + CLAUDE.md (with learned rules) ↓ Work phase — Tier 2 feature development (Plan → UI Design → Code → Test → Review → Docs) ↓ /wrap → Verifier runs quality checks (typecheck, lint, build, tests) ↓ Vibe Score calculated → saved to .vibecrew/scores/score-{timestamp}.json ↓ Performance Coach analyzes score against 3–5 session window ↓ Anti-pattern detection → checks if any pattern recurred across 3+ sessions ↓ Mutation proposal (if eligible) → presented for your approval ↓ Handoff document generated → saved to .vibecrew/handoffs/ ↓ Next session reads updated CLAUDE.md + handoff → better behavior
The recursive effect
Each loop iteration compounds. Session 1 establishes baselines. By session 5, the system has learned your project’s specific patterns — which test strategies work, which code paths cause issues, which conventions matter most.
Measurement

Vibe Score — Quantified Feedback

Every session produces a Vibe Score: a numerical measure of session quality that feeds the learning loop. The score starts at 100 and is adjusted by deductions (anti-patterns) and bonuses (best practices).

Key deductions

-5

Prompt Churn

Multiple clarification sequences that should have been resolved upfront in planning.

-10

Tool Loops

Repeated tool calls that don’t make progress — indicates the agent is stuck.

-15

Low Cache Utilization

Poor use of prompt caching, wasting tokens on repeated context.

-20

Context Violations

Exceeding context window thresholds, degrading response quality.

Key bonuses

+5

All Phases Complete

Every phase artifact present — spec, tests, code, review, docs.

+3

TDD Discipline

Tests written before implementation code, verified by commit order.

+3

Visual Compliance

No design-system token violations detected in the UI.

+2

Accessibility Clean

No accessibility issues found by automated checks.

Pattern Recognition

The Performance Coach

The Performance Coach is an Opus-powered agent that runs during /wrap to perform cross-session trend analysis. It doesn’t just look at the current session — it compares scores across a 3–5 session window to identify recurring anti-patterns that a single session can’t detect.

The 7-step mutation workflow

  1. Detection

    The coach reads the current Vibe Score and checks which deductions were applied.

  2. Correlation

    It cross-references with the previous 3–5 session scores stored in .vibecrew/scores/ and its persistent memory file.

  3. Eligibility check

    A mutation is only proposed if the same anti-pattern appeared in 3+ sessions within the analysis window.

  4. Proposal generation

    The coach drafts a concrete CLAUDE.md rule using its anti-pattern template library.

  5. Presentation

    The proposal is shown to you with context: which sessions triggered it, what the expected score improvement is, and the exact rule text.

  6. Decision

    You approve, reject, or modify the proposed rule. The coach records your decision.

  7. Recording

    Approved rules are appended to the “Session Learnings” section of your project’s CLAUDE.md. Rejections are logged and the pattern enters a 3-rejection cooldown.

Anti-pattern templates

The Performance Coach watches for six categories of recurring issues:

⟳

Tool Loops

Agent repeatedly calls the same tool without making progress. Rule: “If a tool fails twice with the same error, try a different approach.”

⚠

Context Bloat

Sessions consistently exceed context thresholds. Rule: “Use subagents for research tasks over 3 queries.”

📄

Missing Artifacts

Same phase artifact repeatedly missing. Rule: “Always create feature spec before implementation.”

📋

Test Gaps

Features shipped without tests across sessions. Rule: “Write tests before marking any feature as code-complete.”

📎

Documentation Drift

Docs consistently lag behind code changes. Rule: “Update feature documentation in the same session as code changes.”

$

Cost Spikes

Sessions repeatedly exceed cost thresholds. Rule: “Prefer Haiku for mechanical tasks; reserve Opus for analysis.”

Guardrails
The Performance Coach has strict limits to prevent runaway rule accumulation: mutations are never auto-applied (always require your approval), at most 1 mutation per session, a 3-rejection cooldown (won’t re-propose the same pattern after 3 rejections), and the Session Learnings section is capped at 15 rules.
Permanent Memory

CLAUDE.md Session Learnings

When you approve a Performance Coach mutation, the rule is appended to a dedicated “Session Learnings” section in your project’s CLAUDE.md. Because every agent reads CLAUDE.md at session start, these rules become permanent behavioral changes — the system literally cannot forget them.

The recursive loop

Session N: Performance Coach detects recurring tool loops ↓ Proposes rule: “If a tool fails twice with the same error, try a different approach” ↓ You approve → rule appended to CLAUDE.md Session Learnings ↓ Session N+1: All agents read updated CLAUDE.md ↓ Builder agent encounters a failing tool → switches approach after 2 failures instead of looping ↓ Vibe Score improves → tool loop deduction no longer applies

What it looks like

## Session Learnings

- Always run `npm run typecheck` before committing — 3 sessions had late-caught type errors (2026-02-15)
- Use subagents for file searches spanning more than 3 directories — context bloat in sessions 12-14 (2026-02-18)
- Write API integration tests before frontend components that depend on them (2026-02-20)
- Update architecture diagrams when adding new database tables — missed in sessions 17-19 (2026-02-25)

Auto-pruning

The Session Learnings section is capped at 15 rules. When a new rule is added and the count exceeds 15, the oldest rule is automatically removed. This prevents CLAUDE.md from growing unbounded and keeps only the most recent and relevant learnings.

Monthly curation
Review your Session Learnings monthly. Remove rules for patterns you’ve outgrown, and promote critical rules to your project’s main CLAUDE.md conventions section so they become permanent fixtures rather than prunable learnings.
Persistence

Cross-Session Data Transfer

Beyond CLAUDE.md mutations, VibeCrew transfers context between sessions through multiple channels:

Handoff documents

Every /wrap generates a structured handoff document saved to .vibecrew/handoffs/. The next session’s Session Startup agent reads the latest handoff to understand what was accomplished, what’s pending, and any known issues.

Handoffs include: features completed, current backlog position, open blockers, test status, branch state, and recommended next actions.

State persistence

Two JSON files survive across sessions and provide continuity:

  • state.json — Foundation status, active feature, current phase within the Tier 2 cycle
  • backlog.json — Feature backlog with specs, priorities, and completion status

On session start, sync-state.sh validates these files and repairs any corruption from interrupted sessions.

Context compaction

When /compact runs (manually or automatically during /run-backlog), the compact-reinject.sh hook re-injects fewer than 300 tokens of critical state: current feature, phase, active branch, and architecture diagram references. This gives the compressed context window just enough to continue seamlessly.

Error recovery

On every session start, error-recovery.sh cleans up stale state from interrupted sessions: releases advisory locks, detects orphaned processes, repairs inconsistent git state, and resolves signal file conflicts.

Performance Coach memory

The Performance Coach maintains a persistent MEMORY.md file with anti-pattern history, mutation decisions, score trends, and cross-session observations. This file is read at the start of every /wrap analysis, giving the coach continuity that doesn’t depend on the conversation context window.

Data flow between sessions

Session N ends (/wrap) ↓ Generates: score-{ts}.json + handoff-{ts}.json + session-{ts}.json Updates: state.json + backlog.json + CLAUDE.md (if mutation approved) ↓ --- session boundary --- ↓ Session N+1 starts ↓ session-startup.sh → environment check sync-state.sh → validates state.json + backlog.json error-recovery.sh → cleans stale locks, orphaned processes ↓ Session Startup agent reads: state.json + latest handoff + CLAUDE.md ↓ Routing decision: resume in-progress feature, start next backlog item, or await instructions
Ecosystem

Cross-Project Learning

Learning isn’t limited to a single project. When you use VibeCrew across multiple projects, the /system-review command aggregates anonymized performance data to identify patterns at the plugin level.

The System Reviewer agent analyzes:

  • Vibe Score trends across projects — are some project types consistently lower-scoring?
  • Agent usage patterns — which agents are used most, which are underutilized?
  • Cost distribution — how costs break down across agents and project types
  • MCP server adoption — which MCP integrations provide the most value?

All data is anonymized: project paths and names are replaced with aliases (project-001, project-002). Telemetry is stored locally at ${CLAUDE_PLUGIN_ROOT}/telemetry/aggregate.json.

Best Practices

Practical Tips

✓

Always /wrap

End every session with /wrap. This is what triggers the Vibe Score calculation, Performance Coach analysis, and handoff generation. Without it, the session’s learnings are lost.

📋

Review CLAUDE.md monthly

Curate your Session Learnings section. Remove rules that no longer apply, and promote universally-valuable rules to your main conventions section.

⚙

Trust the coach

The Performance Coach only proposes a mutation when it detects a pattern across 3+ sessions. If it suggests something, the data backs it up. Give proposed rules a fair trial.

▶

Use /replay for proven patterns

When a session scores 90+, capture it as a workflow template with /replay --create. Future features can reuse the proven approach, compounding the learning effect.

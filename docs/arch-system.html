Architecture

System Deep Dive

VibeCrew is a system of specialized agents, deterministic hooks, and bash scripts that work together to enforce quality, manage attention, and continuously improve your workflow. Here's how every piece fits together.

New to coding? Start here
This page explains how VibeCrew works under the hood. You don't need to understand all of this to use VibeCrew — just type the slash commands and the system handles the rest. But if you're curious about what's happening behind the scenes, or want to troubleshoot an issue, this page has the answers. Each section starts with a plain-English explanation before diving into technical details.

Plugin Manifest & Registration

What is a plugin?
A plugin is an add-on that gives Claude Code new abilities. Think of it like installing an app on your phone — your phone works fine without it, but the app adds features. VibeCrew is a plugin that adds project management, quality enforcement, and specialized AI agents to Claude Code. When you open a project with VibeCrew installed, Claude Code reads a small configuration file and automatically loads all the extra features.

VibeCrew is a Claude Code plugin. Claude Code auto-detects it from the .claude-plugin/plugin.json manifest in the project root. The manifest registers all system components:

plugin.json{
  "name": "vibe-crew",
  "version": "1.3.0",
  "description": "Autonomous vibe-coding operating system",
  "agents": "./agents/",
  "skills": "./skills/",
  "hooks": "./hooks/hooks.json",
  "mcpServers": "./.mcp.json"
}
■

agents/

13 specialized agent prompt files. Each defines a model, isolation type, tool allowlist, and turn budget. Claude Code spawns them on demand.

▶

skills/

20 slash command definitions. Each is a SKILL.md file with YAML frontmatter that registers the command name, description, and arguments.

⚙

hooks/

Event-to-script routing table. 10 hook matchers across 6 lifecycle events, triggering bash scripts for zero-token enforcement.

◉

.mcp.json + mcp-registry.json

MCP server configuration. 10 bundled servers in .mcp.json (3 enabled by default, 7 conditionally enabled from TDR). A registry of 25 servers in templates/mcp-registry.json enables discovery and injection of additional servers (Firebase, Clerk, MongoDB, etc.) based on TDR technology choices.

Plugin file structure

layoutclaude-plugin-vibe-crew/
  .claude-plugin/plugin.json    # Plugin manifest (entry point)
  .mcp.json                     # MCP server configuration
  settings.json                 # Permission rules (66 allowed, 22 denied)
  hooks/hooks.json              # Event-to-script routing table
  scripts/                      # ~67 bash automation scripts
  agents/                       # 14 specialized agent prompts
  skills/                       # 26 slash command definitions
  templates/                    # Badge catalog, challenge pool, quizzes, docs-site

The 14-Agent Architecture

What are agents?

Think of agents as specialist team members, each with a specific job. Instead of one AI doing everything, VibeCrew splits work across 14 agents — just like a real development team has designers, builders, testers, and reviewers. Each agent is an AI "personality" optimized for one task. The Builder writes code. The Verifier runs tests. The Security Auditor checks for vulnerabilities. You never interact with agents directly — VibeCrew picks the right one for each job automatically.

Inline vs. Worktree: Some agents work directly in your project folder ("inline") — like a colleague sitting at your desk. Others work in a worktree, which is an isolated copy of your project files. Think of it as giving that specialist their own private office with a photocopy of all your documents. They can read, analyze, and write without affecting your real files. When they're done, only the finished result comes back to you. This isolation also saves your AI "memory" (context window) — all of their research stays in their office, not yours.

Each agent has a specific role, model selection, tool access, and context budget. Opus agents handle planning, research, code, security, and analysis — tasks where mistakes are expensive to fix later. Haiku agents handle fast, mechanical tasks (routing, running shell commands). Sonnet handles template-driven output like documentation.

Why isolated agents matter
Agents marked "Worktree" run in separate context windows. All their research tokens, documentation fetches, and analysis stay outside your main session. Only the distilled output enters your primary context — saving thousands of tokens per session.

Skills System (Slash Commands)

What are slash commands?
Slash commands are the buttons you press to make VibeCrew do things. You type a command starting with / (like /new-project or /wrap) and VibeCrew handles the rest. Each command triggers a specific workflow — some are simple (like /idea which just saves a note) and some are complex (like /new-project which orchestrates multiple agents over 6 steps). You don't need to know how they work internally, just what they do and when to use them.

Every slash command in VibeCrew is implemented as a skill — a SKILL.md file in the skills/ directory. Skills are the primary user-facing interface to the system.

How skills work

User types: /new-feature "user-auth" ↓ Claude Code discovers skills/new-feature/SKILL.md ↓ Reads YAML frontmatter: name: new-feature description: Start a new feature args: feature_name ↓ Expands SKILL.md body as agent instructions ↓ Skill executes: precondition checks, state mutations, agent handoffs ↓ Results written to .vibecrew/ state files

Skill definition format

Each skill is a Markdown file with YAML frontmatter. The body contains the full workflow: preconditions, step-by-step execution, error handling, state mutations, and agent handoffs.

skills/new-feature/SKILL.md---
name: new-feature
description: Start a new feature session on a dedicated branch
args: feature_name
---

# /new-feature workflow

1. Check foundation is complete (read state.json)
2. Check WIP limits (max 2 in-progress features)
3. Find or create feature in backlog.json
4. Create git branch: feat/{feature_name}
5. Create safety checkpoint
6. Initialize 6-phase tracking in state.json
7. Hand off to Builder agent

Script-only skills vs. agent-driven skills
Some skills (like /idea, /status, /cost) are pure script execution — they read/write JSON files and produce output with zero AI token cost. Others (like /new-project, /wrap) orchestrate multiple agents across the full workflow. The distinction keeps costs down: cheap operations stay cheap.

The Hook System

What are hooks?
Hooks are automatic safety checks that run behind the scenes. Imagine a building with security guards at every door — when someone (an AI agent) tries to walk through (write a file, run a command), the guard (hook) checks if they're allowed. If yes, they pass through. If no, they're blocked with a clear message explaining why. Hooks are small programs that run instantly and cost nothing — they don't use any AI processing power. They're the reason VibeCrew can enforce rules like "no source code before the foundation is complete" without you having to remember or check yourself.

Hooks are the enforcement layer. They run as bash scripts triggered by Claude Code lifecycle events. Because they're shell scripts, they consume zero AI context tokens — the most efficient enforcement mechanism possible.

Hook EventScript(s)When It FiresWhat It Does
SessionStart session-startup.sh, sync-state.sh, error-recovery.sh Every Claude Code start Environment check, state reconciliation, clear stale locks
SessionStart (compact) compact-reinject.sh After context compaction Re-injects project state after context compaction
PreToolUse (Write/Edit) phase-gate.sh, restrict-paths.sh Before any file write Blocks source writes before foundation; validates write targets
PreToolUse (Bash) protect-data.sh Before any shell command Blocks destructive operations (rm -rf, DROP TABLE, force push)
PostToolUse (Write/Edit) format-code.sh After every file write Auto-formats with Prettier, Black, rustfmt, gofmt
Notification notify.sh Permission blocked or task complete Sends native OS notification with Warp deep-link
PostToolUseFailure notify.sh error Any tool execution fails Sends error notification
Stop check-context.sh, cost-guardrails.sh, claude-md-lint.sh, quality-gate.sh Session ending Context warnings, cost threshold checks, CLAUDE.md validation, typecheck/lint/build on modified files

How hooks enforce behavior

When Claude Code encounters a lifecycle event, it checks hooks.json for matching entries, passes a JSON payload to the script via stdin, and reads the exit code. Exit 0 = allow the operation. Exit 2 = block the operation. This gives hooks the power to both observe (PostToolUse) and control (PreToolUse) agent behavior.

Scripts Reference

What are scripts?
Scripts are the worker bees of VibeCrew. While agents think and make decisions, scripts do the actual mechanical work: creating files, updating project state, calculating scores, sending notifications. They're small programs that run in milliseconds and always produce the same result for the same input. This makes VibeCrew predictable and reliable — the creative AI work is separated from the bookkeeping, so nothing gets lost or corrupted.

VibeCrew includes ~67 bash scripts in the scripts/ directory. Every state mutation goes through a script — agents never write .vibecrew/ files directly. Scripts are organized by function:

Settings & Permissions

What are permissions?
Permissions control what the AI is and isn't allowed to do on your computer. VibeCrew pre-configures a list of safe operations (reading files, running tests, creating branches) and explicitly blocks dangerous ones (deleting everything, overwriting important data, installing system-wide software). This means the AI can work productively without asking you for permission every 5 seconds, while being physically unable to do anything destructive. It's like giving a contractor a key to the workshop but not the safe.

The settings.json file defines tool-level permission rules enforced by Claude Code before any hook runs. This is the outermost security boundary.

Allowed tools (66 rules)

Standard development operations are pre-approved so the agent can work without constant permission prompts:

  • File operations — All Read, Write, Edit, Glob, Grep
  • npm scripts — test, lint, build, format, type-check, audit
  • Git operations — status, log, diff, add, commit, checkout, branch, worktree, revert, reset --soft, tags
  • GitHub CLI — pr create/list/view, run list/view/watch; GitLab CLI — mr create/list/view, pipeline list/view
  • Shell utilities — jq, cat, ls, wc, sort, head, tail, mkdir, cp, mv
  • Security audits — npm audit, pip audit, bundle audit, govulncheck, cargo audit, composer audit

Denied tools (22 rules)

Destructive operations are blocked at the permission layer — even if an agent tries to run them:

⚠

Elevation

sudo, su, doas, pkexec

⚠

Force operations

git push --force, git push -f, git reset --hard, git clean -f

⚠

Destructive

rm -rf /, rm -rf ~, rm -rf $HOME, chmod 777

⚠

System modifications

npm install -g, kill -9, systemctl, crontab, mkfs, dd

Two layers of protection
The settings.json permission rules are the first layer (enforced by Claude Code). The protect-data.sh PreToolUse hook is the second layer (catches patterns like DROP TABLE that aren't tool-level commands). Together they form a defense-in-depth system.

Mermaid Architecture Diagram System

The 6th foundation artifact is a set of 5 Mermaid diagrams stored in .vibecrew/architecture/. They give agents a compact visual architecture reference at a fraction of the token cost of reading full-text documents.

FileMermaid SyntaxContent
system.mmdflowchart TDInfrastructure topology with service boundaries

state-flows.mmdstateDiagram-v2Authentication states and primary user journeys
api-sequences.mmdsequenceDiagramAPI request/response patterns
component-tree.mmdflowchart TDComponent hierarchy with data flow direction

Lifecycle: Generated during Tier 1 (Step 5) from VISION.md + TDR + roadmap. At the start of each Tier 2 feature, the Workflow Orchestrator runs inject-architecture.sh to pre-load all 5 diagrams into context as a compressed architecture map. This gives every downstream agent instant architectural awareness without each loading diagrams independently. Updated during Tier 2 by the Builder (component-tree.mmd) and Doc Generator (all diagrams, during /wrap). The Code Reviewer checks diagram consistency as a warning-level finding.

Token savings: All 5 diagrams total ~250–600 tokens, compared to the TDR alone (2,000–5,000 tokens). Pre-loading them once via inject-architecture.sh eliminates redundant file reads across agents and enables faster, more accurate responses to architecture questions.

MCP Server Integration

What are MCP servers?
MCP servers are external tools that give the AI extra abilities. Normally, the AI can only read your files and run commands. MCP servers connect it to additional services — like a reference library (Context7, for looking up documentation) or a web browser (Chrome DevTools, for visiting websites and debugging). They're optional: VibeCrew works fine without them, but with them, the AI works faster and uses less of its "memory" because it can look things up on demand instead of trying to remember everything.

Nine MCP (Model Context Protocol) servers extend the agent's capabilities. Three ship enabled by default; six are conditionally enabled when the TDR selects matching technologies.

Always Enabled (no auth required)

◉

Context7

Documentation lookup. Instead of pasting library docs into chat (~1,500 tokens per paste), agents query Context7 for on-demand API references. Used by the Builder, Stack Scout, and Verifier.

◉

Chrome DevTools

Browser debugging and automation. The Stack Scout uses it for web research and screenshot verification during TDR creation.

◉

Playwright

Interactive E2E testing. The Verifier uses it for browser debugging, selector exploration, and visual verification during E2E test development. Use npx playwright test for running full suites.

Conditionally Enabled (auto-enabled from TDR)

◉

Semgrep

Static security analysis. Augments the Security Auditor's manual OWASP scanning with pattern-based vulnerability detection across large codebases. No auth required.

◉

Sentry

Production error context. The CI Healer queries Sentry for stack traces and error frequency to enrich CI failure diagnosis. Requires SENTRY_AUTH_TOKEN.

◉

Supabase

Database schema inspection. Stack Scout and Builder use it for schema inspection, migrations, and seed data. Never use against production. Requires SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY.

◉

Stripe

Payment product management. Builder uses it for creating products, prices, and verifying webhook configurations. Always use test mode keys. Requires STRIPE_SECRET_KEY.

◉

Vercel

Deployment management. Builder uses it for project configuration, deployment status, and environment variable inspection. Requires VERCEL_TOKEN.

◉

Figma

Design spec extraction. Builder uses it to extract design specifications, spacing values, and component structures from Figma files. Requires FIGMA_ACCESS_TOKEN.

Servers are toggled via scripts/enable-mcp-server.sh <name> [enable|disable]. After TDR approval, scripts/sync-mcp-from-tdr.sh auto-enables bundled servers and recommends additional servers from the registry. Run scripts/recommend-mcp-servers.sh to see recommendations, or scripts/add-mcp-server.sh <key> to add a server from the registry (Firebase, Prisma, Clerk, Auth0, Netlify, Railway, Shopify, MongoDB, Resend, Next.js, shadcn/ui, Terraform, Kubernetes, Neon, Upstash Redis).

Token savings from Context7
A single session might query Supabase auth docs, Next.js routing docs, and Tailwind utility references. Without Context7, that's ~4,500 tokens of pasted documentation. With Context7, the agent fetches exactly what it needs on demand — and those tokens are served from the MCP server, not your context window. The Performance Coach tracks this and deducts points (-15) for low cache utilization when Context7 isn't being used.
MCP Tool Search (automatic)
Claude Code's built-in Tool Search (January 2026) dynamically loads only 3–5 relevant tool definitions per task instead of preloading all MCP tools into context. It activates automatically when combined tool definitions exceed 10% of the context window. For VibeCrew projects that enable 5+ servers after TDR selection, this prevents tool definitions from consuming context — reducing overhead from ~60K tokens to ~8.5K. VibeCrew's “disabled by default, enable from TDR” pattern complements this: baseline projects start with only 3 servers, and Tool Search handles the scaling.

The Problem

Why VibeOS Exists

AI-assisted development — "vibe coding" — has changed how software gets built. A single developer can now ship at the pace of a small team. But scaling this workflow reveals three critical problems that VibeOS was designed to eliminate.

⚠

The Attention Bottleneck

When you run 5–15 concurrent Claude Code sessions, finished or blocked agents wait silently. You manually poll tabs to find which session needs you, destroying your focus every time. Your most valuable resource — your attention — is wasted on hunting.

■

Token Waste & Context Exhaustion

Pasting docs into chat (+1,500 tokens), correcting vague prompts (+500 each), re-explaining context after /clear (+2,000). When the context window fills, you lose all accumulated understanding and start from zero.

⚙

Code Without Architecture

Jump straight into code and the AI picks the wrong state library, uses incompatible API patterns, and generates components that ignore your design system. You catch it three features in, when technical debt has compounded.

How VibeOS Solves Each One

→

The Interrupt Protocol

The terminal stays silent during normal work. When an agent needs you (permission blocked, task complete, critical error), it sends a native OS notification with a one-click deep link to the exact tab. You never poll again.

→

The Performance Coach

Every session ends with a Vibe Score (0–100). The coach identifies token waste, proposes a concrete CLAUDE.md rule to prevent it, and — with your approval — permanently writes that rule. Each session is more efficient than the last.

→

The Two-Tier Workflow

A phase gate blocks all source code writes until the project foundation is complete: vision, design system, tech stack decision, roadmap, and project rules. Architecture decisions are deliberate, not accidental.

The Core Philosophy

Human attention is the bottleneck, not AI speed. VibeOS is designed to maximize your focus time by minimizing interruptions, enforcing architecture before code, and turning every session into a learning opportunity.

Step-by-Step Installation

  1. Install system dependencies

    These are needed for notifications, JSON parsing in hooks, and PR automation.

    bashbrew install terminal-notifier jq
brew install gh && gh auth login

  2. Add the plugin to your project

    Copy or symlink the VibeOS plugin directory into your project root. Symlinking is recommended for teams so updates propagate automatically.

    bash# Option A: Direct copy
cp -r /path/to/claude-plugin-vibe-os/ ./claude-plugin-vibe-os/

# Option B: Symlink (recommended for teams)
ln -s /path/to/claude-plugin-vibe-os ./claude-plugin-vibe-os

# Option C: Git submodule (best for version control)
git submodule add <repo-url> claude-plugin-vibe-os

  3. Verify plugin detection

    Start Claude Code in your project directory. It reads the .claude-plugin/plugin.json manifest and loads VibeOS automatically.

    bashcd /path/to/your-project
claude

    You should see the VibeOS session startup agent run on first launch.

  4. Run the setup wizard

    Inside Claude Code, run:

    claude code/setup

    The wizard walks you through terminal selection, notification testing, MCP server verification, git checks, and creates the .vibeos/ runtime directory.

  5. Install MCP servers (optional but recommended)

    Context7 saves ~1,500 tokens per API lookup by fetching documentation on-demand instead of pasting it into chat. Puppeteer enables browser automation for research and visual testing. Both are configured in mcp-servers.json.

  6. Verify the full pipeline

    • Notifications: Tested during setup wizard
    • Session startup: Exit and restart Claude Code — the startup agent should show a 3-line status summary
    • Phase gate: Try writing a source file before running /new-project — it should be blocked

Terminal Setup

Configuring Warp Terminal

Warp provides the best VibeOS experience thanks to its deep-link support. When a notification fires, you click it and land on the exact tab that needs your attention — no hunting through 15 open sessions.

Why Warp Is Recommended

TerminalNotification MethodTab Deep-Link
WarpOSC 777 + macOS bannerYes — click goes to exact tab
iTerm2OSC 9 + macOS bannerNo
VS Code TerminalmacOS bannerNo
Terminal.appmacOS bannerNo

How Deep-Linking Works

Warp exposes a WARP_SESSION_ID environment variable for each terminal tab. VibeOS captures this value and constructs a warp://session/<id> URI. When the notify.sh script fires a notification, it passes this URI to terminal-notifier's -execute flag. Clicking the macOS banner executes the deep link, which brings Warp to the foreground and switches to the exact tab.

Agent blocks on permission ↓ notify.sh reads JSON from stdin, extracts notification_type ↓ Captures $WARP_SESSION_ID from environment ↓ Constructs deep link: warp://session/$SESSION_ID ↓ Dispatches via terminal-notifier -execute "open '$DEEP_LINK'" ↓ You click the notification → Warp focuses the exact tab

Setup Steps for Warp

  1. Install Warp

    Download from warp.dev and complete the initial setup. Warp runs on macOS and Linux.

  2. Enable desktop notifications in Warp

    Open Warp Settings → Features → ensure Desktop Notifications is enabled.

  3. Verify WARP_SESSION_ID

    In any Warp tab, run:

    bashecho $WARP_SESSION_ID

    This should return a UUID. If it's empty, update Warp to the latest version.

  4. Allow macOS notifications

    Go to System Settings → Notifications → terminal-notifier and ensure "Allow Notifications" is on. Set the alert style to Banners or Alerts.

  5. Select Warp during /setup

    When the VibeOS setup wizard asks "Which terminal do you use?", select Warp. This is stored in .vibeos/config.json and determines how notifications are dispatched.

  6. Test the full loop

    The setup wizard sends a test notification. Click it — you should be taken back to the exact Warp tab where Claude Code is running.

Using a different terminal?

VibeOS works with any terminal. You'll get macOS banner notifications regardless. The only difference is that non-Warp terminals can't deep-link to a specific tab — clicking the notification brings the terminal app to focus but you'll need to find the tab manually.

New Projects

Using VibeOS with New Projects

New projects follow the Two-Tier Workflow. Tier 1 creates the architectural foundation. Tier 2 builds features on top of it. The phase gate enforces this order — you cannot write source code until the foundation is complete.

Tier 1: The Project Foundation

Run /new-project to start a guided, 6-step process. Each step produces a concrete artifact before the next begins.

  1. VISION.md — Define project goals

    VibeOS asks: What problem does this solve? Who are the target users? What's the value proposition? What are the constraints? What does success look like?

    The output is VISION.md — a document every agent reads. When the Feature Developer writes code, it knows who your users are. When the Stack Scout evaluates technologies, it factors in your constraints.

  2. design-system.css — Establish visual identity

    The UI Designer agent asks about your brand preferences: primary color, font, border radius, density. It generates a complete set of CSS custom properties (colors, typography, spacing, radii) that every component will use. No hardcoded values, ever.

  3. TDR — Research and lock the tech stack

    The Stack Scout agent activates. This is a read-only research agent that runs in an isolated context window. It uses WebSearch, Context7, and Puppeteer to evaluate technology options against your requirements, then produces a Technology Decision Record at docs/tdr-001-tech-stack.md.

    The TDR documents what was considered, what was chosen, and why. Once approved, every agent works within these boundaries. The research costs 8,000–15,000 tokens but none of them touch your main session — only the distilled decision enters your context window.

    Step 3.5: Opponent Processor — Immediately after the TDR, VibeOS invokes the Opponent Processor agent to stress-test every technology decision. You see both the TDR and the counter-analysis side by side, then choose: keep all decisions, reconsider specific ones, or skip. See Opponent Processor for details.

  4. Roadmap — Map out features

    List your planned features in rough priority order. VibeOS generates docs/roadmap.md with priority tiers (Must Have, Should Have, Nice to Have, Out of Scope). This becomes the input for /plan-features later.

  5. CLAUDE.md — Codify project rules

    VibeOS synthesizes everything into the master rules file. It includes your tech stack, architecture conventions, design system reference, and a "Session Learnings" section that the Performance Coach populates over time. This is the first file Claude Code reads every session.

  6. Git commit — Version the foundation

    Everything is committed: git commit -m "plan: project foundation". The phase gate unlocks. Source code writes are now allowed.

The Phase Gate

Until all 6 steps are complete, a PreToolUse hook blocks all writes to source directories (src/, app/, lib/, components/). Configuration files (.vibeos/, CLAUDE.md, docs/) are allowed. This is enforced by phase-gate.sh — it's a hard block, not a suggestion.

Tier 2: Building Features

With the foundation in place, you enter the iterative feature loop.

Planning the backlog

Run /plan-features to create structured specifications for each feature: name, description, acceptance criteria, priority, complexity (S/M/L/XL), and dependencies. These are stored in .vibeos/backlog.json.

Starting a feature

claude code/new-feature "user authentication"

This creates a feature branch (feat/user-authentication), initializes 5-phase tracking, and loads the feature spec. You're now in the development loop.

The 5-phase cycle

Plan → UI Design → Code → Test → Docs Phases can be worked in any order. Completeness is checked at /wrap, not during work.

Plan

Feature spec with acceptance criteria, edge cases, and technical notes at docs/features/<name>.md.

UI Design

Component hierarchy, props, variants. Uses design system tokens. Mobile-first, WCAG AA compliant.

Code

Implementation within TDR boundaries. Checks Context7 before using any library API. Follows CLAUDE.md conventions.

Test

TDD-hybrid: spec tests for business logic (written first), implementation tests for UI (written after). Tests behavior, not implementation.

Docs

Feature documentation, CHANGELOG entries, session logs. Structured JSON for the companion dashboard.

Wrapping a session

claude code/wrap

Checks completeness, runs the quality gate (tests + build + lint), triggers the Performance Coach for your Vibe Score, logs the session, and creates a conventional commit. Never close the terminal without wrapping.

Automated execution

claude code/run-backlog

Automatically picks the next planned feature by priority, executes it through Plan → Design → Code → Test, runs the quality gate, and loops. Stops on failure so you can fix and resume.

Existing Projects

Using VibeOS with Existing Projects

VibeOS isn't only for greenfield work. Bringing it into an existing codebase provides structure, quality gates, and continuous improvement to projects that were started without this framework.

Onboarding an Existing Project

  1. Install the plugin

    Same process as a new project: copy or symlink claude-plugin-vibe-os/ into your project root, then run /setup inside Claude Code.

  2. Run /onboard

    The /onboard command launches the Code Auditor agent in a read-only worktree to analyze your codebase. It supports 7 languages (Node.js, Python, Ruby, Go, Rust, PHP, Java) and:

    • Detects language and framework — scans manifests (package.json, pyproject.toml, Gemfile, go.mod, Cargo.toml, etc.)
    • Extracts conventions — naming patterns, formatters, linters, commit format, import style
    • Identifies test gaps — compares source vs test files, finds untested modules, estimates coverage
    • Derives the design system — extracts existing CSS variables, colors, and spacing values via extract-design-system.sh
    • Generates CLAUDE.md — project-specific rules from discovered patterns, framework conventions, and architecture
    • Initializes state — sets foundation.complete = true so the phase gate is unlocked immediately

  3. Or run /new-project for full foundation

    Alternatively, when /new-project detects an existing codebase, it adapts the Tier 1 flow: the Stack Scout documents the stack as it exists (rather than researching from scratch), the design system is derived from existing CSS, and VISION.md is still generated from your input. This takes longer but produces all 5 foundation artifacts.

  4. Map existing features to the backlog

    Use /plan-features to document features that already exist (marked as "complete") and define new features you want to build. This gives you a unified backlog that includes both history and future work.

  5. Start developing with full VibeOS workflow

    From this point forward, every new feature uses the Tier 2 cycle. The phase gate is active, the Performance Coach runs at session end, and CLAUDE.md accumulates project-specific intelligence.

The phase gate and existing code

The phase gate only blocks new source code writes before the foundation is complete. Once you've completed the /new-project flow for your existing project, the gate unlocks and you can modify any file freely. Existing code is never touched or reformatted without your explicit instruction.

What You Get Immediately

  • Interrupt Protocol — native notifications for blocked agents, completed tasks, and errors
  • Safety hooks — protection against rm -rf, force pushes, and other destructive commands
  • Auto-formatting — every file the AI writes is formatted automatically via PostToolUse hooks
  • Context warnings — alerts at 60% and 80% context usage to prevent exhaustion
  • Cost tracking — real-time session cost via /cost with configurable spend limits
  • Status bar — persistent display of context %, cost, feature, Vibe Score, duration, and compactions
  • Security auditing — OWASP Top 10 scanning via /audit with language-specific dependency checks
  • Performance coaching — Vibe Scores and CLAUDE.md mutations from your first /wrap

Advanced Workflows

VibeOS v1.3.0 introduces four advanced workflows that extend the development lifecycle: reusable session templates, automated code simplification, self-healing CI, and adversarial review of technology decisions.

Workflow Templates (/replay)

Capture what worked and reuse it. /replay extracts reusable workflow templates from successful sessions (Vibe Score ≥ 70) so you can apply proven patterns to future features.

Three modes

☰

List templates

Run /replay with no arguments to list all saved workflow templates with their names, descriptions, and quality thresholds.

+

Create a template

Run /replay --create <name> to extract a template from the most recent high-scoring session. Captures phase order, branch conventions, test strategy, and quality thresholds.

▶

Apply a template

Run /replay <name> to load a template and have it guide your current feature development with the proven workflow.

When to create templates

After a session scores 90+, create a template. Common examples: "api-feature" for CRUD endpoints, "ui-component" for design-system-aligned components, "data-migration" for schema changes. Templates are stored in .vibeos/workflows/.

Code Simplification (/simplify)

After building a feature, run /simplify to get an Opus-powered analysis of your code for unnecessary complexity. The agent operates in a read-only worktree — it analyzes but never modifies your code directly.

The simplification cycle

/simplify collects files changed on the feature branch ↓ Launches the Code Simplifier agent (Opus, worktree, read-only) ↓ Agent analyzes four categories: Dead code · Abstraction flattening · API simplification · Dependency reduction ↓ Presents suggestions one at a time for your approval ↓ Each accepted change is applied and tests re-run If tests fail → automatic revert

Suggestions are categorized by impact (high, medium, low) and include before/after snippets, estimated line reduction, and confidence ratings. You approve or reject each individually. Reports are saved to .vibeos/simplifications/.

Safe by design

The analysis agent cannot write files. Only the /simplify skill applies approved changes in the main session, and every change is verified by running your test suite. Failed tests trigger an automatic revert.

Auto-Healing CI (/heal)

When CI fails, run /heal instead of manually debugging logs. The CI Healer fetches the failure logs from GitHub Actions, diagnoses the root cause, and applies targeted fixes — up to 3 attempts.

How it works

  1. Fetch and diagnose

    /heal runs gh run view --log-failed to retrieve the CI output, then pattern-matches errors to categorize the failure: build, test, lint, dependency, or environment.

  2. Checkpoint

    Before any fix, a git checkpoint is created so all changes can be reverted cleanly if the fix doesn't work.

  3. Fix loop (max 3 attempts)

    The CI Healer agent applies the minimum viable fix for the diagnosed failure, then pushes and waits for CI. If CI fails again, it re-diagnoses with the new context and tries a different approach.

  4. Report

    A heal report is saved to .vibeos/ci-heals/ documenting each attempt, diagnosis, fix, and outcome. If all 3 attempts fail, the healer escalates to you with a summary of what it tried.

Failure CategoryCommon PatternsFix Strategy
BuildTypeScript errors, missing imports, syntax errorsFix the type error or import at its source
TestAssertion failures, snapshot mismatches, timeoutsUpdate assertion/snapshot or fix the logic bug
LintESLint/Prettier violationsAuto-fix with the project's lint command
DependencyMissing packages, version conflictsInstall missing dep or resolve version conflict
EnvironmentMissing env vars, wrong Node version, permission errorsUpdate CI config (YAML/TOML) to match requirements

Opponent Processor (TDR Debate)

Every technology decision deserves a devil's advocate. During Tier 1, after the Stack Scout produces the TDR, VibeOS automatically invokes the Opponent Processor — a read-only agent that challenges every decision.

What it produces

✗

Counter-arguments

For each technology decision, the opponent generates 2–3 reasons why the choice might be wrong, citing real-world failure modes and edge cases.

⚖

Debate matrix

A structured comparison table scoring each option across 6 criteria: performance, DX, ecosystem, scalability, learning curve, and lock-in risk.

⚠

Risk assessment

Identifies the highest-risk decisions and recommends which ones deserve extra scrutiny or prototyping before committing.

After reviewing both the TDR and the counter-analysis, you choose: keep the original decisions, reconsider specific choices, or skip the review. The opponent's analysis is saved alongside the TDR for future reference.

Why adversarial review matters

The Stack Scout is optimized to find the best answer quickly. The Opponent Processor is optimized to find where that answer might break. Together, they produce more robust technology decisions than either could alone. This is especially valuable for decisions that are expensive to reverse (database choice, state management, auth provider).

Architecture

System Deep Dive

VibeOS is a system of specialized agents, deterministic hooks, and bash scripts that work together to enforce quality, manage attention, and continuously improve your workflow. Here's how every piece fits together.

The 12-Agent Architecture

Each agent has a specific role, model selection, tool access, and context budget. Haiku agents handle fast, routine tasks. Sonnet agents handle complex reasoning and implementation. One agent (Code Simplifier) uses Opus for deep analysis.

Why isolated agents matter

Agents marked "Worktree" run in separate context windows. All their research tokens, documentation fetches, and analysis stay outside your main session. Only the distilled output enters your primary context — saving thousands of tokens per session.

The Hook System

Hooks are the enforcement layer. They run as bash scripts triggered by Claude Code lifecycle events. Because they're shell scripts, they consume zero AI context tokens — the most efficient enforcement mechanism possible.

Hook EventScript(s)When It FiresWhat It Does
SessionStart session-startup.sh, sync-state.sh, error-recovery.sh Every Claude Code start Environment check, state reconciliation, clear stale locks
SessionStart (compact) compact-reinject.sh After context compaction Re-injects project state after context compaction
PreToolUse (Write/Edit) phase-gate.sh, restrict-paths.sh Before any file write Blocks source writes before foundation; validates write targets
PreToolUse (Bash) protect-data.sh Before any shell command Blocks destructive operations (rm -rf, DROP TABLE, force push)
PostToolUse (Write/Edit) format-code.sh After every file write Auto-formats with Prettier, Black, rustfmt, gofmt

How hooks enforce behavior

When Claude Code encounters a lifecycle event, it checks hooks.json for matching entries, passes a JSON payload to the script via stdin, and reads the exit code. Exit 0 = allow the operation. Exit 2 = block the operation. This gives hooks the power to both observe (PostToolUse) and control (PreToolUse) agent behavior.

Graceful degradation

If jq is missing, the status bar shows “VibeOS”. If .vibeos/ doesn’t exist, it shows “no project”. The script always exits 0 and is compatible with macOS Bash 3.2. Target execution time is under 50ms.

The Interrupt Protocol

The Interrupt Protocol is the "Attention Economy" architecture. The terminal stays completely silent during normal operation. Notifications fire only on three conditions:

!

Permission Stalls

permission_prompt — The agent needs Y/N approval. Execution is halted. Priority: Critical.

✔

Task Completion

idle_prompt — A complex operation finished. The agent is waiting for your next instruction. Priority: High.

⚠

Critical Failures

PostToolUseFailure — A tool returned a fatal exit code or compilation error that can't be resolved autonomously. Priority: High.

Everything else — standard tool execution, file reads, successful commands — is silent. Your Deep Work state is preserved.

The Phase Gate

The phase gate is the architectural enforcement mechanism. It runs as a PreToolUse hook on every Write and Edit operation.

phase-gate.sh receives JSON payload from Claude Code ↓ Reads .vibeos/state.json → checks project_foundation.status ↓ If "complete": exit 0 (allow all writes) If "incomplete": ↓ Check file path being written: .vibeos/, CLAUDE.md, VISION.md, docs/, design-system.css → exit 0 (foundation artifacts allowed) src/, app/, lib/, components/, etc. → exit 2 (BLOCKED)

When blocked, the developer sees a clear message listing which foundation steps remain incomplete and how to complete them.

The Vibe Score & Performance Coach

The Performance Coach runs at the end of every session (triggered by /wrap). It ingests the session transcript, calculates a Vibe Score, and initiates an interactive coaching dialogue.

How the score is calculated

Starting from 100, deductions are applied for detected anti-patterns:

Anti-PatternDeductionHow It's Detected
Prompt churn -5 per sequence 3+ consecutive corrective messages without a successful tool call
Tool loops -10 per loop Same tool call with identical arguments repeated 3+ times
Low cache utilization -15 cache_read_input_tokens < 20% of total input_tokens
Context violation -20 Significant work continued after the 80% context warning
No tests written -10 Feature has coding artifacts but no test artifacts
No feature spec -5 Coding started without a plan artifact

Bonuses (up to +10): +5 for all 5 phases having artifacts, +5 for cache utilization above 50%.

Score RangeRatingMeaning
90–100ExcellentEfficient, well-structured session
75–89GoodMinor inefficiencies
60–74Needs ImprovementNotable token waste
Below 60Review SessionSignificant anti-patterns detected

The coaching dialogue

After calculating the score, the Performance Coach:

  1. Presents the score with the single biggest observation: "Vibe Score: 82/100. You pasted API docs 3 times (~4,500 tokens). Using Context7 MCP would have saved those tokens."
  2. Asks for feedback: "How did this session feel? Any friction points?"
  3. Proposes a CLAUDE.md rule: "Proposed rule: Always use Context7 for Dexie.js API docs. Add this? (y/n)"
  4. Mutates CLAUDE.md if approved — the rule is permanent and active from the next session onwards.
The recursive improvement loop

Session 1: paste docs, score 78, rule added. Session 2: AI reads rule, uses Context7, score 89, new rule proposed. Session 3: two rules active, score 94. Each session is more efficient than the last. Mistakes are identified, codified, and permanently prevented.

Safety Hooks

Three layers of protection run as PreToolUse hooks, blocking operations before they execute:

■

protect-data.sh

Blocks destructive bash commands: rm -rf, git push --force, DROP TABLE, sudo, kill -9, chmod 777, and more. 18 denied tool patterns in settings.json.

■

phase-gate.sh

Blocks source code writes (src/, app/, lib/, components/) until all Tier 1 foundation artifacts exist. Allows config and docs writes always.

■

restrict-paths.sh

Validates that write targets are within the project directory and match allowed path patterns. Prevents accidental writes to system files or other projects.

Permission rules

settings.json defines 71+ permission rules: 53 allowed tool patterns (npm, git, gh, jq, standard dev tools) and 18 denied patterns (sudo, force push, hard reset, kill -9, mkfs, dd). These are enforced at the Claude Code level before any hook runs.

Checkpoint safety net

Both /heal and /new-feature create a git checkpoint (vibeos-checkpoint-<timestamp>) before making changes. If anything goes wrong, /undo can roll back to any checkpoint. Checkpoints are lightweight git tags that don’t add repository overhead.

Progression

Gamification System

VibeOS includes a persistent progression layer that motivates across sessions and teaches vibe-coding skills over time. Built on three principles: artifacts over actions (rewards map to real outputs), teaching over tracking (every mechanic helps you improve), and sustainable over addictive (grace periods, opt-in challenges, no toxic leaderboards).

The gamification system uses the existing Vibe Score as its primary data source. Every metric flows from real work artifacts — shipped features, passing tests, clean sessions — not arbitrary actions.

How it integrates

The gamification pipeline runs automatically at the end of every /wrap. Six scripts execute sequentially: award XP, check badges, update streak, distribute skill XP, update challenges, and check level-ups. The /achievements command shows a compact CLI summary, and the VitePress dashboard provides the full visual experience.

Streaks

Streaks track consecutive days of coding, designed to be encouraging rather than punitive.

  • Increment on calendar days where /wrap is run
  • Weekend auto-grace: Saturdays and Sundays don’t break streaks and don’t consume grace credits
  • 2 grace days/month: Missing one weekday preserves the streak (resets on the 1st)
  • No penalty for broken streaks — the counter resets to 0 but no XP is lost
  • Streak reminders are opt-in (disabled by default in config.json)
Sustainable by design

The weekend auto-grace and monthly grace days ensure that taking time off doesn’t feel punishing. The system celebrates consistency without demanding it — a broken streak is just a number, not a loss.

Best Practices

Maximizing Efficiency

VibeOS is designed to make each session more efficient than the last. Here's how to get the most out of the system and why each practice matters.

Context Window Discipline

VibeOS targets <50% context usage per session. Three mechanisms enforce this automatically:

60%

Warning at 60%

check-context.sh emits a warning. Start thinking about wrapping up. Commit working code.

80%

Critical at 80%

Stronger warning. Commit and run /wrap. Consider delegating remaining work to a sub-agent.

90%

Danger at 90%

Agent quality severely degraded. Immediately run /wrap. Do not attempt complex operations.

When context compaction occurs, compact-reinject.sh automatically re-injects the current project state, active feature, and phase — so you don’t lose context on what you were working on.

Token Efficiency

Use Context7 for everything

This is consistently the single biggest token saver. Every time you paste documentation into chat, you burn ~1,500 tokens that Context7 could fetch on-demand. The Performance Coach will flag this — listen to it.

Write clear initial prompts

Prompt churn (-5 points each) comes from vague instructions. Spend 30 seconds writing a precise prompt instead of 3 follow-up corrections. The first prompt is the cheapest prompt.

Respect context warnings

At 60%: start thinking about wrapping. At 80%: definitely wrap. Pushing to 100% forces a /clear and loses all accumulated understanding. A fresh context + CLAUDE.md = fast restart.

Let agents run in isolation

Stack Scout, Builder, and Code Simplifier run in separate worktree context windows. Don’t duplicate their work in the main session. Their research tokens never touch your context.

Workflow Efficiency

Always /wrap

Never close the terminal without wrapping. The session log feeds the learning system, the commit preserves your work, and the Vibe Score identifies improvements. Skipping /wrap means the session is invisible.

Use /idea aggressively

Mid-feature inspiration should be captured, not pursued. /idea takes 1 second and produces 1 line of output. The idea is safe in the backlog. Your flow is preserved.

Trust the phase gate

It feels restrictive at first. But the 15–30 minutes spent on the foundation prevents hours of rework from wrong architectural assumptions. Every seasoned VibeOS user says the same thing: "I'm glad it forced me to plan."

Review CLAUDE.md monthly

Remove stale rules, consolidate duplicates, promote critical rules to the top. The Performance Coach adds rules — you curate them. A well-maintained CLAUDE.md is the most powerful file in your project.

For Teams

  • One person owns the foundation. The project lead runs /new-project and establishes the TDR. Don't debate architecture in separate sessions.
  • Share the backlog. Use /plan-features as a team exercise. Commit backlog.json so everyone works from the same list.
  • Commit Vibe Scores. Make scores visible to the team — not as competition, but as a shared learning signal for retrospectives.
  • Standardize on Warp. The deep-link notifications are worth it when running parallel sessions across a team.
  • Do score retros. Even 15 minutes every two weeks reviewing score trends and adding team rules to CLAUDE.md compounds into massive efficiency gains.
Help

Troubleshooting

Notifications don't appear

  1. Test terminal-notifier directly: terminal-notifier -message "test"
  2. If nothing appears, reinstall: brew install terminal-notifier
  3. Check macOS: System Settings → Notifications → terminal-notifier → Allow Notifications
  4. Check VibeOS config: verify .vibeos/config.json has "notifications": true
  5. Warp deep-links not working: run echo $WARP_SESSION_ID — should return a UUID

Phase gate blocks when it shouldn't

  1. Check .vibeos/state.json — is project_foundation.status set to "complete"?
  2. If any foundation step is null, run /new-project to complete the missing steps
  3. The phase gate allows writes to config paths (.vibeos/, CLAUDE.md, docs/). If a legitimate config file is blocked, check the path patterns in phase-gate.sh

MCP servers not available

  1. Context7: Verify it's configured in your Claude Code settings. Try a test query
  2. Puppeteer: Ensure the Puppeteer MCP server is running and configured
  3. Both are optional. VibeOS works without them — you just miss the token efficiency benefits

Vibe Score seems inaccurate

  • New projects: Scores are less meaningful in the first few sessions as the system establishes baselines
  • Complex features: Large features naturally have more tool calls and corrections — the score accounts for this but may seem low
  • Override deductions: If the coach flags something unavoidable, say so during the coaching dialogue — it factors into the next proposal

/heal can't fetch CI logs

  1. Verify GitHub CLI is authenticated: gh auth status
  2. Ensure the repo has a remote: git remote -v
  3. Check that a recent CI run exists: gh run list --limit 5
  4. If the failure is on a different branch, switch to it first

/simplify shows no suggestions

  • The agent only analyzes files changed on the current feature branch vs. the default branch
  • Verify you're on a feature branch (not main/master): git branch --show-current
  • Check that source files were changed (config and docs are excluded)
  • The minimum files threshold is configurable in .vibeos/config.json under simplify.min_files_for_analysis

/replay can't find eligible sessions

  • Only sessions with a Vibe Score ≥ 70 are eligible for template extraction
  • Verify session logs exist in .vibeos/sessions/ and score files in .vibeos/scores/
  • Run /wrap at the end of sessions to generate the required data

Gamification not showing after /wrap

  1. Check that gamification is enabled: jq '.gamification.enabled' .vibeos/config.json should return true
  2. Verify .vibeos/gamification.json exists. If not, run /setup to create it
  3. Check that the gamification scripts are executable: ls -la scripts/award-xp.sh
  4. Run a script manually to debug: bash scripts/award-xp.sh — it outputs JSON with the XP breakdown

/quiz shows "Unlocks at Level 3"

  • The /quiz command requires Level 3 (approximately 3–4 completed sessions)
  • Check your level: jq '.level' .vibeos/gamification.json
  • Keep running /wrap at the end of sessions to earn XP and level up

Streak broke unexpectedly

  • Streaks increment on calendar days where /wrap runs. If you didn’t wrap, the day doesn’t count
  • Weekends never break streaks. Check if you missed a weekday
  • Grace days reset on the 1st of each month: jq '.streak.grace_days_remaining' .vibeos/gamification.json
  • If the streak counter seems wrong, check .streak.last_session_date in gamification.json

Stale locks or corrupted state

  1. Run ./scripts/error-recovery.sh to clear lock files and repair corrupted JSON
  2. This resets any in-progress tasks that were interrupted by a crashed session

Git conflicts in .vibeos/

  • state.json: Resolve by keeping the most recent active feature
  • backlog.json: Merge the feature arrays
  • scores/ and sessions/: Rarely conflict — they're timestamped per-developer

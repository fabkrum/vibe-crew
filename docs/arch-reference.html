State Management

What is state management?
State is VibeCrew's memory between sessions. It remembers what features you've planned, which ones are done, your quality scores, session history, and configuration preferences. All of this is stored in a folder called .vibecrew/ inside your project. Unlike the AI's conversation memory (which resets every session), these files persist forever. They're plain JSON files — human-readable text — so you can always open them and see exactly what VibeCrew knows about your project.

All VibeCrew runtime state lives in .vibecrew/:

File / DirectoryPurposeUpdated By
config.jsonTerminal preference, notification settings, feature toggles, user profile/setup, /profile
state.jsonFoundation status + active feature + active workflow + phase trackingAll commands
backlog.jsonFeature backlog with specs, priorities, dependencies/plan-features, /idea, /run-backlog
gamification.jsonXP, level, badges, skill tree, streaks, challenges, quiz progress/wrap (gamification pipeline)
mutation-log.jsonCLAUDE.md mutation audit log with timestamps and diffsPerformance Coach
sessions/*.jsonSession logs with phase data and token metrics/wrap
scores/*.jsonVibe Score breakdowns with deductions and bonusesPerformance Coach
releases/*.jsonRelease notes dataDoc Generator
handoffs/*.mdCross-session context transfer documents/handoff, /wrap
workflows/*.jsonReusable workflow templates from high-scoring sessions/replay --create
simplifications/*.jsonCode simplification reports with per-suggestion status/simplify
ci-heals/*.jsonCI heal reports documenting diagnosis and fix attempts/heal

Git strategy for .vibecrew/

  • Solo developer: Commit everything — preserves session history across machines
  • Teams: Commit state.json, backlog.json, and scores/. Gitignore config.json (terminal-specific)
  • Sensitive projects: Add .vibecrew/ to .gitignore entirely

State schema migration

When VibeCrew is upgraded, scripts/migrate-state.sh automatically detects the current schema version and applies incremental migrations (1.0.0 → 1.1.0 → 1.2.0 → 1.3.0). New fields are added with sensible defaults. No manual migration is needed.

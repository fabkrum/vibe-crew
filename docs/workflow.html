Getting Started

A Normal Workday

Once your project foundation is in place, daily development follows a simple rhythm. Here's the mental model before diving into each use case.

Review PRs → Plan features → Build (manual or autonomous) → Monitor dashboard → Wrap up Repeat. Each feature gets its own session and branch.

Morning: Merge yesterday's PRs. Check /status for open work. Mid-day: Build features — one at a time with /new-feature, or let /run-backlog handle multiple autonomously. End of day: /wrap every session, review Vibe Scores, capture stray ideas with /idea.

The rest of this page covers each part in detail.

Use Case

Planning Features

"I have ideas and need to turn them into buildable specs."

/idea — instant capture

Ideas come at the worst times — mid-implementation, during testing, while reviewing code. Capture them instantly without losing flow. One line in, one line out, zero context consumed.

any tab> /idea "add dark mode toggle to settings page"
Added to backlog: "add dark mode toggle to settings page" (unplanned)

> /idea "export trip itinerary as PDF"
Added to backlog: "export trip itinerary as PDF" (unplanned)

> /idea "rate limiting on auth endpoints"
Added to backlog: "rate limiting on auth endpoints" (unplanned)

Ideas land in .vibecrew/backlog.json with status "unplanned". They sit there until your next planning session.

/plan-features — structured specs

When you've accumulated several ideas, run /plan-features to promote them to structured specs. VibeCrew reads your roadmap and walks through each feature. For each one, you provide or confirm:

  • Name and description — one sentence
  • Acceptance criteria — when is this feature "done"?
  • Priority — P0 (must have) through P3 (nice to have)
  • Complexity — S / M / L / XL
  • Dependencies — which features must exist first?
Planning session$ claude
VibeCrew v1.8.0 | Foundation: complete | No active feature
Ready. 5 features in roadmap, 0 planned.

> /plan-features

The output is .vibecrew/backlog.json — a structured file that /new-feature and /run-backlog read to determine what to build next.

backlog.json (excerpt){
  "features": [
    {
      "id": "user-auth",
      "name": "User Authentication",
      "priority": "P0",
      "complexity": "M",
      "status": "planned",
      "acceptance_criteria": [
        "Users can sign up with email/password",
        "Users can sign in with Google OAuth",
        "Protected routes redirect to login",
        "Session persists across page refresh"
      ],
      "dependencies": []
    },
    {
      "id": "trip-creation",
      "name": "Trip Creation",
      "priority": "P0",
      "complexity": "M",
      "status": "planned",
      "dependencies": ["user-auth"]
    }
  ]
}
Planning session> /wrap
Vibe Score: 92/100
5 features planned. Backlog ready for /new-feature or /run-backlog.

Weekly planning ritual

Every week, ideas accumulate via /idea. Process them before they become a graveyard of forgotten thoughts.

Every Friday (or Monday morning): 1. Run /status to see the full picture 2. Run /plan-features to promote unplanned ideas to specs 3. Review Vibe Score trends — are scores going up or down? 4. Review CLAUDE.md rules added by Performance Coach 5. Merge any remaining PRs 6. /wrap to close the week Total: ~30 minutes. Sets up the entire next week.
Use Case

Building a Single Feature

"I want to build one feature with full control."

/new-feature "name" creates a feature branch and initializes 6-phase tracking. Each feature passes through: Plan → UI Design → Code → Test → Review → Docs. Here's a complete walkthrough building "User Authentication".

Starting the feature

Development$ claude
VibeCrew v1.8.0 | Foundation: complete | No active feature
Next in backlog: user-auth (P0, M complexity)

> /new-feature "user-auth"

Key rules

One feature per session. Each Claude Code session has a finite context window. Cramming two features into one means both get less attention and lower Vibe Scores. Commit at phase boundaries. Each phase completion is a natural commit point — if something goes wrong later, you can roll back to the last clean phase. Use /check mid-session to run the full quality gate (build, tests, lint, types) without wrapping up.

Use Case

Running the Backlog Autonomously

"I want VibeCrew to build multiple features while I do other things."

/run-backlog automates the full 6-phase cycle for each feature in your backlog. It picks up the next planned feature, builds it through all phases, wraps it, and moves to the next one.

Development> /run-backlog
Starting autonomous backlog run.
3 features queued: trip-creation, itinerary-builder, group-invites
Building: trip-creation...

Inter-feature context hygiene

Between features, VibeCrew forces a /compact to prevent context degradation across long autonomous runs. Each feature starts with a clean context window, ensuring the Builder agent doesn't confuse Trip Creation's patterns with Group Invites' requirements.

When to use /run-backlog vs /new-feature

/run-backlog

Features are well-specced with clear acceptance criteria. You trust VibeCrew to make implementation decisions. You want to batch-build multiple features while you do other work.

/new-feature

The feature needs creative direction or nuanced decisions. You want to guide each phase. You're learning the workflow and want to see each step.

What to expect

VibeCrew notifies you on three conditions only: permission prompts (a tool needs approval), task completion (a feature finished), and critical failures (something broke). Everything else runs silently. You'll get a native OS notification for each — click it to jump directly to the session.

Use Case

Working in Parallel with Warp

"I want to plan ahead while a feature builds."

VibeCrew is designed for parallel work across multiple terminal panes. Each project gets its own Warp tab with three split panes.

Left — Planning
claude /plan-features, /idea /status, /check, /cost
Right top — Development
claude Building: user-auth Code phase active
Right bottom — Terminal
npm run dev Local server running http://localhost:3000

Left: Planning

Your primary focus. /plan-features to refine upcoming specs, /idea to capture thoughts, /status to check progress, /check to run quality gates.

Right top: Development

The one in-progress feature moves through the 6 phases here. Guide decisions, review output, run /wrap when done.

Right bottom: Terminal

A raw shell for npm run dev, git commands, manual tests, or quick file browsing. Not a Claude Code session.

How a multi-pane session flows

9:00 Development pane: /new-feature "trip-creation" Terminal pane: npm run dev 9:05 Development: You guide the Plan phase for trip-creation. Planning: /plan-features — refine the itinerary-builder spec. 9:25 Development: Code phase starts. Builder agent working. Planning: /idea "add map view to itinerary with Mapbox" 9:30 Notification: "Development pane — Code phase complete." You review the code, start the Test phase. 9:45 Development: All phases done. /wrap → Score 88 WIP slot is now free. 9:46 Development: /new-feature "itinerary-builder" Spec is already polished from earlier planning — Plan phase is fast. 10:15 Development: /wrap → Score 85 Two features shipped in ~75 minutes.
WIP limit of 1

Only one feature can be in-progress at a time. This is enforced at multiple levels: state.json tracks a single active feature, backlog.json limits the in-progress column to 1, and claim-task.sh blocks new claims. This prevents merge conflicts, keeps context focused, and produces higher Vibe Scores.

How notifications keep this manageable

You don't need to watch all panes. The Interrupt Protocol sends a native OS notification when any session needs you (permission prompt, task complete, or error). Click the notification to jump directly to that pane. Work in your Planning pane until you're interrupted — that's the whole system.

For Warp installation, launch configurations, and keyboard shortcuts, see the Warp Integration page.

Use Case

Multi-Project Development

"I'm working on 2+ projects simultaneously."

Each project gets its own Warp tab with the same 3-pane layout. Color-code tabs so you can identify projects at a glance.

  • CMD+1 through CMD+8 to jump between projects
  • Opt+CMD+Arrow to move between panes within a tab
Each pane is an independent Claude Code session

Every pane with Claude Code runs its own context window. They share the filesystem (git branches, .vibecrew/ state, CLAUDE.md) but not conversation history. This is by design — planning in one pane doesn't consume context in the development pane. Coordinate between sessions via branches: each feature gets its own branch.

Use Case

Monitoring Performance

"I want to check how my sessions are going."

Vibe Dashboard

A browser-based metrics dashboard showing your Kanban board, Vibe Score trends, and session logbook. Launch it with:

Terminal$ bash scripts/start-dashboard.sh

The dashboard shows feature status (backlog/in-progress/done), score trends over time, and detailed session logs. See the Dashboard page for a full tab-by-tab reference.

/status — quick CLI check

For a quick look without leaving the terminal:

any tab> /status

Open PRs:
  #12 feat/user-auth        — approved, ready to merge
  #13 feat/trip-creation    — review requested, 2 days old
  #14 feat/itinerary-builder — draft, tests passing

Context usage: 42%
Features: 3/5 complete | Backlog: 2 planned, 4 ideas

Context budget

The check-context.sh hook warns at 45% and 60% context usage. Don't wait for the warning — check proactively with /status.

What happens at high context usage

Above 70%, Claude Code starts losing early conversation context. It may forget design decisions, repeat questions, or generate contradictory code. The rule: if you're past 60%, wrap up and start fresh. A new session with full context is always better than pushing a depleted one.

Vibe Score

Every session ends with a score (0–100) calculated from real work artifacts. Starts at 100, applies deductions for prompt churn, tool loops, low cache utilization, missing tests, skipped reviews, and documentation drift. Bonuses for clean sessions, high test coverage, TDD discipline, and complete phase artifacts. The Performance Coach proposes permanent CLAUDE.md rule mutations based on patterns it detects.

Putting It Together

A Full Week with VibeCrew

Here's what a productive week looks like building a travel planning SaaS called TripFlow from zero to a working MVP.

Monday: Foundation

1 tab, 1 session. Run /new-project. Complete all 6 foundation steps. Run /plan-features to spec out your first 5 features. End with /wrap. Total: ~45 min.

Tuesday: First features

1 tab, 2 sessions. Build user-auth in session 1. Build trip-creation in session 2. /wrap after each. Capture 3 ideas with /idea along the way. Total: ~2 hours.

Wednesday: Full 3-pane workflow

3 panes. Build itinerary-builder in Development while planning group-invites in Planning. Dev server running in Terminal. Once itinerary-builder wraps, start group-invites immediately — spec is already polished. Total: ~2 hours, 2 features.

Thursday: Final feature + cleanup

3 panes. Development: Build expense-splitting. Planning: Run /simplify on earlier features. Run /heal if CI has issues. Total: ~1.5 hours.

Friday: Polish + review

1 tab. Run /status. Review Vibe Score trends. Plan next week from captured ideas. Review and merge PRs. /wrap to close the week. Total: ~1 hour.

Week summary

Features shipped: 5 (user-auth, trip-creation, itinerary-builder, group-invites, expense-splitting) Sessions: 8 Average Vibe Score: 89 Ideas captured: 12 (ready for next week's /plan-features) CLAUDE.md rules: 3 new rules added by Performance Coach Total active time: ~8 hours across 5 days
The compounding effect

Week 2 is faster than Week 1. The 3 CLAUDE.md rules from this week prevent token waste next week. Your /replay templates capture what worked. The Performance Coach learns your patterns. By Week 4, you're shipping at nearly double the pace — not because you're working harder, but because the system is eliminating waste automatically.

Quick Reference

Best Practices

VibeCrew enforces many rules automatically through hooks, but some habits need to be built by you.

1. Always /wrap before closing a tab 2. One feature per session, no exceptions 3. Review & merge PRs before building more features 4. Wrap up at 60% context — don't push past it 5. Run /plan-features weekly to process ideas 6. Commit at every phase boundary 7. Keep .vibecrew/ in version control 8. Never build on main — always use feature branches 9. Resolve uncommitted changes before starting new work 10. Let Session Startup detect stale sessions
Most of these are enforced automatically

The phase gate blocks writes on main. Session Startup detects stale sessions and uncommitted changes. The context hook warns at 45% and 60%. /new-feature creates branches automatically. The habits above are about the few things only you can do — like remembering to /wrap and reviewing PRs.

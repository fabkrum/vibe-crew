Advanced Workflows

VibeCrew includes four advanced workflows that extend the development lifecycle: reusable session templates, automated code simplification, self-healing CI, and adversarial review of technology decisions.

Workflow Templates (/replay)

Capture what worked and reuse it. /replay extracts reusable workflow templates from successful sessions (Vibe Score ≥ 70) so you can apply proven patterns to future features.

Three modes

List templates

Run /replay with no arguments to list all saved workflow templates with their names, descriptions, and quality thresholds.

Create a template

Run /replay --create <name> to extract a template from the most recent high-scoring session. Captures phase order, branch conventions, test strategy, and quality thresholds.

Apply a template

Run /replay <name> to load a template and have it guide your current feature development with the proven workflow.

When to create templates
After a session scores 90+, create a template. Common examples: "api-feature" for CRUD endpoints, "ui-component" for design-system-aligned components, "data-migration" for schema changes. Templates are stored in .vibecrew/workflows/.

Code Simplification (/simplify)

After building a feature, run /simplify to get an Opus-powered analysis of your code for unnecessary complexity. The agent operates in a read-only worktree — it analyzes but never modifies your code directly.

The simplification cycle

/simplify collects files changed on the feature branch ↓ Launches the Code Simplifier agent (Opus, worktree, read-only) ↓ Agent analyzes four categories: Dead code · Abstraction flattening · API simplification · Dependency reduction ↓ Presents suggestions one at a time for your approval ↓ Each accepted change is applied and tests re-run If tests fail → automatic revert

Suggestions are categorized by impact (high, medium, low) and include before/after snippets, estimated line reduction, and confidence ratings. You approve or reject each individually. Reports are saved to .vibecrew/simplifications/.

Safe by design
The analysis agent cannot write files. Only the /simplify skill applies approved changes in the main session, and every change is verified by running your test suite. Failed tests trigger an automatic revert.

Auto-Healing CI (/heal)

When CI fails, run /heal instead of manually debugging logs. The CI Healer fetches the failure logs from GitHub Actions or GitLab CI pipelines, diagnoses the root cause, and applies targeted fixes — up to 3 attempts.

How it works

  1. Fetch and diagnose

    /heal runs gh run view --log-failed (GitHub) or glab ci view (GitLab) to retrieve the CI output, then pattern-matches errors to categorize the failure: build, test, lint, dependency, or environment.

  2. Checkpoint

    Before any fix, a git checkpoint is created so all changes can be reverted cleanly if the fix doesn't work.

  3. Fix loop (max 3 attempts)

    The CI Healer agent applies the minimum viable fix for the diagnosed failure, then pushes and waits for CI. If CI fails again, it re-diagnoses with the new context and tries a different approach.

  4. Report

    A heal report is saved to .vibecrew/ci-heals/ documenting each attempt, diagnosis, fix, and outcome. If all 3 attempts fail, the healer escalates to you with a summary of what it tried.

Failure CategoryCommon PatternsFix Strategy
BuildTypeScript errors, missing imports, syntax errorsFix the type error or import at its source
TestAssertion failures, snapshot mismatches, timeoutsUpdate assertion/snapshot or fix the logic bug
LintESLint/Prettier violationsAuto-fix with the project's lint command
DependencyMissing packages, version conflictsInstall missing dep or resolve version conflict
EnvironmentMissing env vars, wrong Node version, permission errorsUpdate CI config (YAML/TOML) to match requirements

Issue Tracker Integration (/fix-issue)

Connect GitHub Issues or GitLab Issues directly to VibeCrew’s development pipeline. Someone files a bug, a human labels it for auto-fix, and VibeCrew diagnoses, implements, tests, and opens a PR or MR — all autonomously. The provider is auto-detected from the git remote URL, with a config override in .vibecrew/config.json.

/fix-issue <number>

Interactive single-issue fix. Fetches the issue from GitHub or GitLab, imports it into the backlog, creates a branch, implements the fix with the Builder agent, runs quality checks, and opens a PR/MR with Fixes #N (or Closes #N on GitLab) for auto-close.

/sync-issues

Batch-import open issues by label (default: autofix) from GitHub or GitLab into the backlog. Zero token cost — pure bash. Then run /run-backlog to process them automatically.

CI Automation

Fully automated CI-triggered fixes. On GitHub, the github-actions-autofix.yml template triggers on issues.labeled events. On GitLab, the gitlab-ci-autofix.yml.template provides equivalent pipeline-triggered fixes. Both run Claude Code CLI headless and comment results back on the issue.

Hotfix vs Full Feature

Bug issues use a hotfix path (Code → Test → Review) that skips planning and design since bugs don’t need upfront design work. Issues labeled enhancement or feature-request, or those invoked with --full, use the standard 6-phase Tier 2 cycle.

Deduplication built in
The import script tracks issue_number on each backlog entry. Running /sync-issues multiple times or calling /fix-issue on an already-imported issue will detect the duplicate and offer to resume instead of creating a new entry.

Opponent Processor (TDR Debate)

Every technology decision deserves a devil's advocate. During Tier 1, after the Stack Scout produces the TDR, VibeCrew automatically invokes the Opponent Processor — a read-only agent that challenges every decision.

What it produces

Counter-arguments

For each technology decision, the opponent generates 2–3 reasons why the choice might be wrong, citing real-world failure modes and edge cases.

Debate matrix

A structured comparison table scoring each option across 6 criteria: performance, DX, ecosystem, scalability, learning curve, and lock-in risk.

Risk assessment

Identifies the highest-risk decisions and recommends which ones deserve extra scrutiny or prototyping before committing.

After reviewing both the TDR and the counter-analysis, you choose: keep the original decisions, reconsider specific choices, or skip the review. The opponent's analysis is saved alongside the TDR for future reference.

Why adversarial review matters
The Stack Scout is optimized to find the best answer quickly. The Opponent Processor is optimized to find where that answer might break. Together, they produce more robust technology decisions than either could alone. This is especially valuable for decisions that are expensive to reverse (database choice, state management, auth provider).

Inter-Feature Context Hygiene (/run-backlog)

When /run-backlog processes multiple features autonomously, stale conversation history from earlier features can degrade quality for later features. VibeCrew solves this with fresh-session Agent delegation.

Primary approach: Each feature's build phases (Plan→Test) are spawned as an Agent tool call with a completely fresh 200k context window. The prepare-feature-context.sh script assembles the feature spec, TDR, architecture diagrams, design system, CLAUDE.md, user profile, and codebase analysis docs into a structured prompt. The Agent runs in its own worktree, eliminating context rot entirely.

Fallback: If Agent delegation is unavailable, VibeCrew falls back to inline execution with /compact between features. This compresses stale history and fires compact-reinject.sh to re-inject fresh project state and architecture diagrams.

Impact on long autonomous runs
With fresh-session execution, feature 10 gets the exact same 200k context quality as feature 1. The orchestrating session only accumulates lightweight state management overhead. This is a significant improvement over compaction, which still carries summarized prior context. See Runtime State for the full technical flow.

Wave-Based Milestones (Complex Features)

Complex features with milestones can now declare dependencies between milestones via the depends_on field. Independent milestones are grouped into waves and executed in parallel.

Dependency Analysis

During the Plan phase, the Builder analyzes shared files and data flow between milestones to populate depends_on. Milestones sharing files or where one produces data another consumes must have explicit dependencies.

Wave Computation

compute-milestone-waves.sh performs topological sort to group milestones into waves. Wave 1 milestones have no dependencies and can run in parallel. Wave 2 depends on Wave 1, etc.

Parallel Execution

Independent milestones in a wave spawn parallel Agent calls, each with its own worktree and fresh context. After a wave completes, merge-milestone-branches.sh merges the results.

Safety Fallbacks

Cycle detection falls back to sequential. Merge conflicts are resolved by file ownership from estimated_files. If all milestones are linear, behavior is unchanged from sequential processing.

Structured Task Plans

Implementation plans now include a structured ## Tasks section alongside the existing free-form sections (Approach, Files, Component Strategy, etc.). Each task has explicit fields:

### Task 1: Create database schema
- Files: `prisma/schema.prisma` (modify)
- Action: Add User and Session models with email, password_hash, created_at
- Verify: `npx prisma validate`
- Done when: Schema validates without errors and includes both models

The Code phase extracts structured tasks via extract-plan-tasks.sh and processes them sequentially: implement the Action, run the Verify command, check the Done criteria, commit per task. Legacy plans without structured tasks fall back to free-form execution. Task count scales with complexity: 2-3 for trivial, 4-6 for standard, 6-8 per milestone for complex.

Plan Freshness Checks

When multiple features execute sequentially (especially during /run-backlog), earlier features may modify files that later features planned against. VibeCrew records the git SHA when each plan completes and checks for drift before the Code phase starts.

How it works:

  1. Plan phase completes → git SHA recorded in state.json
  2. Code phase starts → check-plan-staleness.sh diffs plan files against recorded SHA
  3. Severity determines response: proceed, review, or refresh affected tasks

Severity levels:

  • Minor (1–2 files, <20 lines): Re-read affected files, proceed
  • Major (3+ files or >50 lines): Refresh affected plan tasks
  • Critical (deleted/renamed files): Mandatory re-plan of affected tasks

Behavior adapts to your autonomy setting — full_auto refreshes silently, collaborative asks before refreshing, supervised shows full diffs.

Persistent Codebase Analysis

When you onboard an existing project with /onboard, VibeCrew generates 4 persistent analysis documents in .vibecrew/analysis/ that capture your codebase's stack, architecture, conventions, and gaps. These docs are auto-injected into every Plan phase and post-compaction context, eliminating the need to re-discover conventions each session.

stack.md

Language, framework, runtime, package manager, key dependencies, component library, database, deployment target.

architecture.md

Source directories, component organization, API routes, schema location, state management, error handling, auth approach.

conventions.md

Code style (quotes, semicolons, indent), formatter/linter, naming patterns, import style, commit format, test framework.

gaps.md

Source vs test file count, estimated coverage, untested modules (top 10), deprecated dependencies, TODO count.

Analysis docs are committed to git (not gitignored) and persist across sessions and team members. Staleness detection runs on session startup — if docs are >30 days old with >50 commits, or package.json changed, VibeCrew warns you. Refresh with /onboard --refresh (re-runs the auditor without re-generating CLAUDE.md or re-initializing state).

Cost & Safety

Cost Tracking & Safety

VibeCrew provides real-time cost visibility and multi-layered safety enforcement. Cost tracking runs at zero token cost via hook scripts, and safety hooks block destructive operations before they execute.

Cost Dashboard (/cost)

Run /cost at any time to see a complete financial picture of your AI usage.

Current Session

Live cost, turn count, model name, and last-updated timestamp. Read from .vibecrew/session-cost.json which is updated after every assistant turn.

Aggregates

Daily, weekly, monthly, and all-time totals calculated by aggregate-costs.sh from session log files in .vibecrew/sessions/.

Threshold Status

Visual progress bars showing proximity to session warning, session max, and daily warning limits. Configurable in .vibecrew/config.json.

Pricing Reference

Per-model pricing table for Opus, Sonnet, and Haiku showing input, cache write, cache read, and output costs per million tokens.

Cost Guardrails

The cost-guardrails.sh hook runs on every Stop event, calculating per-turn costs with model-aware pricing and accumulating totals in .vibecrew/session-cost.json. Alongside cost monitoring, the Stop hook also runs quality-gate.sh, which detects modified source files and runs typecheck/lint/build checks automatically. See Hooks for details.

ThresholdDefaultConfig KeyAction
Session Warning $2.00 cost_limits.session_warn_usd Emits a cost warning to the agent
Session Hard Limit $5.00 cost_limits.session_max_usd Agent MUST pause and ask for permission to continue
Daily Warning $20.00 cost_limits.daily_warn_usd Emits a daily spend warning

Daily totals are calculated by summing estimated_cost_usd from all session files matching today’s date, plus the live session cost. All thresholds are configurable in .vibecrew/config.json.

Safety Hooks

VibeCrew enforces safety through PreToolUse hooks (protect-data.sh, phase-gate.sh, restrict-paths.sh) and permission rules in settings.json. These block destructive commands, enforce foundation-before-code ordering, and restrict file writes to the project directory — all at zero token cost.

See the Permissions & Safety page for the full breakdown of hooks, permission rules, and enforcement layers.

Checkpoint safety net
Both /heal and /new-feature create a git checkpoint (vibecrew-checkpoint-<timestamp>) before making changes. If anything goes wrong, /undo can roll back to any checkpoint. Checkpoints are lightweight git tags that don’t add repository overhead.

Security Audit (/audit)

Run /audit to perform an OWASP Top 10 security analysis of your project. The Security Auditor agent operates in a read-only worktree — it analyzes your code but never modifies it.

What it checks

  • Injection vulnerabilities — SQL injection, command injection, XSS
  • Authentication & authorization — missing auth checks, insecure session handling
  • Secrets exposure — hardcoded API keys, tokens, credentials in source
  • Dependency vulnerabilities — runs language-specific audit tools (npm audit, pip audit, etc.)
  • Security headers & configuration — missing CORS, CSP, HSTS headers

Findings are categorized by severity (critical, high, medium, low) and saved to .vibecrew/. The audit adapts to your project's language — see Multi-Language Support for details.

More Commands

These commands cover specialized workflows. Each is a single slash command that orchestrates the right agent(s) and scripts.

/handoff

Generates a structured context transfer document capturing in-progress work, decisions made, and next steps. Use when context is running low or you need to continue in a new session.

/pause

Checkpoints the active feature: commits WIP changes, creates a pause handoff file, cleans up the worktree, and preserves the branch. Use when you need to switch context mid-feature.

/resume

Resumes a previously paused feature: restores state, recreates the worktree from the preserved branch, and continues at the paused phase. Session Startup auto-detects paused features.

/release

Automates version bumps, changelog generation from conventional commits, and release notes creation. The Doc Generator compiles a release summary from git history and session logs.

/tdd

Test-driven development workflow: write a failing test first, then implement until it passes, then refactor. The Verifier agent guides the red-green-refactor cycle.

/debug

Structured debugging with hypothesis testing. The Builder agent systematically isolates the issue, forms hypotheses, tests each one, and applies the fix.

/e2e

Generates Playwright end-to-end tests using the Page Object Model pattern. Tests cover user flows defined in the feature spec and run in real browsers.

/perf-test

Generates k6 performance test suites covering load, stress, spike, and soak scenarios. Establishes baselines for response times and throughput.

/a11y

Runs WCAG 2.1 AA accessibility scanning via axe-core. Reports violations by severity with fix suggestions. Contributes +2 to Vibe Score when clean.

While VibeCrew was designed with JavaScript/TypeScript projects in mind, it supports 7 languages for onboarding, convention detection, security auditing, and dependency scanning.

LanguageManifestFormatterLinterFramework DetectionDep Audit

Java pom.xml / build.gradle Checkstyle Checkstyle Spring Boot, Hibernate —

How language detection works

detect-conventions.sh scans project root for manifests ↓ Identifies language from: package.json, pyproject.toml, Gemfile, go.mod, Cargo.toml, composer.json, pom.xml ↓ extract-project-conventions.sh detects per-language: framework, ORM, auth library, API patterns, naming conventions ↓ Results feed into Code Auditor and CLAUDE.md generation

Where language support applies

  • /onboard — Code Auditor detects language, conventions, frameworks, and test gaps for all 7 languages
  • /audit — Security Auditor runs language-specific dependency audit tools and adapts OWASP scanning patterns
  • PostToolUse formatting — format-code.sh auto-formats with the correct tool: Prettier (JS/TS), Black (Python), rustfmt (Rust), gofmt (Go)
  • /new-project — Stack Scout research adapts to the detected or chosen language ecosystem
Non-Node.js confidence levels
Node.js/TypeScript projects receive “high” confidence from the Code Auditor due to deeper ecosystem integration. Other languages receive “medium” confidence — the core workflow (Tier 1 foundation, Tier 2 cycle, Vibe Score, hooks) works identically, but framework-specific patterns may need manual refinement in CLAUDE.md.

Parallel Backlog Execution

/run-backlog --parallel enables wave-based parallel processing of independent features. The system analyzes feature dependencies via analyze-feature-dependencies.sh and groups features into waves where no feature depends on another within the same wave.

AspectSequential (default)Parallel (--parallel)
ExecutionOne feature at a timeUp to N features per wave (default: 3)
DependenciesPriority orderWave-based: independent features grouped together
Quality gatePer featurePer wave (after merge)
Cost guardrailsPer featureMultiplied by concurrent agents per wave
Merge strategySequential on mainSequential merge between waves

How it works under the hood

Parallel features are not separate Claude Code sessions or terminal tabs. Each feature runs as a concurrent Agent tool call within the same parent orchestration session. Every Agent call gets its own fresh 200k context window and isolated git worktree — so features cannot interfere with each other's files or accumulate stale context.

The parent session stays lightweight: it manages wave ordering, monitors Agent completion, runs the quality gate after each wave merges, and advances to the next wave. The analyze-feature-dependencies.sh script performs a topological sort on the depends_on fields to compute which features can safely run in the same wave.

When to use parallel mode
Use --parallel when your backlog has 3+ features with few dependencies between them. For backlogs with chain dependencies (A→B→C), parallel mode adds no benefit and falls back to sequential.

Agent Overlay System

Customize any agent's behavior per-project by creating override files in .vibecrew/agent-overrides/<agent>.md. Override sections with matching ## Heading names replace the base section; new headings are appended. YAML frontmatter (model, tools, isolation) is always preserved from the base agent.

Overrides survive plugin updates because they live in your project, not the plugin. See the Personalization page for details.

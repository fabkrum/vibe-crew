Self-Improving System

VibeCrew doesn't just build software — it learns from every session. The Performance Coach analyzes each session's patterns, proposes permanent rule changes to CLAUDE.md, and aggregates anonymized metrics across all your projects. Each session makes the next one better.

■
What it is

A feedback loop: the Performance Coach scores each session, detects anti-patterns, and proposes CLAUDE.md mutations. Cross-project telemetry tracks trends across all your VibeCrew projects. The /system-review command analyzes the plugin's own performance.

✓
What problem it solves

AI agents make the same mistakes across sessions because they start fresh each time. The self-improving loop captures what went wrong (and right), encodes fixes as permanent CLAUDE.md rules, and tracks whether those fixes actually work over time.

Performance Coach

The Performance Coach is an Opus agent that runs during /wrap at the end of every session. It analyzes what happened during the session and produces actionable coaching.

What It Analyzes

DimensionWhat It ChecksExample Finding
Prompt Efficiency Prompt churn (repeated similar prompts), tool loops (same tool called 3+ times) "You re-prompted the Builder 4 times for the same component — next time, include acceptance criteria in the spec."
Cache Utilization Cache hit ratio across the session "Cache utilization was 23% — consider keeping CLAUDE.md stable to improve prompt caching."
Phase Completeness Missing artifacts (tests, docs, review) for each phase "Feature shipped without E2E tests — consider adding /e2e to your workflow."
Context Discipline Context window usage at session end, number of compactions "Session hit 82% context usage — offload research to Stack Scout earlier."
Anti-patterns Recurring mistakes across 3+ sessions "This is the 3rd session with skipped code review — proposing a CLAUDE.md rule to make review mandatory."

Plan Staleness Detection

During the Code phase, check-plan-staleness.sh compares files referenced in plan.md against the plan's commit SHA. If source files have changed since the plan was written, the script assesses severity and recommends action.

Severity Levels

SeverityCriteriaRecommendation
noneNo plan-referenced files changed since plan commitProceed normally
minor1–2 files changed, <50 lines totalReview changes, then proceed
major3+ files changed or >50 lines modifiedRefresh the plan before continuing
criticalPlan-referenced file deleted or renamedRefresh the plan (mandatory)

Vibe Score Integration

The plan_revision_count field in state.json tracks how often specs change mid-feature. Frequent plan revisions indicate unstable requirements and reduce the session's Vibe Score. The Performance Coach monitors this metric across sessions to detect planning pattern issues.

Erosion & Drift Tracking

VibeCrew monitors two forms of session degradation: drift (agents exploring instead of progressing) and code erosion (increasing complexity metrics over time).

Drift Tracking

A two-tier system detects when agents spend too much time exploring rather than making progress.

PhaseSoft Warning
(drift-tracker.sh)		Hard Escalation
(drift-circuit-breaker.sh)
Plan40 exploration calls60 exploration calls
Design30 exploration calls45 exploration calls

Test15 exploration calls25 exploration calls
Docs15 exploration calls25 exploration calls

Soft warnings are emitted by drift-tracker.sh (PostToolUse hook) and never block. Hard escalation via drift-circuit-breaker.sh (Stop hook) creates a WIP commit and blocker signal, prompting the agent to change approach. The circuit breaker is fail-open — it never prevents a session from stopping.

Code Erosion

collect-erosion-metrics.sh gathers complexity metrics (lines of code, cyclomatic complexity, function length, import count) and calculate-erosion-score.sh computes a 0–100 erosion score.

Session Learnings & CLAUDE.md Mutations

When the Performance Coach detects a recurring anti-pattern (appears in 3+ sessions), it proposes a permanent rule change to the project's CLAUDE.md file. These mutations are the mechanism by which VibeCrew gets smarter over time.

How Mutations Work

StepWhat Happens
1. DetectionPerformance Coach identifies a pattern appearing in 3+ sessions (e.g., "tests always written after code" or "docs consistently skipped").
2. ProposalCoach drafts a concrete CLAUDE.md rule using a standard template. Example: "Always run /tdd before implementing — write the test first."
3. ApprovalThe proposal is shown to the user for approval. Mutations never auto-apply — the user always has final say.
4. Applicationapply-mutation.sh appends the rule to the Session Learnings section of CLAUDE.md.
5. PruningSession Learnings are capped at 15 entries. When a new rule is added past the limit, the oldest entry is removed to keep CLAUDE.md lean.
⚠
Why 15 learnings max?

Research shows oversized CLAUDE.md files increase agent cost 20%+ without improving success rates. The cap ensures the file stays under 200 lines. Old learnings that haven't prevented their anti-pattern get pruned first.

Cross-Project Telemetry

VibeCrew tracks anonymized performance data across all your projects. This isn't sent anywhere — it lives locally in the plugin directory and powers the /system-review command.

How It Works

StepWhat Happens
Auto-registrationDuring /setup, the project registers itself in the central plugin's project-registry.json. Project paths are replaced with anonymous aliases (project-001, project-002).
Data collectionAfter each /wrap, anonymized metrics (Vibe Score, agent usage, token counts, cost) are appended to telemetry/aggregate.json in the plugin directory.
Aggregation/system-review reads all registered projects' telemetry to compute cross-project trends: average scores, most-used agents, cost patterns, MCP adoption rates.

What /system-review Shows

SectionWhat It Contains
Score TrendsAverage Vibe Score trajectory across all projects — are you getting better over time?
Agent UsageWhich agents are used most, which are underutilized, and cost breakdown by agent.
Cost AnalysisPer-project and aggregate cost metrics. Identifies expensive patterns and cost-saving opportunities.
MCP AdoptionWhich MCP servers are active across projects and their impact on session efficiency.
Ecosystem ResearchThe System Reviewer agent checks for VibeCrew updates, new MCP servers, and community best practices.

Agent Persistent Memory

Some agents maintain persistent memory across sessions using two complementary mechanisms. This allows agents to learn from previous runs without relying solely on CLAUDE.md mutations.

Three Learning Mechanisms

MechanismStorageScopeUsed By
Performance Coach Mutations CLAUDE.md rules All agents (global) Performance Coach
Expertise Records .vibecrew/expertise/ JSON Cross-agent (structured) Builder, Code Reviewer
Agent Memory .vibecrew/memory/ Agent-private (free-form) Performance Coach, Code Simplifier, Security Auditor
■
Why three mechanisms?

Each serves a different purpose: CLAUDE.md mutations encode global rules that all agents follow. Expertise records store structured, queryable data (conventions, failure patterns, decisions) shared across agents. Agent memory stores private, free-form notes for unstructured learnings specific to one agent.

Skill Evaluation & Model-Change Resilience

VibeCrew tracks whether its skills remain effective as models improve. The /validate-skills command evaluates skill health, and model-change detection at session startup alerts you when re-evaluation is needed.

The Evaluation Loop

StepWhat Happens
1. DetectionSession startup compares the current model against .last-validated-model.txt. If changed, a one-line warning fires.
2. Evaluation/validate-skills runs 3-tier analysis: schema check, model-version tracking, and A/B test recommendations.
3. TestingCapability-uplift skills (analysis + action categories) are flagged for A/B testing via Skill Creator.
4. TrackingResults stored in .vibecrew/reviews/skill-health-*.json with model version and validation date.

Skill Categories

CategoryMaintenance Strategy
workflowDurable — encodes preferences, optimize triggers
analysisCapability-uplift — A/B test after model upgrades
actionCapability-uplift — A/B test after model upgrades
dashboardDurable — read-only, optimize for speed
utilityDurable — simple operations, minimal maintenance
✓
Schema Validation Hook

The validate-skill-schema.sh PostToolUse hook automatically validates every SKILL.md write. It checks required fields, category values, and context: fork / agent: pairing — catching schema errors before they reach production.

Regression Test Feedback Loop

When a bug fix (fix: commit) is made without an accompanying test, VibeCrew automatically generates a regression test skeleton to prevent the bug from recurring. This closes the gap between bug fixes and test coverage.

How It Works

StepWhat Happens
1. DetectionDuring /wrap, detect-fix-commits.sh scans the session's git log for fix: conventional commits. For each, it checks whether the same commit also modified test files.
2. GenerationIf no test changes accompany the fix, generate-regression-test.sh creates a test skeleton in the appropriate framework (BATS for bash scripts, Vitest/Jest for TypeScript projects). Skeletons include a skip marker for developers to fill in.
3. ScoringThe Vibe Score applies a -5 deduction per fix commit without a regression test (fix-without-regression). Fix commits with tests get no deduction.
4. ExpertiseBug-fix patterns are stored in the expertise knowledge base (domain: failures) for cross-session analysis of recurring bug categories.
5. MutationAfter 3+ sessions with uncovered fix commits, the Performance Coach proposes a CLAUDE.md rule: "When fixing a bug, always add a regression test that reproduces the original failure."

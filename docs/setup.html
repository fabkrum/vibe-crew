Getting Started

Installation from Scratch

A complete walkthrough from zero to a fully operational VibeOS environment.

Prerequisites

Verify these are installed before proceeding:

RequirementMinimum VersionCheck Command
Claude Code2.0.0+claude --version
Git2.30+git --version
GitHub CLI2.0+gh --version
Node.js18+ (for JS/TS projects)node --version
jq1.6+jq --version
macOS13+ (for native notifications)—

Step-by-Step Installation

  1. Install system dependencies

    These are needed for notifications, JSON parsing in hooks, and PR automation.

    bashbrew install terminal-notifier jq
brew install gh && gh auth login

  2. Add the plugin to your project

    The recommended approach is a central clone + symlink, especially if you'll use VibeOS across multiple projects. See Multi-Project Setup below for the full guide.

    bash# Recommended: Central clone + symlink (see Multi-Project Setup below)
mkdir -p ~/claude-plugins && cd ~/claude-plugins
git clone https://github.com/fabkrum/vibe-os.git
cd ~/projects/my-project
ln -s ~/claude-plugins/vibe-os/claude-plugin-vibe-os ./claude-plugin-vibe-os

    For alternative approaches (direct copy, git submodule), see the comparison table in the Multi-Project section.

  3. Verify plugin detection

    Start Claude Code in your project directory. It reads the .claude-plugin/plugin.json manifest and loads VibeOS automatically.

    bashcd /path/to/your-project
claude

    You should see the VibeOS session startup agent run on first launch.

  4. Run the setup wizard

    Inside Claude Code, run:

    claude code/setup

    The wizard walks you through terminal selection, notification testing, MCP server verification, git checks, and creates the .vibeos/ runtime directory.

  5. Install MCP servers (optional but recommended)

    Context7 saves ~1,500 tokens per API lookup by fetching documentation on-demand instead of pasting it into chat. Puppeteer enables browser automation for research and visual testing. Both are configured in mcp-servers.json.

  6. Verify the full pipeline

    • Notifications: Tested during setup wizard
    • Session startup: Exit and restart Claude Code — the startup agent should show a 3-line status summary
    • Phase gate: Try writing a source file before running /new-project — it should be blocked

Recommended

Multi-Project Setup

Most users work on multiple projects. Instead of copying VibeOS into every project, install it once and share it. This gives you a single source of truth, instant updates across all projects, and zero duplication.

How it works

Central install (one copy on your machine) ~/claude-plugins/vibe-os/ # the plugin — shared by all projects Per-project (symlink + local state) ~/projects/tripflow/ claude-plugin-vibe-os → # symlink to central install .vibeos/ # project-specific state ~/projects/saas-dashboard/ claude-plugin-vibe-os → # same symlink, different project .vibeos/ # its own state ~/projects/mobile-app/ claude-plugin-vibe-os → # same symlink, different project .vibeos/ # its own state

The plugin code (agents, hooks, scripts, commands) lives in one place. Each project gets its own .vibeos/ folder with its own backlog, session logs, scores, and config. Projects are fully isolated from each other.

Step-by-step

  1. Clone VibeOS to a central location

    Pick a permanent home for the plugin. ~/claude-plugins/ is a good convention.

    bashmkdir -p ~/claude-plugins
cd ~/claude-plugins
git clone https://github.com/fabkrum/vibe-os.git

  2. Symlink into your first project

    Create a symbolic link from your project to the central install. Use an absolute path so the link works regardless of where you open the terminal.

    bashcd ~/projects/my-project
ln -s ~/claude-plugins/vibe-os/claude-plugin-vibe-os ./claude-plugin-vibe-os

  3. Run /setup in the project

    Start Claude Code and run the setup wizard. This creates the .vibeos/ folder with project-specific state. Each project runs /setup once.

    bashclaude
claude code/setup

  4. Repeat for each new project

    For every new project, just create the symlink and run /setup. Two commands, under 30 seconds.

    bashcd ~/projects/another-project
ln -s ~/claude-plugins/vibe-os/claude-plugin-vibe-os ./claude-plugin-vibe-os

Updating VibeOS across all projects

Since every project symlinks to the same central location, updating is one command:

bashcd ~/claude-plugins/vibe-os && git pull

Every project picks up the changes instantly. No need to copy files, run installers, or touch individual projects. Check the Release Notes after updating to see what changed.

Make it even faster with a shell alias

Add this to your ~/.zshrc to create new VibeOS projects in one command:

.zshrc# Add to ~/.zshrc
vibeos-init() {
  ln -s ~/claude-plugins/vibe-os/claude-plugin-vibe-os ./claude-plugin-vibe-os
  echo "VibeOS linked. Run 'claude' then '/setup' to initialize."
}

vibeos-update() {
  (cd ~/claude-plugins/vibe-os && git pull)
  echo "VibeOS updated to $(cd ~/claude-plugins/vibe-os && git describe --tags 2>/dev/null || git log -1 --format=%h)"
}

Then for any new project: cd ~/projects/new-project && vibeos-init

Git and symlinks

By default, Git tracks symlinks as tiny pointer files (not the target contents). This means:

  • Your project repo stays small — only the symlink is committed, not the entire plugin
  • Teammates need their own central install — the symlink points to your local path, so each person clones the plugin to the same location or updates the symlink
For teams: standardize the path

Agree on a team-wide convention like ~/claude-plugins/vibe-os/. If everyone uses the same path, symlinks work across the entire team with zero config. Document this in your project's README or onboarding guide.

Comparing installation approaches

ApproachBest ForUpdate MethodDuplication
Central clone + symlink Solo devs, small teams git pull once → all projects updated None
Git submodule Teams needing pinned versions git submodule update per project Full copy per project
Direct copy Quick experiments, air-gapped Manual copy per project Full copy per project
Don't mix approaches

Pick one method and stick with it. If some projects use symlinks and others use submodules, updates become confusing and you risk running different VibeOS versions across projects without realizing it.

What's shared vs. what's project-specific

⇄

Shared (via symlink)

Agent prompts, hook scripts, slash commands, plugin manifest, MCP config, templates. These are the same across all projects and update together.

☗

Project-specific (.vibeos/)

Backlog, session logs, Vibe Scores, config, state, handoffs, workflows. Each project has its own isolated state folder that's never shared.

✍

Project-specific (project root)

CLAUDE.md, VISION.md, design-system.css, TDR, roadmap. These are created by VibeOS during the foundation phase and are unique to each project.

⚙

Machine-specific (~/.zshrc)

Shell aliases (vibeos-init, vibeos-update), shell traps, Warp Terminal config. Each developer sets these up once on their machine.

Terminal Setup

Warp Terminal

Warp is the recommended terminal for VibeOS. It provides tab deep-linking (click a notification and land on the exact session that needs attention), structured output blocks, Launch Configurations for instant workspace setup, and session restoration.

Everything you need — installation, deep-linking setup, keyboard shortcuts, Warp Drive, window layouts, and more — is covered on the dedicated Warp page:

Warp Tips & Tricks →

Using a different terminal?

VibeOS works with any terminal. You'll get macOS banner notifications regardless. The only difference is that non-Warp terminals can't deep-link to a specific tab — clicking the notification brings the terminal app to focus but you'll need to find the tab manually.

Troubleshooting

Notifications don't appear

  1. Test terminal-notifier directly: terminal-notifier -message "test"
  2. If nothing appears, reinstall: brew install terminal-notifier
  3. Check macOS: System Settings → Notifications → terminal-notifier → Allow Notifications
  4. Check VibeOS config: verify .vibeos/config.json has "notifications": true
  5. Warp deep-links not working: see the deep-linking guide on the Warp page

MCP servers not available

  1. Context7: Verify it's configured in your Claude Code settings. Try a test query
  2. Puppeteer: Ensure the Puppeteer MCP server is running and configured
  3. Both are optional. VibeOS works without them — you just miss the token efficiency benefits

Stale locks or corrupted state

  1. Run ./scripts/error-recovery.sh to clear lock files and repair corrupted JSON
  2. This resets any in-progress tasks that were interrupted by a crashed session
